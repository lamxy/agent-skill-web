## 用途

适用于分析单个 GitHub 仓库，尤其是可能较大、结构复杂、README 过长、需要多轮外部请求才能形成结论的目标。

目标：
- 先以最小证据成本形成可用结论
- 避免子代理在弱网或差代理环境下静默扩大检索范围
- 当范围、成本或等待时间超出预算时，先升级给主代理；必要时再请求用户确认

## 默认流程

### 第一步：轻量探测
默认只允许读取以下范围：
- README
- 顶层目录结构
- 1 个最关键文件或页面

主代理或子代理应先回答：
- 仓库大致是什么
- 已验证的核心证据是什么
- 现有证据是否已经足够回答用户问题

若足够，则直接停止，不继续扩大范围。

### 第二步：范围判断
若轻量探测后仍不足，必须先判断是否超出预算。

以下情况默认视为“超预算风险”：
- 需要继续读取多个二级目录或多个关键文件
- 需要并行分析多个 GitHub 仓库后再汇总
- 需要多次外部请求才能拼出基本结论
- 外部请求已明显变慢，或 Fast mode 不可用
- 子代理已长时间无结果或出现阻塞迹象

### 第三步：升级而不是静默深挖
当目标超出预算时，子代理不得继续静默扩张检索范围，必须先返回：

```text
[agent] role=<sub-agent>
state=partial|blocked
delta=<目前已验证的最小结论>
evidence=<已读范围与关键证据>
risk=<范围扩大、慢网或等待成本>
next=<建议缩小目标，或改为串行轻量分析>
ask=<是否允许扩大到哪些目录、文件或第二个仓库>
```

主代理收到后应做二选一：
- 缩小目标，基于现有证据继续输出
- 若用户问题确实要求更大范围，再请求用户确认后继续

## 派发模板

复杂仓库分析默认使用以下派发格式：

```text
[dispatch]
task=<分析单个 GitHub 仓库，并先做轻量探测>
cmd=<先读 README、顶层目录和 1 个关键文件；若超预算则停止并返回 ask>
context=<用户问题、目标仓库、当前已知边界>
output_format=<sub-agent-output-template.md，最多 10 行；禁止表格、代码块、长报告>
```

## 主代理约束

- 若某个仓库已明显超预算，不要同时再派发第二个重型仓库分析子代理
- 若已有一个子代理完成，另一个子代理阻塞，允许基于已完成结果先输出部分结论
- 若存在 hook 噪音、PostToolUse 错误或 remember 目录异常，先判断是否真正阻断了分析，不要因噪音重复整个外部请求链
- 默认优先“已验证部分 + 未验证边界 + 下一步建议”，而不是等待完整覆盖
