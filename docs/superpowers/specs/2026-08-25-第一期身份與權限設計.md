# 第一期身份與權限設計

## 1. 目標與邊界

本設計對應 Taskmaster 任務 #2「M1 身份與權限模組實作」。第一期的首要目標是讓身份識別、登入狀態、角色授權、審核人管理與作者迴避形成可運行、可測試的功能閉環。

第一期實作以下能力：

- 未登入訪客可取得穩定的匿名 UUID，並以明確的聯合型別與已登入 UID 區分。
- 開發與測試環境可經本地身份提供者完成登入；正式環境沒有正式身份提供者時必須拒絕登入，不得偽造 SSO。
- 使用 PostgreSQL 保存身份、工作階段、角色與審核人指派。
- 支援可疊加且帶作用域的角色：`employee`、`maintainer`、`reviewer`、`platform_admin`。
- 平臺管理員可新增及撤銷審核人指派，變更必須留下稽核事件。
- 審核資格同時檢查審核人作用域與作者／所屬團隊迴避。
- 提供登入、回呼、目前身份、登出及審核人管理 API。

以下項目延後至第二期：

- 真實 OIDC Authorization Code + PKCE、JWKS 驗證與金鑰輪替。
- 多身份提供者、MFA、Refresh Token 輪替與完整撤銷策略。
- 完整 CSRF Token、分散式速率限制、風險登入與安全事件中心。
- 複雜組織架構同步、即時群組同步與細粒度 ABAC 策略引擎。

延後上述項目是為了先完成系統功能，而不是把臨時登入冒充正式 OIDC。第一期仍保留明確的身份提供者介面，使第二期替換提供者時不需要重寫工作階段與授權模組。

## 2. 強制工程原則

### 2.1 反範式資料設計

所有資料表只保存邏輯業務 ID，不建立資料庫外鍵、不使用 `ON DELETE CASCADE`，Drizzle schema 不得呼叫 `.references()`。

原因是資料完整性需能跨服務、分庫分表與批量作業運作，不能依賴單一 PostgreSQL 實例的同步外鍵鎖。完整性改由以下機制保障：

- 應用層在同一交易中驗證必要的邏輯 ID。
- 唯一索引與檢查約束只約束單表內不變量。
- 重複請求依靠冪等鍵或唯一索引消除。
- 重要變更同步寫入 `domain_events`，供補償與對帳使用。
- 查詢所需的團隊、類型與分類資訊保存快照，避免授權路徑依賴多層關聯。

既有 migration 內的外鍵視為技術債；本任務觸及 schema 時一併移除，並提供相容既有資料庫的 `DROP CONSTRAINT IF EXISTS` migration。

### 2.2 第一期基本安全線

第一期不追求完整安全強化，但下列基本措施不能省略：

- 所有管理操作在伺服器端重新驗證身份與角色。
- 工作階段 ID 使用密碼學安全亂數，只把雜湊摘要存入資料庫。
- Cookie 設為 `HttpOnly`、`SameSite=Lax`、限制 `Path=/`，正式環境加上 `Secure`。
- 輸入使用 schema 驗證；錯誤回應不洩露秘密或資料庫細節。
- 秘密只從環境變數讀取；日誌不得輸出 Cookie、工作階段原文或提供者 Token。
- 正式環境未配置正式身份提供者時，登入端點回傳不可用，不得降級為本地身份。
- 狀態變更 API 僅接受非安全方法，依靠 `SameSite=Lax` 與伺服器端授權提供第一期基本保護；完整 CSRF Token 延後至第二期。

## 3. 模組架構

身份模組拆成五個邊界，讓提供者、工作階段與權限判斷可以分別測試：

```text
HTTP 路由
   │
   ├── IdentityProvider ── DevelopmentIdentityProvider / DisabledIdentityProvider
   │
   ├── IdentityResolver ── 已登入 UID / 匿名 UUID
   │
   ├── SessionService ── SessionRepository
   │
   ├── AuthorizationService ── RoleRepository / ReviewerAssignmentRepository
   │
   └── IdentityRepository / DomainEventRepository
                         │
                      PostgreSQL
```

- `IdentityProvider` 只負責取得外部身份聲明，不負責本地角色與工作階段。
- `IdentityResolver` 是 HTTP 層的唯一身份入口，避免各路由自行解析 Cookie。
- `SessionService` 建立、解析與撤銷不透明工作階段。
- `AuthorizationService` 實作 `hasRole` 與 `canReview`，路由不能重複拼裝授權規則。
- Repository 只封裝資料存取與交易，不把 Fastify request/response 帶入資料層。

## 4. 身份提供者與登入流程

### 4.1 統一介面

第一期定義以下概念介面；實際名稱可依現有 TypeScript 慣例微調：

```ts
interface IdentityProvider {
  beginLogin(input: BeginLoginInput): Promise<LoginRedirect>;
  completeLogin(input: LoginCallbackInput): Promise<ProviderIdentity>;
}

interface ProviderIdentity {
  uid: string;
  displayName: string;
  teamIds: string[];
}
```

`ProviderIdentity` 是通過提供者驗證後的最小可信聲明。角色不從 query string 或客戶端聲明取得，只能來自本地資料庫。

### 4.2 開發與測試提供者

`DevelopmentIdentityProvider` 僅在明確的開發／測試設定下啟用，用固定測試資料或經 schema 驗證的開發回呼產生身份聲明。它的用途是讓 API 與工作階段流程可端到端測試，不代表正式 SSO。

正式環境使用 `DisabledIdentityProvider`。其登入與回呼方法回傳服務不可用錯誤，直到第二期注入真實 OIDC provider。這個 fail-closed 行為避免把開發登入誤部署為正式登入。

### 4.3 登入資料流

```text
GET /api/auth/login
  → provider.beginLogin()
  → 開發環境導向本地 callback；正式未配置時回 503

GET /api/auth/callback
  → provider.completeLogin()
  → upsert identity（包含 teamIds 快照）
  → 建立不透明工作階段
  → 寫入 HttpOnly Cookie
  → 導向站內安全路徑
```

Callback 的導向目標只接受站內相對路徑；無效值回落至固定首頁，以免產生開放重新導向。

## 5. 身份解析與匿名 UUID

HTTP 層對外只暴露可判別的聯合型別：

```ts
type ResolvedIdentity =
  | { kind: 'authenticated'; uid: string; displayName: string; teamIds: string[] }
  | { kind: 'anonymous'; anonymousId: string };
```

解析順序如下：

1. 讀取工作階段 Cookie，對原文做摘要後查詢有效且未過期的 session。
2. 若有效，載入本地身份並回傳 `authenticated`。
3. 若無效或不存在，讀取匿名 Cookie。
4. 匿名 Cookie 必須是合法 UUID；否則產生 UUID v4 並寫回 Cookie。
5. 回傳 `anonymous`，絕不把 UUID 放入 `uid` 欄位。

安裝腳本生成器使用相同的穩定介面：優先使用已登入 UID；未登入則使用已持久化的匿名 UUID。由於兩者帶有不同 `kind`，遙測不會把匿名使用者錯標為登入帳號。

## 6. 工作階段設計

工作階段採伺服器端不透明 Token：

- 建立時產生至少 32 bytes 的安全亂數並以 URL-safe 形式交給 Cookie。
- 資料庫只保存 `SHA-256` 摘要，不保存原文。
- Session 保存 `uid` 邏輯 ID、建立時間、到期時間、最後使用時間與撤銷時間。
- 每次解析時檢查到期與撤銷狀態；登出只需標記撤銷並清除 Cookie。
- 第一期使用固定有效期；滑動續期、裝置管理與 Token 輪替延後。

工作階段查詢以摘要主鍵完成，不依賴身份表外鍵。身份不存在或停用時，解析結果視為未登入，並可由後續對帳清理孤兒 session。

## 7. 角色與作用域

角色採可疊加模型，一個 UID 可同時擁有多個角色。每筆指派包含：

- `role`：`employee | maintainer | reviewer | platform_admin`
- `scopeType`：`global | team | package_type | category | package`
- `scopeValue`：全域作用域使用空字串，其餘保存邏輯值
- `active`、指派人、建立與撤銷資訊

核心函式：

```ts
hasRole(uid, role, scope): Promise<boolean>
```

匹配規則是「指定角色存在有效指派，且其作用域覆蓋要求的作用域」。`platform_admin` 不會在資料層被隱式改寫為其他角色；需要管理員旁路時，由明確的授權策略判斷，以便測試與稽核。

## 8. 審核人指派與作者迴避

審核人管理以獨立的 `reviewer_assignments` 保存查詢快照：

- `reviewerUid`
- `packageType`
- `category`
- `assignedByUid`
- `active`、建立與撤銷資訊

新增指派時，同一審核人、套件類型與分類只能有一筆有效指派；重複請求回傳既有結果或明確衝突。撤銷採狀態更新而非刪除，以保留歷史。

`canReview(uid, packageId)` 按以下順序判斷：

1. 載入套件的 `ownerTeam`、`type` 與 `category` 快照；不存在即拒絕。
2. 載入審核人的 `teamIds` 快照；包含 `ownerTeam` 即拒絕，完成作者／團隊迴避。
3. `platform_admin` 可按明確策略放行，但仍遵守作者迴避。
4. 否則必須存在涵蓋該套件類型／分類的有效 reviewer 指派。

作者迴避放在服務端集中執行，任何建立 publication review 的路徑都必須呼叫同一函式。

## 9. 資料表草案

### 9.1 `identities`

| 欄位 | 用途 |
| --- | --- |
| `uid` | 提供者穩定 UID，主鍵 |
| `display_name` | 顯示名稱快照 |
| `team_ids` | JSONB 團隊 ID 陣列快照 |
| `provider_type` | `development` 或未來 `oidc` |
| `active` | 本地停用開關 |
| `created_at` / `updated_at` | 稽核時間 |

`team_ids` 採 JSONB 是有意的反範式：授權解析只需一次 identity 查詢，不需要 team membership join。團隊同步以整體快照覆寫，並由事件與對帳修正。

### 9.2 `identity_sessions`

| 欄位 | 用途 |
| --- | --- |
| `session_digest` | Token 摘要，主鍵 |
| `uid` | 身份邏輯 ID，不設外鍵 |
| `expires_at` | 到期時間 |
| `last_seen_at` | 最後使用時間 |
| `revoked_at` | 撤銷時間，可空 |
| `created_at` | 建立時間 |

索引涵蓋 `(uid, revoked_at)` 與 `expires_at`，支援撤銷及清理。

### 9.3 `role_assignments`

| 欄位 | 用途 |
| --- | --- |
| `id` | UUID 主鍵 |
| `uid` | 身份邏輯 ID |
| `role` | 角色字串 |
| `scope_type` / `scope_value` | 作用域 |
| `assigned_by_uid` | 指派人邏輯 ID |
| `active` | 是否有效 |
| `created_at` / `revoked_at` | 歷史資訊 |

以 `(uid, role, scope_type, scope_value, active)` 建立查詢索引；有效唯一性可用部分唯一索引保障。

### 9.4 `reviewer_assignments`

| 欄位 | 用途 |
| --- | --- |
| `id` | UUID 主鍵 |
| `reviewer_uid` | 審核人邏輯 ID |
| `package_type` / `category` | 審核範圍快照 |
| `assigned_by_uid` | 管理員邏輯 ID |
| `active` | 是否有效 |
| `created_at` / `revoked_at` / `revoked_by_uid` | 歷史資訊 |

以有效部分唯一索引避免重複指派；所有欄位均不建立外鍵。

## 10. API 契約

### `GET /api/auth/login`

- 開發／測試：啟動本地登入流程並導向 callback。
- 正式未配置 provider：`503 AUTH_PROVIDER_UNAVAILABLE`。
- 可選 `returnTo` 只接受站內相對路徑。

### `GET /api/auth/callback`

- 完成 provider 流程、更新 identity 快照、建立 session 與 Cookie。
- 驗證失敗回傳通用 `401 AUTHENTICATION_FAILED`，不回傳 provider 細節。

### `GET /api/auth/me`

- 已登入回傳 `{ kind: 'authenticated', uid, displayName, teamIds, roles }`。
- 未登入回傳 `{ kind: 'anonymous', anonymousId }`，必要時同時設定匿名 Cookie。

### `POST /api/auth/logout`

- 撤銷目前 session 並清除 Cookie。
- 沒有有效 session 時仍回傳成功，使操作具冪等性。

### `POST /api/admin/reviewers`

- 僅 `platform_admin`。
- 輸入 `reviewerUid`、`packageType`、`category`。
- 在同一資料庫交易內建立指派與 `reviewer.assigned` domain event。

### `DELETE /api/admin/reviewers/:id`

- 僅 `platform_admin`。
- 採邏輯撤銷；在同一交易內更新指派與寫入 `reviewer.revoked` domain event。
- 重複撤銷回傳成功或既有狀態，避免重試造成額外副作用。

## 11. 稽核與事件

審核人新增與撤銷必須和資料變更位於同一 PostgreSQL 交易，事件寫入現有 `domain_events`：

- `aggregate_type = 'reviewer_assignment'`
- `aggregate_id = assignment.id`
- `event_type = 'reviewer.assigned' | 'reviewer.revoked'`
- payload 保存 actor UID、reviewer UID、作用域、時間與必要追蹤 ID

事件不保存工作階段、Cookie 或提供者 Token。後續發布器可讀取未發布事件形成 outbox；第一期只要求可靠落庫與可查證。

## 12. Migration 策略

現有 migration runner 只執行單一初始化檔，無法安全增量演進。本任務將其改為按檔名排序的版本化 runner，並建立 migration 紀錄表。

- 新資料庫依序套用所有 migration。
- 既有資料庫可辨識已存在的基線表，登記基線後再套用身份 migration。
- 身份 migration 先以 `DROP CONSTRAINT IF EXISTS` 移除三個既有外鍵，再建立身份、session、角色與審核人表。
- 初始 migration 同步移除 `REFERENCES`，確保新建環境從一開始就符合無外鍵規則。
- 每個 migration 在交易內執行；成功才寫入版本紀錄。

## 13. 測試策略

實作遵循先失敗測試、再最小實作、最後重構：

- 單元測試：匿名 UUID 穩定性、身份聯合型別、session 摘要與到期／撤銷。
- 單元測試：角色疊加、作用域匹配、管理員策略與作者／同團隊迴避。
- Repository 整合測試：無外鍵 schema、角色與審核人唯一性、交易回滾、domain event 同步寫入。
- API 整合測試：本地登入、callback、`/me`、登出、未登入與無權限回應。
- API 整合測試：管理員新增／撤銷審核人、一般使用者拒絕、重複請求。
- 正式配置測試：未提供正式 provider 時登入必須為 503，確認開發身份不會洩漏到正式環境。
- 端到端測試：已登入 UID 與未登入匿名 UUID 都能給安裝腳本生成器提供穩定且不混淆的身份。

## 14. 驗收條件

完成本任務必須同時滿足：

- 所有新增與既有測試通過，TypeScript 型別檢查與 build 通過。
- PostgreSQL migration 可在乾淨資料庫及既有第一期基線資料庫執行。
- schema 與 SQL 中不存在新外鍵、cascade 或 Drizzle `.references()`；既有三個外鍵已移除。
- 正式環境不會啟用開發登入。
- `hasRole`、`canReview`、管理 API 與稽核事件具直接測試證據。
- 安裝身份解析可穩定區分 UID 與匿名 UUID。
- 技能來源、安裝位置、選用原因、安全檢查與使用方法已記錄在中文備查文件。
- 驗證完成後才把 Taskmaster 任務 #2 更新為 `done`。

## 15. 第二期擴展點

第二期新增 `OidcIdentityProvider` 實作統一介面，將 Authorization Code + PKCE、state/nonce、JWKS、issuer/audience 驗證封裝於 provider 邊界。登入完成後仍輸出相同 `ProviderIdentity`，因此 identity upsert、session、角色、審核與 API 不需要改寫。

若未來需要企業目錄同步，新的同步器只更新 `identities.team_ids` 快照並寫入 domain event；授權讀路徑仍保持單次查詢與應用層完整性。這正是第一期採反範式快照與 provider adapter 的主要原因。
