# 第一期發布審核模組設計

## 目標

Task #6 建立可追蹤、不可繞過的版本發布治理流程：維護者提交版本後，平台先做可重現驗證，再由符合迴避規則的審核人批准或拒絕；發布、撤下、緊急停用及內容修改都必須立即反映到搜尋、下載與腳本生成，並同交易留下 Audit 與 Outbox。

第一期以功能閉環為優先，只做必要的伺服器端授權、輸入驗證、隔離執行與交易一致性。完整供應鏈簽章、遠端沙箱集群、原生 macOS／Windows VM、外部通知渠道與全面安全加固延後。

## 已批准方案

採純 TypeScript 狀態機、治理服務與可插拔驗證 Runner。狀態規則留在應用層，PostgreSQL 只保存反範式業務記錄、交易事件及審計證據；不增加 XState，不使用資料庫 trigger 實作業務狀態機，不建立外鍵。

這樣做的原因是狀態轉換需要同時協調身份授權、外部驗證、Review、Audit、Outbox 與通知。應用層能明確測試每個分支，也保留未來拆服務與分庫空間。

## 狀態機

| 當前狀態 | 事件 | 下一狀態 | 執行者／條件 |
| --- | --- | --- | --- |
| `draft` | `SUBMIT` | `validating` | 套件維護者或平臺管理員 |
| `validating` | `VALIDATION_PASSED` | `review_required` | 所有聲明且首期支援的矩陣均通過 |
| `validating` | `VALIDATION_FAILED` | `draft` | 任一必要矩陣失敗或不支援 |
| `review_required` | `APPROVE` | `published` | 指定作用域審核人，且不是作者或所有團隊成員 |
| `review_required` | `REJECT` | `draft` | 同上，必填理由 |
| `review_required` | `REVISE` | `draft` | 維護者修改版本內容 |
| `published` | `REVISE` | `draft` | 任何版本內容修改，下載立即失效 |
| `published` | `DEPRECATE` | `deprecated` | 維護者或平臺管理員 |
| `published` | `DELIST` | `delisted` | 維護者或平臺管理員，必填原因 |
| `published` | `EMERGENCY_DISABLE` | `emergency_disabled` | 僅平臺管理員 |
| `deprecated` | `DELIST` | `delisted` | 維護者或平臺管理員 |
| `deprecated` | `EMERGENCY_DISABLE` | `emergency_disabled` | 僅平臺管理員 |
| `delisted` | `EMERGENCY_DISABLE` | `emergency_disabled` | 僅平臺管理員 |

`emergency_disabled` 是終態。未列出的轉換固定回 `409 INVALID_VERSION_TRANSITION`。`validation_failed` enum 保留舊資料相容，但第一期失敗會保存 ValidationRun 後回到 `draft`，不把失敗狀態當成長期工作狀態。

目錄 API 不再允許呼叫者直接修改 `lifecycle`。所有版本欄位修改都視為需要重新審核：若版本為 `review_required` 或 `published`，更新與退回 `draft`、關閉 pending Review、Audit、Outbox 必須在同一交易完成；`validating` 中禁止修改。

## 提交與驗證流程

外部執行不能包在長資料庫交易中，因此採兩階段 CAS：

```text
transaction A
  draft --SUBMIT--> validating
  + validation_runs(running)
  + audit_logs
  + domain_events

外部 ValidationRunner 執行

transaction B
  validating --PASSED--> review_required + publication_reviews(pending)
  或 validating --FAILED--> draft
  + validation_runs 結果
  + audit_logs
  + domain_events
```

每次更新都以當前 lifecycle 作 compare-and-set。重複請求不會建立兩個有效 Review；程序在外部驗證期間中止時，管理員或原維護者可重試同一個 `validating` run，不直接發布。

### 驗證證據

每個目標矩陣保存：Runner 名稱與版本、OS、Client、腳本 digest、開始／結束時間、安裝退出碼、是否收到白名單遙測、卸載退出碼、人工清理檢查、狀態與結構化錯誤碼。工作台展示證據，不只展示布林結果。

### 第一期 Runner

- `linux`：使用乾淨 Docker 容器，掛載只讀腳本與可寫臨時目錄；執行安裝、捕獲遙測 payload、執行卸載並檢查退出碼。
- `windows`：在 WSL 主機使用 PowerShell 7 Runner 真實執行 `.ps1`，結果明確標記 `powershell-wsl`，不冒充原生 Windows VM。
- `wsl`：使用 Linux Runner 並加入 WSL 能力標記；只驗證聲明為 WSL 的後續版本。
- `macos`：第一期沒有可信 Runner，結果為 `not_supported`。若版本聲明 macOS，提交不得通過；第二期接入 macOS VM adapter。

首期產品鎖定的可發布矩陣仍是 Linux／Windows × Codex／Claude Code。Runner registry 接受新增 OS 與 Client adapter，但沒有 Runner 時不能偽造成功。

## 審核與作者迴避

Review 提交時保存 Package 與 Version 快照，但不預先綁死單一審核人。任何符合 `reviewer_assignments(package_type, category)` 或 `platform_admin` 的身份都可在工作台看到 pending Review；決議時再寫入 `reviewer_uid`。

`AuthorizationService.canReview` 繼續強制：作者不能審核自己的版本，所有團隊成員不能審核本團隊套件。決議使用 CAS，第二位審核人對已決議 Review 操作時回 409。

工作台詳情依序展示：

1. 套件、版本、作者與所有團隊快照。
2. install／uninstall 命令全文。
3. OS／Client、適配來源與維護者。
4. 殘留副作用、人工清理步驟。
5. 腳本 digest 與平台遙測白名單。
6. 每個驗證矩陣的實際證據。
7. 批准／拒絕操作與審核標準提示。

## 撤下、停用與通知

第一期 `DELIST` 只接受 `effective_at <= 現在`，避免尚未有排程 worker 卻保存無法準時執行的未來撤下。交易會：

1. CAS 更新版本為 `delisted`。
2. 保存 `reason_code`、`effective_at`、操作者與說明。
3. 查詢該版本成功／已下載的安裝記錄，按 `uid` 去重建立站內通知。
4. 忽略匿名 UUID，因為沒有可信外部送達渠道。
5. 同交易寫 Audit 與 Outbox。

下載與腳本生成本來只接受 `published`，狀態提交後立即回 404。`EMERGENCY_DISABLE` 使用相同失效路徑，但只允許平臺管理員，並使用更高優先級通知類型。

通知第一期保存於資料庫及 Outbox，提供查詢 API；郵件、企業 IM 與推送 adapter 延後，不讓外部渠道阻塞撤下交易。

## 反範式資料模型

### `publication_reviews`

- `id`：穩定 UUID。
- `package_id`、`version`、`package_type`、`category`、`owner_team`、`author_uid`：提交時快照。
- `validation_run_id`：邏輯 UUID，不建立外鍵。
- `reviewer_uid`：決議前可空。
- `status`、`decision_reason`、`created_at`、`decided_at`。

### `validation_runs`

- `id`、`package_id`、`version`、`script_digest`、`status`。
- `requested_by_uid`、`runner_version`。
- `matrix_results` JSONB：保存每個 OS／Client 的完整證據快照。
- `started_at`、`ended_at`、`error_code`。

### `version_delistings`

- `id`、`package_id`、`version`、`reason_code`、`reason_detail`。
- `effective_at`、`actor_uid`、`created_at`。

### `user_notifications`

- `id`、`recipient_uid`、`notification_type`、`package_id`、`version`。
- `payload` JSONB、`status`、`created_at`、`read_at`。
- 以 `(recipient_uid, notification_type, package_id, version)` 的有效記錄唯一索引避免重複。

所有表只使用邏輯 ID 與必要快照，禁止 `FOREIGN KEY`、`REFERENCES`、級聯及 Drizzle `.references()`。

## API 契約

```text
POST /api/packages/:packageId/versions/:version/submit-review
POST /api/packages/:packageId/versions/:version/validation/retry

GET  /api/reviews?status=pending&os=&client=&cursor=&limit=
GET  /api/reviews/:id
POST /api/reviews/:id/approve
POST /api/reviews/:id/reject

POST /api/packages/:packageId/versions/:version/deprecate
POST /api/packages/:packageId/versions/:version/delist
POST /api/packages/:packageId/versions/:version/emergency-disable

GET  /api/notifications?status=unread&cursor=&limit=
POST /api/notifications/:id/read
```

審核理由、撤下原因、時間、OS／Client 與分頁參數使用 Fastify schema 驗證。授權全部在服務端完成；不存在與不可見資源使用 404，未登入 401，身份存在但權限不足 403，狀態衝突 409。

## 交易與失敗語義

- 狀態、Review／Delisting／Notification、Audit、Outbox 必須同交易。
- Outbox insert 失敗時整個業務交易回滾；Audit 不得在提交後另寫。
- Docker／PowerShell runner 超時、不可用或缺少能力都形成失敗 ValidationRun，不吞錯、不自動批准。
- 通知外部發送失敗只影響後續 dispatcher；撤下交易已保存通知與 Outbox 後即成功。
- 重複提交、批准、拒絕、撤下以 CAS 和唯一索引保持冪等或明確 409。

## 測試策略

### 單元測試

- 逐一覆蓋所有合法轉換及每個非法轉換。
- 作者、同團隊、未指派審核人與管理員授權邊界。
- 修改待審／已發布版本必須退回 draft；validating 禁止修改。
- 未支援 OS／Client、驗證失敗、重試與殘留聲明規則。

### 記憶體整合測試

- 提交 → 驗證通過 → pending Review → 批准 → 可下載。
- 拒絕 → draft；修改 → 重新審核；第二位審核人 CAS 失敗。
- 撤下後下載與腳本生成 404，UID 通知建立，UUID 不建立。

### PostgreSQL 整合測試

- 驗證狀態、Review、Audit、Outbox 同交易。
- 強制 Outbox 失敗證明全部回滾。
- 重複提交／決議唯一性與併發 CAS。
- 外鍵數量保持 0。

### 真實 Runner 驗收

- Docker Linux：乾淨容器安裝成功、遙測 payload 可得、卸載成功。
- PowerShell 7：成功、失敗與尾部佇列行為。
- macOS 缺少 Runner 時明確 `not_supported` 且不能進入待審。

## 非目標與第二期擴展

- 不在第一期提供原生 macOS／Windows VM 集群。
- 不在第一期執行延時撤下；只接受立即生效時間。
- 不在第一期接入郵件、Slack、Teams 或企業 IM。
- 不在第一期新增公私鑰供應鏈簽章；沿用 SHA-256 完整性 digest。
- 不提前做全面沙箱加固、惡意程式分析或組織級風險引擎。

上述能力都透過 Runner、NotificationDispatcher 與簽章 adapter 保留擴展點，不改變第一期核心狀態與 API 語義。
