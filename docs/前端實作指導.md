# 前端實作指導

本文件是 Task #9 各子任務的實作依據，綜合兩次需求澄清與線框預覽結論。與 `docs/前端API契約.md` 搭配使用：該文件描述 HTTP 契約，本文件描述介面決策與視覺規範。

線框存於 `design/wireframes/`，可直接在瀏覽器開啟。Task 9.7 的權威線框為 `審核者管理線框.html`、`版本治理線框.html`、`稽核日誌線框.html` 與 `我的安裝線框.html`。

線框只鎖定資訊架構、互動模型與 design token，不作為像素級規範。實作與線框衝突時，以本文件的文字規範為準。

## 頁面實作流程

實作任何頁面前，先產出該頁面的線框原型並保存到 `design/wireframes/`，交由使用者審核原型結構是否滿足需求，取得確認後才開始寫實作程式碼。未經審核不得直接進入頁面實作。

已完成審核的頁面：技能池列表頁、詳情頁、上架頁、安裝頁、作者分析頁、審核工作台待審列表頁、審核詳情頁、管理後台三頁與我的安裝頁。Task 9.7 已通過線框門檻，可以進入生產實作。

線框使用專案級 `prototype` 技能產出，單次只探索一個頁面。線框必須使用真實產品資料與真實後端欄位，不得使用 lorem ipsum，也不得虛構後端不存在的欄位。

第一期前端原則仍採 PC 優先；Task 9.7 依使用者明確要求增加 `390px` 手機自適應驗收，桌面表格在手機改為卡片或單欄表單，不允許整頁橫向捲動。Task 9.7 四頁均採單一方向，不建立多方向比較。

審核通過後，將該頁面的結構決策寫入本文件，並同步更新對應的 Task Master 子任務。

## 已定案的技術選型

前端採 Vite 與 React，置於 `web/`，建置產物由 Fastify 靜態託管。

此決策取代 Task #9 任務詳情中「建議使用 React/Next.js」的原始建議，理由如下。平台第一期僅供企業內部員工使用，即使允許居家訪問也不對外公開，因此沒有 SEO 需求，Next.js 的 SSR 優勢在此場景歸零。同源託管可直接複用既有的 opaque session 與 `HttpOnly` Cookie，不需要 CORS、`SameSite=None` 與本地 HTTPS，也讓「完整 CSRF 體系延後到第二期」這個決定維持安全。依 `AGENTS.md` 第 4 節，無明確收益不引入重依賴。

第二期若需要 SSR，頁面元件為純 React，遷移主要影響路由層與資料獲取，成本可控。

## 設計系統

專案沒有既有設計系統或元件庫，token 由線框確立，實作時定義為 CSS 自訂屬性。

色彩中性色帶輕微冷偏，與強調色同向，避免純灰讀起來像未經選擇。語意色與強調色分離：強調色只用於主要動作與選中態，成功、警告、危險三色專用於狀態表達，不得互相借用。

必須同時定義淺色與深色兩套 token。深色定義只覆寫 token，不得寫在元件規則內。淺色定義放在裸 `:root`，深色同時放在 `@media (prefers-color-scheme: dark)` 搭配 `:root:not([data-theme="light"])` 保護，以及 `:root[data-theme="dark"]`。任何顏色都不得只存在於媒體查詢或 `[data-theme]` 區塊內。

字體使用系統字體堆疊，需包含繁體中文字型；等寬字體用於版本號、路徑、命令與檔名。數字對齊處使用 `font-variant-numeric: tabular-nums`。

### 審核詳情頁：Evidence Desk

單一 PC 線框保存於 `design/wireframes/審核詳情線框.html`。頁面延續 Queue Ledger 的高密度證據語言：左側依序呈現驗證矩陣、安裝／解除安裝命令全文、殘留聲明與驗證歷程；右側使用 sticky 決議欄，持續顯示矩陣、遙測、清理與殘留摘要。

2026-08-27 已完成生產實作。`ReviewDetailPage.tsx` 透過 `GET /api/reviews/:id` 載入權威 `ReviewWorkbench`，矩陣以 `expectedMatrix` 為主列出缺失結果；遙測與清理摘要同樣要求每個預期目標都有結果，避免空陣列被誤判為完整。核准呼叫 `POST .../approve` 並先顯示原生 modal 確認層，駁回呼叫 `POST .../reject` 且空理由會顯示錯誤並把焦點送回欄位。成功決議使用伺服器回傳的 `review` 切成唯讀狀態，不在前端自行推導生命週期；409 自動重載權威狀態，網路或可重試錯誤先鎖定決議重送並要求同步。

PC 驗收以 1440×900 完成：主證據欄與 350px sticky 決議欄同屏，整頁沒有橫向溢出；命令表格只在自身容器保留捲動能力。第一期不建立手機專用版面。

### Task 9.7：管理後台與我的安裝

四頁線框已於 2026-08-28 通過審核，統一沿用高密度 Ledger 語言，並增加 `390px` 手機自適應。管理後台使用相同頂層導覽與「審核者管理／版本治理／稽核日誌」分頁；我的安裝保留一般員工導覽，不暴露管理入口。

審核者管理採 **Scope Registry**：桌面以有效指派表格呈現 `ReviewerAssignment`，手機改為卡片；新增表單只提交 `reviewerUid`、`packageType`、`category`，撤銷必須二次確認。實作已補齊 `GET /api/admin/reviewers` 與 `GET /api/admin/reviewer-candidates`；身份候選顯示姓名、UID、團隊，類型與分類由 Catalog 真實資料聯動產生，避免使用者猜內部值。

版本治理採 **Lifecycle Console**：先透過 Catalog API 定位套件與版本，再於固定側欄選擇標準撤下或緊急停用。標準撤下提交 `reasonCode`、可選 `reasonDetail` 與 `effectiveAt`；緊急停用只允許 global `platform_admin`，兩種不可逆操作都需二次確認，並只採信伺服器回傳的生命週期。

稽核日誌採 **Audit Ledger**：使用 `GET /api/audit/logs` 的 `eventType`、`actorUid`、`targetType`、`targetId`、`from`、`to`、`cursor` 與 `limit`，桌面表格、手機卡片，詳情層顯示 `details`、`ipAddress` 與 `userAgent`。日誌只讀且僅限 global `platform_admin`，分頁固定使用 `occurredAt + id` cursor。

我的安裝採 **Install Registry**：只呈現 `GET /api/me/installations` 回傳的 `packageId`、`packageName`、`currentVersion`、`availableVersion`、`status` 與 `upgradeAvailable`，支援全部／可升級／最新版篩選。卸載入口先回到套件目標選擇，再以 CatalogDetail 的真實 OS／Client 生成腳本；不得從 `MyInstallation` 推測目標。現有 `InstallPreviewPage` 把腳本 `action` 固定為 `install`，正式實作需擴充為 `uninstall`。

Task 9.7 瀏覽驗收發現一項可泛化的 UX 規則：任何要求使用者填寫 `packageId`、`uid`、版本、分類、類型、角色、狀態、OS、Client 或作用域的欄位，只要系統已有權威資料來源，就必須使用真實 API 候選、聯動選項或可搜尋選擇器，不得使用無提示的自由文字輸入。每個內部值欄位需同時說明「值從哪裡來」與「選擇後影響什麼」。後續 Task 9.8 及所有頁面修復都要逐頁檢查此規則；缺少候選 API 時先記錄後端契約缺口，不能要求使用者猜值。

### Task 9.8：頁面狀態與無障礙統一

2026-08-28 已完成全站共用層審計。所有非靜態資料頁均沿用 `usePageState` 與 `PageStateView`；`loading` 新增 `aria-busy`，`empty` 與 `partial` 以非打斷式 live region 宣告，`error` 仍依 `retryable` 決定是否提供重新載入。路由內容外層新增錯誤邊界，發生非預期 render 錯誤時保留頂層導覽並提供重試，不顯示內部錯誤細節。

全站新增「跳至主要內容」入口與主要導覽名稱；Catalog、審核、管理表單原本會覆蓋焦點環的 CSS 已改為 2px `:focus-visible` 實線。我的安裝、作者分析 OS 篩選與版本治理選取按鈕新增 `aria-pressed`，審核理由欄位以 `aria-invalid`／`aria-describedby` 關聯錯誤與提示。

色彩 token 依 WCAG AA 一般文字 4.5:1 門檻校正：淺色與深色 `ink-faint`、淺色 `ok`、`seal` 均由自動測試鎖定。第一期依全域規則以 PC 為驗收基準，實機覆蓋 1280×800 與桌面下限 1024×768；不為手機版擴張本任務。

R-3 逐頁結果：技能池、詳情、安裝／卸載、作者分析、審核工作台、版本治理與審核者管理的內部枚舉或識別均已有真實選項或由上游選擇導出。稽核日誌的 `eventType`、`actorUid`、`targetId` 是精確查詢條件，但目前沒有事件 facet、全身份或跨目標候選 API；本期補上值來源與精確比對影響說明，後端候選缺口記於 `docs/待決策與延後事項.md` R-3。Task 9.9 上架頁也已完成重查，套件、OS 與 Client 均使用權威候選，結論見本文件的上架頁章節。

### 技能池列表頁：Ledger

採表格版面與較高資訊密度。這是技術賦能工程師每週回訪多次的內部工具，應優化掃描效率而非首次驚豔。表格骨架亦可複用於審核工作台與管理後台。

欄位順序為套件、類型、狀態、支援範圍、殘留、安裝次數、成功率、操作。此順序體現「先確認能否安全運行，再看採用熱度」。

**不得引入可信等級概念**。歸檔線框中的「公司推廣／精品／已驗證」在後端不存在，`PackageRecord` 沒有對應欄位。狀態一律使用 `VersionLifecycle` 的真實值，安全性判斷使用 `hasResidualEffects`。若日後需要可信等級，那是後端需求，不能由前端虛構。

### 詳情頁：Target

版面以選擇安裝目標為主流程。頁面依序呈現名稱與基本資料、用途描述、目標選擇與安裝選項、下載、注意事項與使用說明、腳本版本紀錄、使用者回饋佔位、腳本組成說明。

下載區塊需同時顯示生成檔名與帶選項的完整執行命令，讓員工複製後可直接使用。

**詳情頁不得顯示中部安裝命令**。中部是平台內部的腳本片段，不是員工的決策依據。員工需要的是功能描述、注意事項與下載操作。此規則取代 PRD M3-8 中「下載頁展示安裝命令全文」的描述，該描述建立在已廢棄的 InstallPlan 原語模型上。

注意事項固定呈現三類：殘留副作用、所需權限邊界、會回報安裝結果。殘留為 `true` 時使用警告色並說明手動清理方式。

腳本組成說明必須標明上部與尾部由平台生成、腳本內不可見，中部由發布者維護。此說明的目的是讓員工理解遙測從何而來，不是技術文件。

未聲明支援的系統或 Client 顯示為停用態並標註原因，不隱藏。第一期優先支援 Linux 與 Windows、Claude Code 與 Codex，其餘目標保留位置以利擴充。

### 安裝目標的收斂定義

作業系統目標收斂為三項：`linux/macos`、`windows`、`wsl`。Linux 與 macOS 的安裝命令在多數情況下可共用，合併為單一目標可減少發布者重複填寫。此收斂需要後端把 `ScriptTargetOs` 從目前的 `'linux' | 'windows'` 調整為三值列舉。

Client 只記名稱，不含版本號。介面一律顯示「Claude Code」而非「Claude Code 1.8」。版本相容性由發布者在使用說明中自行描述。

第一期開放 `linux/macos`、`windows`、`wsl` 與 Claude Code、Codex。其餘目標在介面上顯示為停用態並標註原因，保留擴充位置。

### 腳本版本與變更紀錄

每份一鍵安裝腳本有自己的版本號，與技能版本相互獨立。腳本版本以 `v` 加遞增整數表示，首次建立為 `v1`，每次編輯儲存後自動遞增。

檔名格式為 `install-{packageId}-{packageVersion}-{os}-{client}-{userRef}-v{scriptVersion}.{ext}`，`linux/macos` 與 `wsl` 為 `.sh`，`windows` 為 `.ps1`。

每次遞增需記錄變更描述、時間與版本號。變更描述由發布者填寫，屬選填；未填寫時版本紀錄顯示「無描述資訊」，不得顯示空白或自動產生的佔位文字。

版本紀錄在詳情頁與上架頁均可查看。詳情頁顯示目前腳本版本與歷次變更，讓員工判斷腳本是否近期修改過。

刪除腳本採軟刪除：標記為不可見，不從紀錄中移除。已刪除的腳本不出現在列表與下載選項中，但版本紀錄仍可追溯。

### 腳本內的技能資訊

生成的腳本需寫入當前技能或工具的版本與發布日期。這些資訊在兩處顯示：執行 `--help` 時的說明輸出，以及安裝過程的提示訊息。

這些資訊同時作為遙測欄位上報，讓平台能區分同一技能不同版本的安裝成功率。

### 選項參數

發布者可為一鍵安裝腳本宣告選項參數，員工在詳情頁選擇後，平台將選定值寫入下載的腳本。

典型用途是安裝層級選擇：全域或使用者層級、專案目錄或家目錄。這類選擇無法由發布者預先決定，必須在安裝時由員工指定。

每個參數包含參數名、類型、說明與預設值。類型分為單選、開關與文字三種。參數名以雙連字號開頭，例如 `--scope`。

參數以環境變數原樣傳給中部命令，變數名由參數名轉大寫並加上 `ASP_OPT_` 前綴：`--scope` 對應 `${ASP_OPT_SCOPE}`，`--with-hooks` 對應 `${ASP_OPT_WITH_HOOKS}`。上架頁必須顯示此對應關係，發布者才知道在命令中如何讀取。

平台不解析也不改寫參數值，只負責傳遞。參數的語意由發布者的命令自行處理。

員工所選的選項隨遙測上報，用於分析不同安裝方式的成功率差異。

### 使用說明

發布者必須填寫腳本使用說明，描述如何執行這份腳本。說明顯示在詳情頁，並寫入腳本的 `--help` 輸出。

此欄位為必填。缺少使用說明的腳本，員工下載後不知道如何帶入選項參數。

### 隱私聲明

平台首頁底部需提供隱私聲明入口，說明遙測收集的完整範圍。此聲明是員工理解「安裝腳本會回報什麼」的權威來源，不是法律免責文字。

聲明內容需逐欄列出上報欄位並說明用途，明確寫出不收集的項目：命令輸出、檔案內容、環境變數。同時說明未登入時使用本機 UUID 識別、UUID 的存放位置與清除方式。

PRD 第 76 行已定義「上報欄位清單同時是隱私聲明範圍與審核判斷依據」，第 89 行要求新增欄位須重新通過隱私審核。因此隱私聲明的欄位清單必須與 `TELEMETRY_FIELDS` 保持一致，欄位變更時兩處同步更新。

詳情頁與上架頁的遙測欄位清單需連結至此聲明，避免在多處重複維護完整說明。

### 使用者回饋：第二期功能

PRD 第 40 行已將「點讚評論討論」列為 MVP 不做。第一期在資料庫設計時預留相應結構，但不實作功能。

詳情頁保留回饋區塊的版面位置，內容為停用態：讚與踩的按鈕不可點擊、計數顯示為破折號而非零，評論列表位置顯示「評論功能尚未實作」。區塊標題旁標註「第二期功能，尚未實作」。

此處刻意不隱藏區塊，目的是讓使用者知道功能規劃中而非缺失。計數不得顯示為 `0`，那會被誤讀為「沒有人給過評價」。

### 安裝頁：Inspect

安裝頁是執行前的最後確認，顯示平台生成後的完整腳本，讓員工在執行會改動自己機器的內容前看到全貌。

與詳情頁的分工必須明確：詳情頁回答「這個技能是什麼、要不要裝」且不顯示任何命令；安裝頁顯示完整的三段式腳本。這與「詳情頁不得顯示中部安裝命令」的規則不衝突，該規則禁的是攤開平台內部的中部片段，不是禁止員工檢視自己即將執行的東西。

版面順序為麵包屑、標題與目標標籤、這份腳本會做什麼、完整腳本、影響資源與所需權限、將上報的欄位、固定在底部的動作列。

「這份腳本會做什麼」只列出有確定來源的項目。UUID 寫入與執行結束回報屬平台固定行為，前端直接呈現；殘留說明來自 `preview.residualDescription`。區塊末尾註明發布者的安裝命令需展開完整腳本的中部自行檢視。

完整腳本區塊顯示 `GeneratedScript.script` 全文，帶行號、可捲動、可複製，中部以 seal 色底與上部尾部區分，並附圖例說明哪一段由平台生成。同時顯示 `digest` 供下載後比對。

分段切換第一期保留為純視覺佔位並標註「尚待實現」，不接功能。

影響資源與所需權限第一期顯示「發布者未提供此資訊」的空狀態。**禁止以靜態分析從 `installCommand` 推導寫入路徑或權限需求**：bash 是圖靈完備的，變數展開、`eval` 與間接執行都能繞過分析，推導錯誤比不顯示更糟。結構化欄位留到第二期，見 `docs/第二期需求收集.md` 的 P2-3。

此頁不需要新端點，`POST .../scripts` 回傳的 `GeneratedScript` 已提供所需全部資料。

實作於 `web/src/pages/InstallPreviewPage.tsx`，路由為 `/packages/:packageId/versions/:version/install`，安裝目標以 query 參數 `os` 與 `client` 傳遞。詳情頁的按鈕改為「檢視並下載腳本」，只負責導向此頁；腳本生成與錯誤處理都移到此頁，詳情頁不再直接觸發下載。

中部的色底範圍由後端生成的固定註解界定，不是行號硬編碼：bash 以 `# 維護者…命令：只在隔離子程序執行` 起、`_asp_exit_code=$?` 迄，PowerShell 以 `# 維護者…命令` 起、`if ($LASTEXITCODE -ne 0) {` 迄。後端調整這些標記時前端需同步，找不到邊界時全段不標示——標錯段落會讓員工誤判哪段由平台生成，比不標示更糟。

缺少 `os` 或 `client` 時必須拋 `ApiError` 而非一般 `Error`：`usePageState` 只保留 `ApiError` 的訊息，一般 `Error` 會被替換成通用文案，使用者就看不到「回詳情頁重選」這個可行動的指示。此處 `retryable` 為 `false`，重試不會補上缺少的參數。

2026-08-28 已完成 Task 9.9 的第一期降級實作。因 D-3 的 `PackageVersionRecord` 與建立版本 API 仍只有單一 `installCommand`／`uninstallCommand`，`/publish` 明示「一次只能建立一個系統與 Client 組合」，只呈現一列 Matrix，且只把該列保存到後端。前端不得暫存或假裝保存其他組合；完整多目標資料模型與介面由高優先 Task 13 承接。

**2026-08-29 更新：Task 13 已完成，上述 9.9 降級限制全部解除。** `/publish` 現在支援完整六組合，每組各自獨立保存命令、選項、使用說明與殘留聲明；頁面不再顯示「一次只能建立一個」的限制文案。以下完整 Matrix 契約即為當前實作的權威描述。

Task 13 補充的實作邊界：所有寫入只依伺服器成功回應更新畫面，不做樂觀假存。複製先開來源預覽，確認後才呼叫 `copy-from`；刪除採用伺服器軟刪除回應。重載走 `GET /versions/:version`，由 query `?packageId=&version=` 選定。草稿建立後表單不再整體鎖定，已保存的 target 仍可繼續編輯。禁止虛構後端不存在的欄位（如可信等級）。

版面以安裝腳本列表為核心。發布者為每個「系統 × Client」組合各填一份中部命令。

列表每列呈現目標組合、填寫狀態、腳本版本、腳本語言、字元數、選項參數數量與生成檔名樣式，並提供編輯、複製命令、版本紀錄、刪除四個操作。狀態分為已填寫、複製自其他組合、待填寫三種。列表下方提供「加入組合」的系統與 Client 下拉選擇。

編輯區下方提供本次變更描述輸入框，儲存後腳本版本自動遞增。刪除為軟刪除，列表下方需說明「刪除的腳本改為不可見，仍可在版本紀錄中追溯」。

**必須支援跨組合複製**。Linux 與 macOS 的命令多數情況可共用，編輯區需提供已建立腳本的複製按鈕，點擊後將該組合的中部命令填入編輯框，填入後可自行調整。複製來源需提供預覽，避免誤選。從其他組合複製而來的項目在列表中標記來源；內容經修改後標記改為已填寫。

已建立的腳本可刪除後重新編寫。已勾選但未填寫命令的組合會阻擋送出審核，並在送出列明確說明尚缺幾個組合。

編輯區必須提示三項禁止事項：不要寫 shebang、不要自行回報結果、不要讀取使用者識別。這三件事由平台在上部與尾部處理，發布者重複實作會與平台衝突。

殘留聲明使用開關搭配條件展開。`hasResidualEffects` 為 `true` 時，殘留說明與手動清理步驟均為必填，這與 `script-generator-service.ts` 的服務端校驗一致。

尾部將回報的欄位以唯讀清單呈現。基礎十一欄與 `TELEMETRY_FIELDS` 一致，新增的 `script_version` 與 `options` 需以不同樣式標示為新增欄位。清單需說明不收集命令輸出、檔案內容或環境變數。

選項參數區塊需呈現參數名、類型、說明與預設值四欄，可新增與刪除。區塊下方必須顯示參數名到環境變數的對應預覽，例如 `--scope` 對應 `${ASP_OPT_SCOPE}`。

使用說明為必填的多行輸入，需註明「說明會顯示在詳情頁，並寫入腳本的 --help 輸出」。

### Task 11：升級差異、支援入口、使用反饋與通知

四個介面依既有慣例各自產出單一線框並經審核，線框存於 `design/wireframes/` 的 `升級差異線框.html`、`支援入口線框.html`、`使用反饋線框.html`、`通知中心線框.html`。

**升級差異頁** 路由 `/packages/:packageId/versions/:version/diff/:targetVersion`，`:version` 是使用者目前安裝的版本。頁面逐一列出每個「系統 × Client」的變更旗標與 `contentDigest` 對照，並顯示新增、移除、變更的選項參數。`unchanged` 的組合仍必須顯示在清單中，否則使用者無法確認該組合確實沒變，只是被略過。

此頁**不得顯示任何命令全文**。後端的 `VersionDiff` 本身就不含命令，只有 digest 與旗標；前端也不得改由其他端點補取。這與「詳情頁不得顯示中部安裝命令」是同一條規則，已由前後端測試各自固定。

`requiresReapproval` 為真時，「檢視並下載升級腳本」以核取方塊擋住，使用者必須明示已閱讀變更才能繼續。這是使用者層級的重新確認，不是治理層的重新送審。

**支援入口** 在詳情頁以區塊呈現，對所有能看到該套件的身分開放，包含未登入訪客。維護者設定介面在 `/admin/support`，採整組覆寫：介面必須明示「送出的清單即為完整結果，移除的渠道會被刪除」，因為後端不做增量合併。位址只有 `https?://` 與 email 兩種形態做成連結，其餘原樣顯示，不猜測協定也不自行補 `https`。

沒有渠道時顯示「維護者尚未設定支援渠道」的空狀態，不隱藏整個區塊。空狀態本身有作用：推動維護者補齊，也讓審核者看得出誰沒填。

**使用反饋** 的提交表單在詳情頁，開放匿名 UUID 提交。這與詳情頁既有的「點讚與評論」佔位是**不同功能**，不共用區塊：後者是 P2-1，第二期才實作，佔位保留停用態與破折號計數。實作 Task 11 時已把該佔位標題從「使用者回饋」改名為「點讚與評論」，避免兩者混淆。

反饋明細與統計只在 `/admin/support` 對維護者呈現。統計固定顯示全部七個分類含計數 0；平均滿意度無樣本時顯示破折號而非 0，並標示「數據僅供參考」——滿意度是自願填寫的自我聲明，與遙測同屬 best-effort。

**通知中心** 路由 `/me/notifications`，一次取回全部通知再於前端分流，切換分頁不重新請求，未讀計數才能在標記已讀後立即反映。標記已讀只依伺服器回應更新，不做樂觀假存。

`version_published` 的 payload 帶 `installedVersion`，前端據此直接連到升級差異頁。舊通知沒有此欄位時只導向套件詳情，不猜測使用者裝的是哪一版——差異比較需要來源與目標兩個版本，猜錯比不提供更糟。

### Task 10.6：登入頁、身份選單與角色導覽

線框為 `design/wireframes/SSO登入與身份體系線框.html`，第 6 節涵蓋登入頁、身份選單與三種頂欄狀態。

**身份解析集中在 `ViewerProvider`**，全站只發一次 `/api/auth/me`，各元件以 `useViewer()` 取用。三種結果必須分開處理，不可合併：`authenticated` 是已登入；`anonymous` 是明確的未登入，屬一等公民而非錯誤；查詢失敗時 `viewer` 為 `undefined`，代表「不知道是誰」，此時不得對角色做任何假設，一律以最小權限呈現。

**匿名不是攔截牆。** 技能池、詳情、支援入口對匿名開放，頁面正常渲染，只有需要身份的動作受限。不得因未登入就把整頁換成登入提示。

**導覽依角色增減入口，但這不是安全邊界。** 隱藏入口只為減少員工點進必然被拒的頁面；真正的授權判定一律在後端按範圍執行，前端不得假設隱藏等同保護。`canReview` 對審核人與平台管理員都回傳真，後者可審所有範圍。

**登入是整頁轉導，不是 fetch。** 後端會把瀏覽器送往 IdP 授權頁，該轉導無法在 XHR 內完成，因此以 `window.location.assign` 觸發。`returnTo` 只接受站內路徑，`//` 開頭與外部網址一律退回首頁——登入流程不得被用來轉導至外部站點，此規則前後端各有一份測試固定。

**登入頁只有一個按鈕，沒有帳密輸入框。** 平台從不接觸密碼，出現輸入框會誤導使用者以為平台收集憑證。身份服務不可用時顯示明確訊息並保留重試，不洩露內部配置細節。

**身份選單顯示 uid、團隊、角色與範圍。** 這是刻意的：使用者能據此理解「為何看不到某個入口」，而不是把權限差異當成故障。沒有角色的員工顯示「一般員工權限」而非空白——無角色是正常狀態，不是資料缺失。

**身份解析完成前不顯示登入鍵**，改以等高佔位維持頂欄高度。否則已登入者會先看到一次「使用公司帳號登入」再跳成姓名，讀起來像登入失效。

## 三段式腳本模型

平台生成的一鍵安裝腳本分三段，前端各頁面對三段的呈現規則不同，不得混淆。

上部負責初始化與身分識別：取得員工 uid，未登入時在本機產生並持久化 UUID，同一台機器沿用同一組；同時建立冪等鍵與環境資訊。中部是發布者填寫的安裝命令，在隔離的子命令下執行。尾部負責識別安裝結果，記錄時間、系統環境與成功或失敗，失敗時收集錯誤碼，然後上報遙測；離線時排入本機佇列，下次執行補交。

上部與尾部由平台生成，發布者不可見也不可修改。前端只在說明區塊描述其職責，不展示其內容。

生成腳本需呼叫 `POST /api/packages/:packageId/versions/:version/scripts`，必填 `targetOs` 與 `clientRuntime`。後端會校驗目標是否在該版本聲明的支援清單內，不符回 409。前端須依詳情資料先行過濾可選項，避免使用者選到必然失敗的組合。

生成檔名由安裝目標與使用者識別拼接，格式為 `install-{packageId}-{version}-{os}-{client}-{userRef}.{ext}`，Linux 與 macOS 為 `.sh`，Windows 為 `.ps1`。

## 分析頁的統計呈現

作者分析頁採 **Signal Board**，路由為 `/packages/:packageId/analytics`。此版面把健康判斷與可採取行動放在同一屏：頁首日期範圍與資料缺口、四項摘要、採用漏斗與失敗熱力圖位於主欄；成功率、可執行時間與版本分布位於側欄；待升級具名使用者保留在主欄下方。選擇此方向是因為作者的高頻任務是先判斷採用是否異常，再定位失敗版本與可觸達使用者；敘事式流程增加掃描距離，診斷矩陣則會過早弱化採用全貌。

頁面資料只使用 `GET /api/packages/:packageId/analytics` 回傳的真實欄位，不建立前端推估欄位。日期輸入轉為 UTC RFC 3339 閉區間，前端先拒絕反向期間與超過後端 366 天上限的請求；預設值使用瀏覽器當地日曆日，避免 UTC 跨日造成日期少一天。

失敗熱力圖由 `failureCells` 組成 `version × osType × errorCode` 稀疏矩陣，OS 篩選只在前端切換現有資料，不改寫統計。資料缺口直接呈現 `dataGaps.code`、`message` 與 `missingCount`；不得把缺失下載事件補成推估下載量。待升級表只顯示後端已依 OS／Client 相容性篩選的 `upgradeCandidates`，前端不得自行擴大名單。

成功率為 `null` 時顯示「尚無數據」，不得顯示 `0%`。所有作者分析回應必須分開呈現 `uid` 與 `uuid`，並標示 `best-effort` 與「數據僅供參考」。此要求源自遙測為盡力而為的機制限制，不是文案修飾。

圖表以手寫 SVG 實作，不引入圖表庫。三段漏斗與 Wilson 信賴區間誤差線在主流圖表庫中均無現成元件，仍需自訂；餅圖與熱力圖手寫成本低。圖表庫的預設行為在成功率為 `null`、需標示 best-effort 等要求下反而需要逐項覆寫。

## 頁面狀態

五種狀態的語義以 `docs/目錄頁狀態契約.md` 為準，本文件不重複。

責任邊界為：搜尋與詳情 API 只回傳 `empty` 或 `success`；`loading`、`error` 與 `partial` 由前端查詢層依請求生命週期與部分失敗情形映射。

非 `development` 環境未配置正式 IdP 時，身份模組使用 `DisabledIdentityProvider` 並拒絕登入。前端必須為此提供明確錯誤狀態，不得停在無限 loading。

## 待後端確認的事項

`PackageVersionRecord` 目前只有單一 `installCommand` 與 `uninstallCommand` 欄位，而 `supportedOs` 是陣列。一個同時聲明支援 Linux 與 Windows 的版本無法用單一命令滿足兩個平台，因為 bash 與 PowerShell 語法不相容。

PRD §6.2 已將「跨系統腳本一致性」列為待解難題，M3-4 要求填寫命令時須選擇適用系統，M3-6 要求按目標系統組合，M3-7 要求使用者只取得其系統對應的變體。`script-generator-service.ts` 的 `assertMaintainerCommand` 也已按 `targetOs` 分流校驗規則。

因此 per-target 命令是既定設計，缺的是儲存層支援。上架頁線框依此設計繪製。此事項需由後端補齊 schema 後前端才能完整實作，記錄於 `docs/待決策與延後事項.md` 的 D-3。

2026-08-26 的需求收斂另外帶來以下後端調整需求，一併記錄於 D-3：

`ScriptTargetOs` 需從 `'linux' | 'windows'` 擴充為 `'linux/macos' | 'windows' | 'wsl'`。

腳本需要獨立於技能版本的自身版本號與變更紀錄，包含描述、時間與遞增號；刪除為軟刪除，需要可見性標記而非實際移除。

版本記錄需支援選項參數的宣告：參數名、類型、說明與預設值，並在生成腳本時將員工選定值注入。

遙測欄位需從十一欄擴充，加入 `script_version` 與 `options`。此變更會影響 `TELEMETRY_FIELDS` 白名單、遙測 API 驗證與分析頁的統計維度，且十一欄白名單原已提交隱私審核，擴充需重新確認。

腳本需寫入技能版本與發布日期，並在 `--help` 與安裝過程顯示。

使用說明需成為版本記錄的必填欄位。

點讚、踩與評論的資料結構在第一期設計時預留，不實作 API 與功能。
