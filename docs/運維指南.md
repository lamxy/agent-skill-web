# 運維指南

## 演示環境

本機演示以 `npm run demo:reset` 重建：清除容器與 volume、重啟資料庫、套用 migration、載入示範資料。MVP 階段以此取代 VM 快照還原。

該指令會清空資料，因此在 `NODE_ENV` 非 `development` 或 `test` 時拒絕執行。

### 已驗證與未驗證的目標系統

| 目標 | 腳本執行驗證 |
|---|---|
| Linux / macOS | 已驗證（本機 bash） |
| WSL | 已驗證（`powershell-wsl` runner） |
| Windows 原生 | **未驗證** |
| macOS 原生 | **未驗證** |

未驗證不代表不可用：這兩個系統的生成腳本仍可正常下載，只是平台端沒有實際執行過。要覆蓋它們需要真實的多平台資源，屬正式推廣前的工作。

不得在介面或文件中聲稱四個系統都已驗證。這與「不用靜態分析推導權限」是同一條原則：不聲稱未經證實的事。

## WSL 開發環境

```bash
docker compose up -d --wait
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:55432/agent_skill_platform npm run db:migrate
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:55432/agent_skill_platform npm run db:check
npm run dev
```

前端另起一個行程，API 由 Vite 代理到後端，維持與正式環境相同的同源行為：

```bash
npm run dev:web        # 127.0.0.1:5173
```

需要示範資料時執行 `npm run db:seed`。資料庫使用 tmpfs，容器重啟後資料清空，需重新執行 migration 與 seed。此腳本僅供本機預覽頁面效果，不在測試或生產使用。

Docker Desktop 必須開啟目前 WSL distribution 的整合。若拉取 image 失敗，先檢查 Docker Desktop proxy；不要在 WSL 另起一套 daemon。Runner 使用本機既有固定 image 並帶 `--pull=never`，驗證期間不隱式下載。

## 必要設定

- `DATABASE_URL`：PostgreSQL 連線字串。
- `TELEMETRY_ENDPOINT`：生成腳本內注入的平台公開位址。
- secrets 只從環境提供，不寫入 repository 或日誌。

`NODE_ENV` 非 `development` 時，`loadConfig` 缺少 `DATABASE_URL` 會直接拋錯，身份模組也會退回 `DisabledIdentityProvider`。這是刻意的 fail-closed：正式 IdP 未配置時拒絕登入，不以開發身份靜默放行。

## SSO 設定

六個變數必須全部提供或全部留空，部分配置會在啟動時直接拋錯——半套配置會等到員工登入途中才失敗，比完全未配置更難排查。

- `OIDC_AUTHORIZE_URL`、`OIDC_TOKEN_URL`、`OIDC_USERINFO_URL`：IdP 端點。
- `OIDC_CLIENT_ID`、`OIDC_CLIENT_SECRET`：向 IdP 註冊本平台後取得。
- `OIDC_REDIRECT_URI`：須與 IdP 端登記的回呼位址完全一致，指向 `/api/auth/callback`。

選填項用於對齊各家 IdP 的欄位命名，取得 userinfo 規格後調整：

- `OIDC_SCOPE`：預設 `openid profile`。
- `OIDC_CLAIM_UID`、`OIDC_CLAIM_DISPLAY_NAME`、`OIDC_CLAIM_TEAMS`：預設 `sub`、`name`、`groups`。支援 `profile.departments` 這類巢狀路徑；團隊欄位接受陣列或以逗號、空白分隔的字串。

配置齊全時一律優先於開發身份，開發環境亦然。正式與 staging 環境拒絕端點指向本機位址，避免把開發期的模擬 IdP 誤帶上線——此檢查獨立於「正式環境禁用開發身份提供者」，後者擋不住模擬 IdP，因為它的 `kind` 是 `oidc`。

### 開發期模擬 IdP

企業 IdP 尚未開放前，以 `npm run dev:idp` 啟動本機模擬 IdP（預設 `127.0.0.1:4780`），並將 `OIDC_*` 指向它，見 `.env.example`。它實作 `/authorize`、`/token`、`/userinfo`，跑的是與正式環境相同的協議路徑；取得真實憑證後只需替換環境變數，程式碼不必更動。

`MOCK_IDP_PORT` 與 `MOCK_IDP_HOST` 可覆寫監聽位址。該腳本在 `NODE_ENV` 非 `development` 或 `test` 時拒絕啟動。

## 通知渠道

外部通知為加值，站內通知不受其影響：渠道未配置時通知照常寫入資料庫並顯示於 `/me/notifications`，只是不外送。

- `NOTIFY_SLACK_WEBHOOK_URL`、`NOTIFY_TEAMS_WEBHOOK_URL`、`NOTIFY_LARK_WEBHOOK_URL`：各渠道的 incoming webhook。只建立已配置的渠道，不會出現「看似啟用卻送不出去」的中間狀態。
- `PLATFORM_BASE_URL`：訊息內連結需要絕對位址，webhook 收件端不在平台網域內。未設定時連結為相對路徑，在外部渠道中不可點擊。

三個 webhook 變數都要求 `https://`，非 https 一律在啟動時拋錯——webhook URL 打錯字的後果是通知靜默消失，比啟動失敗難查得多。

郵件通道不綁定特定 SMTP 或服務商，取得公司郵件通道後實作 `EmailTransport` 介面並注入即可，不需改動模板或派送邏輯。

投遞結果分三類，決定是否重試：

| 結果 | 條件 | 行為 |
|---|---|---|
| 送達 | 2xx | 記錄後結束 |
| 可重試 | 429、5xx、連線失敗與逾時 | 重試至上限（預設 3 次） |
| 拒絕 | 其餘 4xx | 立即停止，重試只會得到相同結果並浪費配額 |

同一事件對同一端點只送一次：outbox 事件可能被重複取出，冪等由投遞紀錄保證。單一渠道失敗不影響其餘渠道。

### 首位平台管理員

`BOOTSTRAP_ADMIN_UID` 指定的 uid 登入時，若尚無 `platform_admin` 則自動取得 global 範圍的管理員角色。**此值必須與 IdP 回傳的 uid 完全一致**——不一致時該員工登入不會取得權限，而且不會有錯誤，只會看不到管理入口。

授予僅在該 uid 尚無 `platform_admin` 時發生，因此重複登入不會重複授予。授予紀錄的 `assignedByUid` 為 `bootstrap`，可與人為授予區分；同時寫入 warn 層級日誌。

管理員被撤銷後重新登入會再次取得，這是刻意的：否則撤銷最後一位管理員會讓平台永久失去授權能力且無法自救。若要真正移除該員工的管理權限，先清除此環境變數再撤銷。

未配置時不授予任何人。SSO 正式對接前務必設定，否則登入可用但無人能指派審核人。

## 單機部署

MVP 階段以 Docker Compose 單機部署，不使用 Kubernetes。決策與理由見 `docs/待決策與延後事項.md` 的 D-5。

```
npm run deploy:up      # 建置並啟動，含 migration
npm run deploy:logs    # 追蹤平台日誌
npm run deploy:down    # 停止（保留資料 volume）
```

`compose.deploy.yaml` 有三個服務：

| 服務 | 作用 |
|---|---|
| `postgres` | 具名 volume 持久化，不對外開放 port |
| `migrate` | 一次性執行 `dist/migrate.js` 後結束 |
| `app` | 待 migrate 成功後才啟動 |

migration 與平台分離，避免多次重啟或未來多副本時併發套用同一批 migration。

### 部署環境變數

複製以下內容為 `.env.deploy`（該檔不進版本控制）後填寫。未填寫的變數在 compose 中會成為空字串，等同未配置——SSO 未配置時登入 fail-closed，通知未配置時站內通知照常但不外送。

```bash
# 資料庫。POSTGRES_PASSWORD 沒有預設值，未設定時 compose 拒絕啟動。
POSTGRES_PASSWORD="請改成強密碼"
POSTGRES_DB="agent_skill_platform"
POSTGRES_USER="postgres"
# 主機名為 compose 服務名 postgres，不是 127.0.0.1。
DATABASE_URL="postgresql://postgres:請改成強密碼@postgres:5432/agent_skill_platform"

# 對外綁定。預設只綁 127.0.0.1，需由反向代理轉發並處理 TLS。
BIND_HOST="127.0.0.1"
BIND_PORT="3000"
LOG_LEVEL="info"

# 平台位址：腳本內注入的回報位址，以及通知訊息的連結前綴。
TELEMETRY_ENDPOINT="https://platform.example.com"
PLATFORM_BASE_URL="https://platform.example.com"

# 首位平台管理員，須與 IdP 回傳的 uid 完全一致。
BOOTSTRAP_ADMIN_UID=""

# SSO：六個全有或全無。正式環境不接受本機位址。
OIDC_AUTHORIZE_URL=""
OIDC_TOKEN_URL=""
OIDC_USERINFO_URL=""
OIDC_CLIENT_ID=""
OIDC_CLIENT_SECRET=""
OIDC_REDIRECT_URI=""
OIDC_SCOPE=""
OIDC_CLAIM_UID=""
OIDC_CLAIM_DISPLAY_NAME=""
OIDC_CLAIM_TEAMS=""

# 通知渠道，選填，必須是 https。
NOTIFY_SLACK_WEBHOOK_URL=""
NOTIFY_TEAMS_WEBHOOK_URL=""
NOTIFY_LARK_WEBHOOK_URL=""
```

平台本身不處理 TLS。要對外開放時請在前面架設反向代理，不要直接把 `BIND_HOST` 改成 `0.0.0.0` 而不加 TLS。

### 發布與回滾

單機不做灰度，`npm run deploy:up` 會重建並替換容器，過程中有短暫停機。MVP 階段此成本可接受。

回滾兩種方式：切回前一個 image tag，或 `git revert` 後重新 `deploy:up`。資料庫 migration **不會自動回滾**——若該次發布含 schema 變更，回滾前須確認舊版程式碼能在新 schema 上運作，否則需要另寫向下 migration。

### 健康輪詢

平台啟動時，若已配置任一通知渠道，會啟動週期性健康檢查（預設 60 秒，`HEALTH_CHECK_INTERVAL_MS` 可調）。連續三次失敗才告警，避免單次抖動觸發；狀態恢復時再送一則。

**只在狀態轉換時告警**，持續異常不重複發送——否則每個週期都會產生訊息，很快會被當成雜訊忽略。未配置通知渠道時不啟動輪詢，因為告警無處可送。

這是 MVP 的可觀測性方案，不引入 Prometheus、Grafana 或外部 APM。

## 容器化

`Dockerfile` 採 builder 與 runtime 兩階段：builder 安裝完整依賴、執行 `npm run build`，再以 `npm prune --omit=dev` 移除開發依賴；runtime 只複製 `node_modules`、`dist`、`package.json` 與 migration 所需的 `drizzle`、`scripts`。

容器以非 root 的 `app` 使用者執行，預設 `HOST=0.0.0.0`、`PORT=3000`。內建 `HEALTHCHECK` 直接請求 `/health`，資料庫不可用時該端點回 503，容器隨之標記為 unhealthy。

```bash
docker build -t agent-skill-platform:local .
docker run --rm -p 3000:3000 -e DATABASE_URL=<連線字串> agent-skill-platform:local
```

映像推送至 registry 需要憑證，屬待提供的外部依賴，見 `docs/待決策與延後事項.md`。

## 持續整合

`.github/workflows/ci.yml` 在 `main` 的 push 與 pull request 觸發，同一分支只保留最新一次執行。

`verify` job 啟動 `postgres:17-alpine` service 並對外映射 55432，與 `compose.yaml` 及測試預設連線字串一致，因此測試不需要另一組設定。步驟依序為型別檢查、建置、套用 migration、重跑 migration 驗證冪等、資料庫健康檢查、零外鍵查詢、測試。

零外鍵步驟以 `pg_constraint` 查詢作為硬性閘門：`public` schema 出現任何外鍵約束即中斷 CI，對應專案的反範式規則。

`container` job 在 `verify` 通過後建置容器映像，只驗證可建置，不推送。

## 健康與監控

- `GET /health` 確認服務與資料庫基本健康。
- 觀察 `runner_timeout`、`runner_error`、`telemetry_missing`、`cleanup_failed` 與遙測 409 的比例。
- 額外遙測欄位只記欄位名；日誌不得記完整 payload、queue、Token 或環境變數。

## 故障排除

- PostgreSQL 連不上：執行 `docker compose ps`、`npm run db:check`，再確認 55432 port 與 `DATABASE_URL`。
- Linux Runner 失敗：確認 Docker image 存在、Docker Desktop WSL integration 可用、具名測試容器沒有殘留。
- Windows Runner unavailable：確認 `pwsh -NoProfile -Command '$PSVersionTable.PSVersion'` 可執行。第一期 Runner 名為 `powershell-wsl`，不是原生 Windows VM。
- 遙測排隊：確認公開 endpoint 可達；`408`／`425`／`429`、網路與 5xx 會保留，其他永久 4xx 進 dead-letter。
- UUID 異常：Linux／WSL 檢查 `~/.agent-platform/uuid`；Windows 檢查 `%APPDATA%\agent-platform\uuid`。刪除會建立新身份，操作前先確認資料影響。

環境重置以 Runner 專用臨時目錄與 Docker 容器銷毀為邊界；禁止清理使用者整個 HOME、APPDATA 或 Docker 全域資源。
