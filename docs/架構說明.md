# 架構說明

## 為什麼先做模組化單體

身份、目錄、腳本生成、審核、遙測、分析、體驗與審計共享同一套版本狀態與事務邊界。首期拆成服務會把一致性問題放大，卻沒有獨立擴縮需求；Fastify plugin 提供足夠清楚的模組封裝，未來可按事件與負載邊界拆出服務。

## 請求與資料流

```text
HTTP request
  → Fastify schema validation
  → domain module plugin
  → Drizzle / PostgreSQL transaction
  → business row + domain_events outbox row
  → structured response or normalized error
```

健康檢查只回報服務與 PostgreSQL 是否可用，不洩露連線字串或底層錯誤。未知錯誤只寫入結構化服務日誌，對外固定為 `INTERNAL_ERROR`。

公開遙測是高頻不可變事實流，不為每筆事件再複製 Audit／Outbox；治理決策、身份與人工操作仍依上圖同交易寫入。這個分流避免遙測造成三倍寫放大，第二期若需要串流消費再加入 telemetry 專用 CDC 或批次 Outbox。

## 資料庫決策

- 內部主鍵使用 `bigint GENERATED ALWAYS AS IDENTITY`，避免 `serial` 與隨機 UUID 的索引問題。
- 所有時間使用 `timestamptz`。
- PostgreSQL 實體名稱固定為小寫 `snake_case`，TypeScript 使用 camelCase 映射。
- 採反範式資料自治：關聯欄位只保存穩定業務 ID，不建立外鍵、級聯刪除或 Drizzle `.references()`。
- 跨聚合完整性由應用層校驗、冪等鍵、Outbox、補償與對帳維護；常見查詢仍使用「等值欄位在前、時間範圍在後」的普通或複合索引。
- 允許保存 `package_id`、`owner_team`、`package_type`、`category` 等必要快照，換取批量操作、分片與服務切分能力。
- `domain_events` 是 transactional outbox：業務寫入和事件寫入應在同一交易，發布者按 `status, occurred_at` 拉取。
- connection pool 上限預設 10、閒置 30 秒、連線逾時 5 秒，避免每個請求建立新連線。

## 遙測事實與冪等語義

`installations` 是遙測唯一不可變事實表，不新增重複的 telemetry event 表。新資料直接保存 `package_id`、`version`、使用者參考、OS、Client、狀態、錯誤碼、事件時間、接收時間與 payload fingerprint；`legacy_package_version_id` 只保留舊資料追溯，不參與新查詢路徑。

`POST /api/telemetry/report` 不依賴 session。Service 先丟棄十一欄以外的資料並只記錄欄位名，再做 UUID、安全 UID、RFC 3339、時間順序、狀態與錯誤碼驗證。Repository 先以 `package_id + version` 做應用層存在性校驗，再使用 `INSERT ... ON CONFLICT DO NOTHING RETURNING`：首筆成功、相同 fingerprint 回 duplicate、不同 fingerprint 回 `IDEMPOTENCY_KEY_CONFLICT`，永不覆寫首筆事實。

晚到事件以 `started_at → ended_at → created_at → id` 排序，不用到達順序推斷安裝狀態。Catalog adoption 按 `package_id` 聚合；撤下通知按 `package_id + version` 尋找成功或已下載的 UID，所有路徑都不依賴外鍵。

## 發布治理與生命週期

治理模組是版本 lifecycle 的唯一寫入入口，狀態依序為 `draft → validating → review_required → published`；已發布版本可轉為 `deprecated`、`delisted` 或終態 `emergency_disabled`。驗證提交、retry claim 與完成都使用 expected-state／active-token CAS，claim 逾時後才可 reclaim；作者與 owner team 成員不得審核自己的版本。

審核工作台使用提交時保存的 package/version 邏輯快照，展示 install／uninstall 命令全文、殘留聲明、人工清理步驟、digest、OS／Client 宣告矩陣及真實 Runner 證據。approve／reject、revise、delist 與通知都在同一交易寫入 Audit 與 Outbox。delist 後下載立即失效，成功安裝記錄按 UID 去重通知；匿名 UUID 不產生通知。

首期 Runner 能力是 Linux Docker 與 Windows `powershell-wsl`；macOS 明確回報 `not_supported`，不得把不支援或失敗證據轉成 `passed`。Runner 證據用於功能驗證，不宣稱能抵抗同權限惡意命令竄改本機 capture；獨立權限 capture、隔離 VM 與簽章／attestation 保留給第二期。原生 Windows／macOS VM 與外部通知 dispatcher 同樣保留給第二期。

## 安裝腳本擴展契約

Taskmaster 已鎖定首期矩陣：Linux／Windows × Claude Code／Codex。平台生成不可變頭部與尾部；發布者或維護者只編輯中部命令。新增 OS 或 Client runtime 必須透過 adapter 擴展，不得改變 UID/UUID、冪等鍵與遙測協議。

這裡描述的是平台產生給終端使用者的三段式腳本，不是 Agent 技能安裝政策：頭部負責 init 並取得 login UID，未識別身份使用 UUID；中部由 UI 保存發布者／維護者的 install／uninstall 命令；尾部上報 success／failed／reason，遙測失敗不得覆寫原始退出碼。

`identity/installation-user-reference.ts` 是腳本生成器的身份入口：已登入身份映射為 `{ type: 'uid', value }`，訪客映射為 `{ type: 'uuid', value }`。判別式聯合型別讓匿名 UUID 無法被誤填到 UID；腳本生成器不得直接解析 Cookie。

腳本生成流程：

```text
已發佈 PackageVersion
  → 服務端驗證 visibility、OS、Client
  → 身份轉 uid／持久 UUID
  → 平台頭部 + 維護者命令 + 平台尾部
  → Linux Bash 或 Windows PowerShell
  → SHA-256 digest + 執行前預覽
```

- Linux 的維護者命令在子程序執行；父程序保留唯讀平台變數與 `EXIT` trap，中部 `exit` 不會跳過遙測。
- Linux 與 Windows 每次真實執行產生新 UUID；pending 項重試保持原 key，不在腳本生成或下載時固定 key。
- Windows 使用 `try/catch/finally`；遙測失敗寫入使用者目錄的 `pending_reports.jsonl`，不改寫原安裝結果。
- 兩個平台每次執行先依 FIFO 補交：2xx 刪除、非重試型 4xx 移入白名單 dead-letter，`408`／`425`／`429`、網路或 5xx 原子保留當前與後續行；Linux 使用含程序 owner 回收的具名目錄鎖與 `mv`，PowerShell 使用獨占 `FileStream` 與 `Move-Item`。
- 安裝與解除安裝共用不可變頭尾，但分別使用目錄中保存的 `install_command`／`uninstall_command`；解除成功回報 `uninstalled`。
- 中部拒絕平台保留變數、trap、endpoint、`exec` 與同類控制面改寫；遙測端點只從服務端配置注入。
- 有殘留副作用時，目錄版本必須同時保存殘留說明和人工清理步驟。

匿名身份 UUID 與事件冪等 key 是兩個不同概念。前者按使用者持久化：Linux／WSL 為 `~/.agent-platform/uuid`，Windows 為 `%APPDATA%\agent-platform\uuid`；刪除後重新生成。後者每次 install／uninstall 真實執行都生成新值，pending 重試才沿用。

`ValidationRunnerRegistry` 保存可注入的 OS adapter map 與 Client adapter set。第一期預設註冊 Docker Linux、`powershell-wsl`、Codex 與 Claude Code；新增 runtime 只增加 adapter，不修改共同的 install／telemetry／uninstall／cleanup 證據檢查。所有生成結果明示 `telemetryAssurance: best-effort`，供 Task #8 分析頁直接顯示。

WSL 終端選用 Linux Bash adapter，沿用 Linux 檔案與 queue 契約；Windows 終端選用 PowerShell adapter。`powershell-wsl` 只是目前審核 Runner 在 WSL 內呼叫 PowerShell 7 的能力名稱，不代表把 Windows 安裝流程改成 WSL Bash。兩邊的使用者資料與匿名 UUID 永遠獨立。

## 第一期身份與權限

```text
IdentityProvider
  → identity 快照（team_ids JSONB）
  → opaque session（只保存 SHA-256 摘要）
  → ResolvedIdentity（authenticated / anonymous）
  → AuthorizationService（hasRole / canReview）
  → reviewer_assignments + domain_events 同交易
```

- `DevelopmentIdentityProvider` 只在 development／test 使用固定 fixture；production／staging 預設 `DisabledIdentityProvider`，即使誤注入開發 provider 也拒絕啟動。
- `IdentityProvider` 保留 `development | oidc | disabled` 邊界。第二期新增真實 OIDC adapter 時，不改寫 session、授權服務或 HTTP 契約。
- session Cookie 使用 `HttpOnly`、`SameSite=Lax`、`Path=/`，production 增加 `Secure`；資料庫只保存安全亂數 Token 的 SHA-256 摘要。
- 匿名訪客取得可持久化 UUID Cookie；`GET /api/auth/me` 永遠明確回傳 `kind`。
- 角色可疊加並帶 `global`、`team`、`package_type`、`category` 或 `package` 作用域。
- `canReview` 先套用作者／同團隊迴避，再判斷管理員或審核人作用域。
- 管理 API 只有平臺管理員可用，新增／撤銷審核人會同步寫入 transactional outbox。

身份 API：

- `GET /api/auth/login`
- `GET /api/auth/callback`
- `GET /api/auth/me`
- `POST /api/auth/logout`
- `POST /api/admin/reviewers`
- `DELETE /api/admin/reviewers/:id`

## Migration 演進

Migration runner 依檔名排序並以 `_schema_migrations` 記錄版本。乾淨資料庫依序套用 `0000`～`0009`；舊資料庫若已有 `packages` 表但沒有版本記錄，先登記基線再套用後續版本。每個 migration 使用獨立交易，可安全重跑。

`0001_identity_access.sql` 同時移除舊基線可能存在的三個外鍵。2026-08-25 的容器實測中，`public` schema 的 `pg_constraint.contype = 'f'` 數量為 0。

`0009_telemetry.sql` 將舊 `package_version_id` 改名為 nullable legacy 欄位，回填邏輯 package/version 與固定 fingerprint；找不到版本列的孤兒資料使用可追溯 placeholder。原始 SQL 連續執行兩次不改變結果。

## Append-only 審計

`domain_events` 與 `audit_logs` 必須分開：前者是會更新 `status/attempts` 的 transactional outbox，後者是永遠只新增的操作證據。把兩者合併會讓 outbox 發布狀態和不可變要求互相衝突。

```text
管理操作 transaction
  ├── reviewer_assignments 業務資料
  ├── domain_events 可發布事件
  └── audit_logs 不可變操作證據
          ↓
GET /api/audit/logs
  → platform_admin
  → 事件／操作者／目標／時間過濾
  → occurred_at + id 游標分頁
```

- `audit_logs` 保存 `event_type`、`actor_uid`、`target_type/id`、`action`、JSONB details、可選 IP／User-Agent 與 `occurred_at`，所有關聯都是邏輯 ID。
- PostgreSQL `BEFORE UPDATE OR DELETE` trigger 以 SQLSTATE `55000` 拒絕竄改；沒有提供更新或刪除 repository 方法。
- reviewer 指派與撤銷在同一交易同步寫業務資料、Outbox 與 Audit。強制讓 Outbox INSERT 失敗的整合測試證明三者全部回滾。
- 查詢依 `occurred_at DESC, id DESC` 穩定排序，複合索引覆蓋事件、操作者與目標過濾；limit 上限為 100。
- 沒有採用裝飾器，因為裝飾器在交易提交後另寫日誌會破壞一致性。第一期使用顯式 transaction writer，讓失敗語義直接可測。

## 體驗模組與版本差異（Task 11）

`experience` 模組承載維護者支援入口與結構化使用反饋兩項第一期能力，兩張新表 `package_support_channels` 與 `package_feedback` 依既有規則不建任何外鍵。支援入口採整組覆寫，先刪後插在同一交易完成並寫 audit 與 outbox，維持「送出的清單即為完整結果」語義。

反饋開放匿名 UUID 提交，因為安裝腳本的使用者不一定登入，要求登入會讓最需要協助的失敗案例回報不上來；但明細含自由文字，讀取限維護者。反饋提交不寫 `audit_logs`：該表的語義是具名操作者的不可抵賴紀錄，而提交者可能是匿名 UUID。維護者變更處理狀態有具名操作者，照常寫 audit。

版本差異計算放在 catalog 而非新模組，因為它的權威來源是 Task 13 的 target／revision。比較範圍固定為雙方 active target 的 current revision：軟刪除的 target 與歷史 revision 都不參與，使用者升級後拿到的是目前指標而非任何歷史快照。差異結果只回 `contentDigest`、`scriptVersion` 與變更旗標，不含命令全文，與「詳情頁不得顯示中部安裝命令」同一條規則。

`requiresReapproval` 的語義是「使用者升級前需重新確認」，不是治理層重新送審；命令、選項或殘留副作用改變時原本的安裝決策依據即不再成立。差異端點只比較呼叫者本來就看得到的版本，不作為探測未發布內容的旁路。

新版本發布通知沿用既有 `user_notifications` 收件匣，只擴充 `version_published` 型別。收件人判定與撤下通知相反：撤下通知同一版本的安裝者，發布通知同套件**其他**版本的安裝者——本次發布的版本尚無安裝紀錄，已在新版者不需提醒。作者與匿名 UUID 排除，通知與 audit、outbox 同交易寫入。

semantic version comparator 位於 `src/shared/version/semantic-version.ts`。它原本在 analytics，但 catalog 的差異計算需要它而 analytics 已依賴 catalog 型別，catalog 反向 import 會形成模組循環；catalog 對外的執行期依賴只有 shared，此邊界必須維持。

## 歸檔線框的沿用範圍

後續 UI 沿用歸檔 HTML 的資訊架構優點：固定側欄、密集表格、雙欄詳情、可見的安全狀態、清楚的 Loading／Empty／Error／Partial／Success。視覺成品不直接複製；`frontend-design` 技能要求根據技能治理場景建立專屬 token、字體與一個可辯護的識別元素。

## 分析查詢與歸檔畫面 3 的資料映射

分析模組只讀取反範式 `installations`、`packages` 與 `package_versions` 的邏輯 ID；不為分析增加外鍵。匿名請求在 repository 讀取前拒絕；已登入請求先以輕量 metadata 查詢完成 404 與作者／owner team maintainer／platform admin 授權，通過後才執行期間 telemetry 查詢。套件期間查詢走 `(package_id, started_at)` 普通索引，因為條件固定為套件等值加 `started_at` 閉區間；使用者「我的安裝」走 `(user_ref_type, user_ref, created_at)` 索引。這讓讀熱點可獨立擴展，也不把跨聚合完整性交給資料庫。

`started_at` 是分析唯一的期間軸：`start <= started_at <= end`，單次查詢最長 366 天。`created_at`／`receivedAt` 是接收時間，保留給晚到遙測診斷，不得替換期間篩選。狀態折疊固定按 `startedAt → endedAt → receivedAt → id` 排序；成功寫入目前安裝，解除安裝刪除目前安裝，因而不受 Memory／PostgreSQL 輸入順序影響。版本分布表示選擇期間資料折疊後的活躍版本，而非歷史事件總和。

員工首次可運行時間先依 `packageId + userRefType + userRef + version` 分組，每組下載只排序一次；每筆成功事件以 binary search 尋找最近前序下載。這維持近似口徑，同時避免每筆成功事件重新掃描與排序整段期間資料。

歸檔線框「畫面 3：作者看見採用與失敗原因」只保留資訊層級，資料區段映射如下：

| 歸檔區段 | 現行 API 欄位 | 呈現限制 |
| --- | --- | --- |
| 推廣成效／嘗試安裝 | `funnel.downloads`、`funnel.installs`、`funnel.uninstalls` 與兩個比率 | 下載事件可能缺失，顯示 `dataGaps`。 |
| 一次成功率 | `successRates.uid`、`successRates.uuid`、各自 Wilson 95% 區間 | UID 與 UUID 不合併；零分母顯示無資料。 |
| 首次可運行時間 | `timeToRunnable.platform` 與 `employee` 的 median／P90／P95 | 員工口徑為近似值，未配對下載不可補樣本。 |
| 失敗原因 | `failureDistribution.byVersion`／`byOs`／`byErrorCode` 與 `heatmap` | 一維聚合可直接呈現；heatmap 不能被解讀成單一根因或使用未保存的命令輸出。`failureCells` 是 heatmap 相容欄位。 |
| 提醒升級 | `upgradeCandidates` | 只列可通知 UID，並依 OS／client runtime 相容推薦；前端不可自行把 UUID 加入。 |
| 我的安裝側欄 | `GET /api/me/installations` | 僅登入 UID 的目前活躍安裝，不是作者報表。 |

分析回應一律帶 `telemetryAssurance: best-effort` 與「數據僅供參考」。原因是腳本可在遙測傳輸失敗時保留原安裝退出碼並延後補交，故資料不能被宣稱為完整或審計級事實。

## 技能目錄

```text
GET /api/packages
  → public／internal 套件可見性
  → 只組合 published 版本
  → keyword／category／client／os
  → 穩定排序 + cursor

GET /api/packages/:packageId
  → published 版本
  └── 作者或指定審核人額外看見 review_required

GET /api/packages/:packageId/versions/:version/download
  └── 只允許 published，待審版本固定 404
```

- `packages.package_id` 是公開穩定 ID；`package_versions.package_id` 直接保存它，不依賴內部 bigint 主鍵。
- Client 支援保存名稱、版本、適配來源與維護者；第一期驗證 Codex、Claude Code、Linux、Windows，JSONB 結構允許日後新增 runtime 與 OS adapter。
- 安裝命令由發布者或維護者經 UI 命令框提交並原樣保存，平台不硬編碼命令中部。
- 套件與版本建立、修改、發佈或下架會在同一 transaction 寫入 `audit_logs` 與 `domain_events`。
- 詳情採用摘要按穩定 `package_id` 聚合 `installations`；版本通知按 `package_id + version` 查詢，不依賴內部 ID 或外鍵。
