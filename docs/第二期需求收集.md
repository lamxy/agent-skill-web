## P2-2 安裝包與內部資源夾

### 場景

發布者可以自定義技能或工具。這類套件的一鍵安裝腳本可能需要拷貝技能檔案或引用工具本體，而不只是執行命令從外部來源下載。

因此下載一鍵安裝腳本時，可能需要生成的不是單一腳本檔，而是一個安裝包。安裝包內含一個內部資源夾，打包發布者上傳的技能檔案與工具，讓中部安裝命令可以直接引用這些資源，不依賴外部網路或額外的來源位址。

### 與第一期的關係

第一期不做。第一期的交付形態固定為單一腳本檔，發布者的中部命令自行從 `sourceUri` 取得內容。

此需求會改變下載產物的形態，連帶影響腳本生成、下載端點、檔名規則與遙測。因此不得在第一期以部分實作的方式引入。

### 第二期需要處理的問題

發布者上傳檔案的入口、大小限制與儲存位置。安裝包的格式與解壓方式在四個目標系統上的一致性。內部資源夾在中部命令中的引用路徑約定。安裝包的完整性驗證，例如摘要或簽章。上傳內容的安全審查，這與現有的殘留聲明審核屬同一個審核流程但檢查項不同。已上傳資源的版本管理與清理。

## P2-3 影響資源與所需權限的結構化欄位

### 背景

安裝頁需要以白話說明這份腳本會做什麼。其中「在本機保存 UUID」與「執行結束時回報結果」屬平台固定行為，前端可直接呈現；「解除安裝後保留設定檔」來自 `preview.residualDescription`，後端已有。

但「會寫入哪些路徑、執行什麼命令」與「需不需要 sudo、讀不讀憑證、連不連外部網路」屬套件專屬資訊，後端目前沒有對應欄位。

### 為什麼不用靜態分析推導

從 `installCommand` 推導寫入路徑與權限需求在技術上不可靠。bash 是圖靈完備的，變數展開、`eval` 與間接執行都能繞過分析。推導錯誤比不顯示更糟：介面聲稱「不連外部網路」而實際連了，會直接侵蝕使用者對平台的信任。

### 第一期的做法

安裝頁的「影響資源與所需權限」區塊顯示「發布者未提供此資訊」的空狀態，不編造內容。此空狀態本身有作用：推動發布者補齊，也讓審核者看得出誰沒填。

### 第二期的做法

在版本記錄新增 `impactSummary` 與 `permissionScope` 兩個結構化欄位，由發布者在上架頁填寫。此變更與 `docs/待決策與延後事項.md` 的 D-3 所列的「使用說明必填」屬同一批 schema 調整，可一併處理。

需注意此類欄位與 `hasResidualEffects` 同屬發布者自行聲明，存在低報風險，需納入審核檢查項。

## P2-4 腳本簽名密鑰管理與金鑰輪換

### 背景

原為 Task 10.7「腳本簽名密鑰管理」，2026-08-29 依 `AGENTS.md` 第 33 條移入第二期需求池。該條明列密鑰輪替延後到第二期，第一期秘密由環境變數提供。

### 第一期的做法

不簽名。平台生成的一鍵安裝腳本以 HTTPS 傳輸，完整性依賴傳輸層而非腳本自身簽章。腳本內容的可信度來自上架審核流程：審核人檢視中部安裝命令並決議通過後才產生腳本。

### 第二期需要處理的內容

需要 HSM 或 Vault 存取權。簽名演算法採 Ed25519 或 RSA-PSS。除簽名產生與驗證外，須一併處理金鑰輪換：輪換期間新舊金鑰並存的驗證窗口、既有已下載腳本的驗證是否仍需成立、公鑰的發布與更新途徑。

### 與其他項目的關係

驗證端在員工的本機執行，因此公鑰分發方式須與一鍵安裝腳本的取得途徑一併設計。若第二期同時實作 P2-2 安裝包，簽名對象會從單一腳本檔變成安裝包，兩者應一起設計而非分別實作。
