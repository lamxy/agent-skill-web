# 公網部署指南

把平台部署到公網雲主機，配獨立域名與 HTTPS，供同事以各自帳號實際操作。

適用場景：分享給同事瀏覽與試用、演講時隨時訪問。
單機內網部署見 `運維指南.md`；本機測試見 `README.md` 的 `npm run dev:all` 與 `npm run stack:up`。

---

## 這個方案的取捨

**不使用模擬 IdP。** 開發期的三個帳號（mock-admin／mock-reviewer／mock-user）點一下就能登入且沒有密碼，放上公網等於平台對所有人敞開。程式碼有兩道防線會擋住這種用法，且不應拆除：

- `src/mock-idp.ts` 與 `scripts/start-mock-idp.ts`：非 development/test 一律拒絕啟動
- `src/shared/config/config.ts`：production／staging 拒絕指向本機的 `OIDC_*`

**改用真實 IdP，角色仍由平台自己管。** 角色存在資料庫的 `role_assignments`，以 uid 為鍵，與 IdP 無關。因此換成 GitHub OAuth 後，同事各自用真帳號登入，你再以管理員身分指派角色——不需要修改任何程式碼。

本指南以 GitHub OAuth 為例：同事多半已有帳號、申請只需兩分鐘、零成本。若貴公司有內部 IdP，替換六個 `OIDC_*` 即可，其餘步驟不變。

---

## 兩條部署路線

| 路線 | 適用 | 對應檔案 |
|---|---|---|
| **A. Coolify**（推薦，若已裝） | 主機上已有 Coolify。反向代理、憑證、自動部署都由它處理 | `compose.coolify.yaml` |
| **B. 自管 Caddy** | 沒有 Coolify，或想要不依賴任何平台的獨立路徑 | `compose.public.yaml` + `Caddyfile` |

兩條路線的應用行為完全相同，差別只在誰負責 HTTPS 與容器編排。

**共通前置**（兩條路線都需要）：步驟二的 GitHub OAuth App、步驟三的 uid 查詢。
先做完這兩步，再依路線跳到步驟四（路線 B）或最後的 Coolify 章節（路線 A）。

---

## 前置準備

| 項目 | 說明 |
|---|---|
| 雲主機 | 2 vCPU／2 GB 記憶體足夠。建議 DigitalOcean、Hetzner、Vultr、AWS Lightsail 等非中國大陸節點，避免域名備案要求 |
| 域名 | 路線 B 需能自行設定 A 記錄；路線 A 若 Coolify 已配泛解析則不需另備域名 |
| 開放埠 | 22（SSH）、80、443。80 必須開放，Let's Encrypt 憑證驗證會用到 |

主機上需安裝 Docker 與 Docker Compose plugin。使用 Coolify 時它已一併安裝。

---

## 步驟一：DNS 指向主機

> 路線 A（Coolify）若已配置泛解析（`*.你的域名` → Coolify 主機），可跳過本步驟，
> Coolify 會自動配發 `platform.你的-coolify-域名` 這類子域。

在域名商後台新增 A 記錄：

```
類型  名稱       值
A     platform   你的主機公網 IP
```

驗證生效（回傳應為主機 IP）：

```bash
dig +short platform.你的域名
```

DNS 未生效就啟動會導致憑證申請失敗。Caddy 會自動重試，但先確認可省去排查。

---

## 步驟二：申請 GitHub OAuth App

GitHub → Settings → Developer settings → OAuth Apps → New OAuth App

```
Application name:            隨意，例如 Agent Skill Platform
Homepage URL:                https://platform.你的域名
Authorization callback URL:  https://platform.你的域名/api/auth/callback
```

Callback URL 必須與平台的對外網址完全一致，含 `https://` 與路徑，多一個斜線都會失敗。
路線 B 對應 `PUBLIC_DOMAIN`，路線 A 對應 Coolify 配發或指定的網址。
若走路線 A 且網址要等 Coolify 建好資源才確定，可先隨意填，之後回來改。

建立後記下 Client ID，並產生一組 Client Secret（只顯示一次）。

---

## 步驟三：查出 uid

平台以 GitHub 的**數字 ID** 作為 uid，而非使用者名稱——使用者名稱可被更改，數字 ID 不會。

```bash
curl -s https://api.github.com/users/你的帳號 | grep '"id"'
```

自己與每位需要登入的同事都查一次，記下來。

---

## 步驟四：部署（路線 B — 自管 Caddy）

> 使用 Coolify 請跳過步驟四到六，直接看文末的「路線 A：Coolify 部署」。

```bash
git clone <你的倉庫位址> platform && cd platform
cp .env.deploy.example .env.deploy
```

編輯 `.env.deploy`，至少填妥：

| 變數 | 說明 |
|---|---|
| `PUBLIC_DOMAIN` | `platform.你的域名`，不含 `https://` |
| `ACME_EMAIL` | 憑證到期通知信箱 |
| `POSTGRES_PASSWORD` | 隨機值，`openssl rand -base64 24` |
| `DATABASE_URL` | 密碼須與上一項一致，主機名是 `postgres` |
| `BOOTSTRAP_ADMIN_UID` | 你自己的 GitHub 數字 ID |
| `LOGIN_ALLOWED_UIDS` | 允許登入的 uid，逗號分隔，**必須包含你自己** |
| `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET` | 步驟二取得 |

啟動：

```bash
npm run public:up
npm run public:logs
```

首次啟動會建置映像並申請憑證，約需數分鐘。日誌出現 `certificate obtained successfully` 即完成。

---

## 步驟五：驗證

```bash
curl -s https://platform.你的域名/health
# 預期：{"status":"ok","database":"up"}
```

瀏覽器開啟 `https://platform.你的域名`，以 GitHub 登入。你會自動獲得 `platform_admin`（僅首次，且僅限 `BOOTSTRAP_ADMIN_UID` 對應的帳號）。

---

## 步驟六：分配角色

1. 請同事各自開啟網址並用 GitHub 登入一次——平台會建立他們的 identity
2. 你在管理介面把 `reviewer` 指派給需要審核權限的人
3. 其餘人維持一般使用者

`platform_admin` 無法經由介面授予，只能由 `BOOTSTRAP_ADMIN_UID` 產生。這是刻意設計，避免管理員身分被誤操作擴散。

---

## 白名單行為

`LOGIN_ALLOWED_UIDS` 用於擋下非預期對象。GitHub OAuth 預設任何 GitHub 用戶都能通過驗證，沒有白名單時他們雖然拿不到權限，仍會在 `identities` 留下記錄。

- 留空 → 不限制
- 有值 → 僅名單內的 uid 可登入，其餘回 403 且**不建立任何記錄**
- 未包含 `BOOTSTRAP_ADMIN_UID` → 啟動時直接拋錯（否則會造成無人能登入，且症狀難以聯想到原因）

新增同事時把 uid 加進去，然後重新套用設定：
路線 B 執行 `npm run public:up`，路線 A 在 Coolify 改完環境變數後按 Redeploy。

---

## 日常操作（路線 B）

```bash
npm run public:up      # 啟動或套用設定變更
npm run public:logs    # 追蹤日誌
npm run public:down    # 停止，保留資料
```

更新版本：

```bash
git pull && npm run public:up
```

`migrate` 是獨立的一次性服務，會在平台啟動前完成，不需要手動執行。

備份資料庫：

```bash
docker compose -f compose.public.yaml exec postgres \
  pg_dump -U postgres agent_skill_platform > backup-$(date +%F).sql
```

## 疑難排解

登入相關的三項（403、無管理員權限、OIDC 配置不完整）兩條路線通用；
憑證與 compose 兩項僅路線 B 適用，Coolify 見 A-6。

**憑證申請失敗**（路線 B）
確認 DNS 已生效、80 埠對公網開放、`PUBLIC_DOMAIN` 未含 `https://`。Let's Encrypt 對同一域名有簽發頻率限制，反覆重試可能觸發暫時封鎖，此時等待約一小時。

**登入後跳轉失敗**
GitHub OAuth App 的 callback URL 與 `PUBLIC_DOMAIN` 不一致。兩者必須逐字相同。

**登入回 403**
該 uid 不在 `LOGIN_ALLOWED_UIDS` 內。注意應填數字 ID 而非使用者名稱。

**登入成功但沒有管理員權限**
`BOOTSTRAP_ADMIN_UID` 與實際 uid 不符。此情況不會報錯，需自行核對。查看日誌是否有「依 BOOTSTRAP_ADMIN_UID 授予首位平台管理員」。

**啟動即失敗，提示 OIDC 配置不完整**
六個 `OIDC_*` 必須全有或全無。路線 B 的 `OIDC_REDIRECT_URI` 由 compose 依
`PUBLIC_DOMAIN` 自動組出，不需在 `.env.deploy` 填寫；路線 A 則必須手動填。

---

## 安全須知

兩條路線共通：

- 資料庫與平台皆不對外開放 port，只有反向代理（路線 B 是 Caddy，路線 A 是 Coolify 的 Traefik）對公網可見
- 公網環境建議始終設定 `LOGIN_ALLOWED_UIDS`
- 密碼與 OAuth secret 不進版本控制：路線 B 存於 `.env.deploy`（已在 `.gitignore`），路線 A 存於 Coolify 的 Environment Variables
- 演講或分享結束後若不再需要，停止服務即可（路線 B `npm run public:down`，路線 A 按 Stop）；資料保留在 volume，下次啟動即恢復

# 路線 A：Coolify 部署

已在主機安裝 Coolify 時走這條。反向代理、憑證簽發與續期、Git push 自動部署都由 Coolify 內建的 Traefik 處理，不需要 Caddy，也不需要 `.env.deploy`。

先完成共通前置：步驟二（GitHub OAuth App）與步驟三（查 uid）。

## A-1：確認域名策略

Coolify 安裝時若配了泛解析，新增服務不必再碰 DNS：

```
*.你的域名  →  A  →  Coolify 主機 IP
```

驗證（回傳應為 Coolify 主機 IP）：

```bash
dig +short 隨便一個字串.你的域名
```

有泛解析 → 可用 `platform.你的域名`，或按 Coolify 的 Generate Domain 讓它給一個。
沒有泛解析 → 為 `platform.你的域名` 單獨加一條 A 記錄。

子域與獨立域名在功能與憑證上沒有差別，僅觀感不同。之後要換獨立域名，只需改
Coolify 的 Domains 欄、`OIDC_REDIRECT_URI` 與 OAuth App 的 callback，無遷移成本。

## A-2：建立資源

Coolify → Project → New Resource → **Private/Public Repository**

| 設定 | 值 |
|---|---|
| Build Pack | **Docker Compose** |
| Docker Compose Location | `/compose.coolify.yaml` |
| Branch | 含本功能的分支（合併前是 `feat/public-deploy`） |

分支選錯會拿不到登入白名單，登入將不受限制。

## A-3：填環境變數

在 Environment Variables 分頁填入。值的說明見 `.env.deploy.example`，
Coolify 不讀該檔，僅作為填寫時的對照。

必填：

```
POSTGRES_PASSWORD     openssl rand -base64 24 產生
DATABASE_URL          postgresql://postgres:<同上密碼>@postgres:5432/agent_skill_platform
BOOTSTRAP_ADMIN_UID   你的 GitHub 數字 ID
OIDC_AUTHORIZE_URL    https://github.com/login/oauth/authorize
OIDC_TOKEN_URL        https://github.com/login/oauth/access_token
OIDC_USERINFO_URL     https://api.github.com/user
OIDC_CLIENT_ID        OAuth App 的 Client ID
OIDC_CLIENT_SECRET    OAuth App 的 Client Secret
OIDC_REDIRECT_URI     https://<你的網址>/api/auth/callback
```

建議填：

```
LOGIN_ALLOWED_UIDS      你的ID,同事A的ID,同事B的ID
OIDC_SCOPE              read:user
OIDC_CLAIM_UID          id
OIDC_CLAIM_DISPLAY_NAME name
```

`DATABASE_URL` 的主機名是 compose 服務名 `postgres`，不是 `127.0.0.1`。

`SERVICE_FQDN_APP_3000` 由 Coolify 注入，不要手動填。`PLATFORM_BASE_URL` 也不必填，
compose 會從它自動帶入。

## A-4：部署與驗證

按 Deploy。首次會建置映像，數分鐘。部署順序由 compose 保證：
postgres 就緒 → migrate 完成 → app 啟動。

Coolify 依 app 的 healthcheck（打 `/health`）判定成功。驗證：

```bash
curl -s https://<你的網址>/health
# 預期：{"status":"ok","database":"up"}
```

瀏覽器開啟網址並以 GitHub 登入，你會自動獲得 `platform_admin`。
接著回步驟六分配角色，之後的白名單行為與安全須知兩節同樣適用。

## A-5：日常操作

| 操作 | 做法 |
|---|---|
| 更新版本 | push 到該分支，Coolify 自動重新部署（或按 Redeploy） |
| 改設定 | 改環境變數後按 Redeploy |
| 看日誌 | Coolify 的 Logs 分頁 |
| 進容器 | Coolify 的 Terminal 分頁 |
| 停止 | Coolify 的 Stop，資料保留在 volume |

migration 由 `migrate` 服務在 app 之前自動完成，不需手動執行。

備份資料庫（在 Coolify Terminal 對 postgres 容器執行）：

```bash
pg_dump -U postgres agent_skill_platform > /tmp/backup-$(date +%F).sql
```

## A-6：Coolify 專屬疑難排解

**部署卡在 unhealthy**
app 的 healthcheck 打 `/health`，資料庫不可用時回 503。先看 postgres 是否
healthy，再確認 `DATABASE_URL` 的主機名是 `postgres` 而非 `127.0.0.1`。

**登入跳轉回來 404 或失敗**
`OIDC_REDIRECT_URI` 與 GitHub OAuth App 的 callback URL 不一致。用了 Coolify
自動產生的子域時，記得回 GitHub 把 callback 改成同一個位址。

**建置時記憶體不足**
容器內跑 `npm ci` + tsc + vite。1 GB 主機可能 OOM，加 swap 或升規格。

**示範資料**
`compose.coolify.yaml` 不含 seed 服務：`src/seed.ts` 在 `NODE_ENV=production`
會拒絕寫入。同事看到的是空平台，需要內容請以真實操作建立。
