技能平台試駕手冊

三十分鐘走完平台的完整生命週期：發布 → 審核 → 上架 → 安裝 → 下架 → 通知。 重點在四種身份看到的畫面各自不同——同一個頁面，換個人登入就換一組入口。 本手冊的每個指令與端點都對應目前程式碼的實際行為。

啟動環境

開兩個終端。模擬 IdP 是開發期的企業登入替身，跑的是與正式環境相同的 OAuth2 協議。

  1. 重建演示環境

    清空資料庫、套用 migration、載入示範套件。此指令在 NODE_ENV 非 development 時會拒絕執行。

    $ npm run demo:reset

  2. 啟動模擬 IdP（獨立終端）

    監聽 127.0.0.1:4780，提供三個可選身份。保持它執行中。

    $ npm run dev:idp

  3. 啟動平台

    $ npm run dev
    → http://127.0.0.1:3000

    若尚未設定 SSO 環境變數，請先依 docs/運維指南.md 的 SSO 章節填入六個 OIDC_* 與 BOOTSTRAP_ADMIN_UID。

先設定 BOOTSTRAP_ADMIN_UID＝mock-admin。

授予角色本身需要管理員權限，所以平台需要一條產生「第一位管理員」的路徑。沒設這個值，登入會成功但沒有人能指派審核人，整條審核流程動不了。

四種身份，四種畫面

模擬 IdP 提供三個帳號。角色不是 IdP 給的，而是登入後由平台管理員授予——這是刻意的分離： 企業目錄決定「你是誰」，平台決定「你能做什麼」。

匿名訪客

未登入

不是錯誤狀態，是設計上的一等公民。

  • 瀏覽技能池、開啟套件詳情、查看支援管道
  • 行為被遙測記錄（以匿名 UUID，非個人身分）
  • 無法安裝、發布、審核

直接開 http://127.0.0.1:3000 就是這個視角。注意頂欄只有「技能池」一個入口， 右上角是登入按鈕。頁面內容完整呈現，不會被攔截牆擋住。

一般員工

mock-user

登入後的預設狀態——沒有任何角色，這是正常的。

  • 安裝技能、取得一鍵安裝腳本
  • 查看「我的安裝」與「通知」
  • 提交使用反饋
  • 看不到審核與管理入口

點右上角登入，在模擬 IdP 選「模擬使用者」。回到平台後頂欄多出「我的安裝」「通知」「發布技能」。 點頭像展開選單，可以看到自己的 uid、團隊與角色——角色欄會顯示「一般員工權限」。

平台管理員

mock-admin

唯一能授予他人角色的身份，由環境變數指定產生。

  • 指派與撤銷審核人，設定其可審範圍
  • 版本治理：撤下、緊急停用
  • 稽核日誌、支援與反饋後台
  • 可審核所有範圍的送審申請

登出後改選「模擬管理員」。頂欄出現「管理」入口。 身份選單的角色欄會顯示 平台管理員 · 全平台。

審核人

mock-reviewer

角色帶範圍——只能審自己被指派的「套件類型 × 分類」。

  • 審核工作台，通過或退回送審申請
  • 檢視完整安裝命令與殘留聲明
  • 不得審核自己團隊的套件（利益迴避，後端強制）
  • 無法指派其他審核人

這個角色需要管理員先指派，見下一節。

導覽隱藏入口不是安全機制。

前端依角色增減入口只是為了不讓人點進必然被拒的頁面。真正的授權判定全在後端按範圍執行——直接打 API 一樣會被擋。

完整流程試駕

依序操作，會走完一個版本從送審到撤下的完整生命週期，並在最後看到通知回到員工手上。

  1. 管理員指派審核人

    以 mock-admin 登入後，先讓 mock-reviewer 登入過一次以建立身份記錄，再回到管理員身份進入管理 → 審核者管理。

    指派時選擇套件類型與分類，例如 tool × 部署。範圍是必填的——審核權限從來不是全域的，除非你是管理員。

  2. 以員工身份瀏覽與安裝

    切到 mock-user。技能池會看到三個示範套件：

    套件類型擁有團隊狀態
    pm-skillskill產品效能已發布 0.8.3
    trace-lensskill可觀測性已發布 1.1.2
    deploy-runnertoolSRE待審核 2.0.0-rc.1

    開啟 pm-skill 詳情 → 安裝。安裝頁會顯示這份腳本會做什麼、是否有殘留，並提供一鍵安裝腳本下載。

  3. 觀察待審核的版本

    deploy-runner 的 2.0.0-rc.1 處於 review_required，一般員工看得到套件但拿不到這個版本的腳本——未通過審核的版本不提供下載。

    它也是唯一宣告了殘留影響的示範套件：會寫入 /etc/deploy-runner 與 systemd unit，並附有手動清理步驟。

  4. 以審核人身份決議

    切到 mock-reviewer，進入審核工作台。開啟 deploy-runner 的送審詳情，可以看到完整安裝命令、殘留聲明與腳本目標矩陣。

    通過或退回都需要填寫理由。退回時理由會回到維護者手上。

  5. 管理員撤下版本，觸發通知

    切回 mock-admin，進入管理 → 版本治理，對已發布的版本執行撤下或緊急停用，填寫原因代碼與說明。

    這一步會為所有安裝過該版本的員工建立站內通知。

  6. 回到員工視角收通知

    切到 mock-user，開啟通知。撤下與緊急停用會出現在「撤下與停用」分頁，新版本發布則在「新版本」分頁並可直接跳到版本差異頁。

    若已設定 NOTIFY_*_WEBHOOK_URL，同一則通知也會送到 Slack、Teams 或 Lark。未設定時站內通知照常，只是不外送。

值得順手一看的地方

這些細節體現了平台的幾個設計立場，容易在快速瀏覽時錯過。

稽核日誌

管理 → 稽核日誌。每一次審核決議、撤下、角色異動都留痕。bootstrap 授予的管理員會標示為 bootstrap 而非人名。

隱私聲明

頁尾入口。逐欄說明遙測上報哪些欄位、不收集什麼。內容與後端的白名單保持一致。

作者分析頁

套件詳情 → 分析。安裝成功率、版本分布。示範資料已含成功與失敗數，圖表不是空的。

版本差異頁

只顯示每個目標組合的變更旗標與摘要對照，不顯示命令全文——與詳情頁同一條規則。

健康告警

設定任一通知渠道後，平台每 60 秒檢查一次資料庫。連續三次失敗才告警，且只在狀態轉換時發送。

API 文件

/docs 提供 Swagger UI，可直接看到所有端點的請求與回應結構。

單機部署

上面走的是開發模式。要以容器完整跑起來（含前端與 migration）：

# 複製運維指南的範本為 .env.deploy 並填寫後
$ npm run deploy:up
$ npm run deploy:logs
$ npm run deploy:down # 保留資料 volume

三個服務依序啟動：postgres 就緒 → migrate 執行完畢 → app 啟動。migration 與平台分離，避免重啟時併發套用。

平台本身不處理 TLS。

預設只綁 127.0.0.1。要對外開放請在前面架反向代理，不要只是把 BIND_HOST 改成 0.0.0.0。

目前尚未驗證的部分

腳本執行只在 Linux／macOS 與 WSL 上實測過。Windows 原生與 macOS 原生的生成腳本可以下載，但平台端沒有實際執行過——文件與介面都不會聲稱它們已驗證。

SSO 目前連的是本機模擬 IdP；通知渠道需要真實 webhook 憑證才會實際送出。 兩者的程式碼路徑與正式環境相同，取得憑證後只需替換環境變數。
