# 全局開發記憶

## 2026-08-25：任務前技能治理

每個 Taskmaster 任務開始前先使用 `find-skills` 搜尋場景技能，完成來源、採用量、授權與檔案內容審核後，優先安裝到目前專案的 `.agents/skills/`。Agent 技能安裝命令固定使用 `DISABLE_TELEMETRY=1 npx -y skills add <owner/repo> --skill <name> -a codex -y --copy`，不使用全域 `-g`。所有採用與拒絕決策寫入 `docs/技能與工具備查.md`，以 `skills-lock.json` 保存來源及內容雜湊。

這項決策的目的不是增加流程，而是讓前端、後端、資料庫與安全工作使用可追溯的專業規則，同時避免未知技能取得 Agent 的完整權限。

### 備援 Agent 來源

`find-skills`、官方插件、現有專案技能與其他可信技能渠道都沒有合適候選時，再檢查 `github.com/msitarzewski/agency-agents`。該倉庫是 MIT 授權的專業 Agent 角色集合，不是可直接信任的 Skill registry。

只允許按任務讀取單一相關 Agent Markdown，完成授權、工具權限、外部命令、提示注入與內容範圍審查後，再專案級複製或改編。不得直接執行倉庫的桌面應用、安裝腳本、轉換腳本或整庫安裝。採用時要記錄原始 URL、commit SHA、內容雜湊、原因與使用方式。

## 2026-08-25：資料庫採反範式且禁用外鍵

本專案面向高併發、批量操作與未來服務切分。資料表保存可自治的業務 ID 與必要快照，資料庫不建立外鍵、級聯刪除或跨聚合約束。完整性改由應用服務、冪等鍵、交易 Outbox、補償與對帳流程維護。

Task #2 已從 `0000_initial.sql` 與 Drizzle schema 移除三個既有外鍵；`0001_identity_access.sql` 也會在舊資料庫以 `DROP CONSTRAINT IF EXISTS` 清理歷史約束。2026-08-25 的 PostgreSQL 17 容器查詢證明 `public` schema 外鍵數量為 0。後續 migration 必須維持這個不變量。

## 2026-08-25：第一期功能優先，OIDC 延後

第一期先完成身份解析、匿名 UUID、session、角色、審核者與 API 功能閉環。只做輸入驗證、伺服器端授權、安全 Cookie、秘密不落碼與錯誤收斂等基本安全處理。

真實 OIDC Provider、PKCE/JWKS/MFA、完整限流與集中安全加固排入第二期。第一期僅保留 `IdentityProvider` adapter 介面，使用開發期本地 Provider 完成功能與測試，不綁定 Azure AD、Auth0 或 Keycloak。

正式與 staging 環境預設使用 `DisabledIdentityProvider`。沒有正式 provider 時登入回 `503 AUTH_PROVIDER_UNAVAILABLE`；不得為了展示功能降級成開發登入。開發管理員 fixture 只在 `DevelopmentIdentityProvider` callback 後取得本地 `platform_admin` 角色。

## 2026-08-25：身份與安裝腳本共享判別式接口

身份解析結果固定為 `authenticated(uid)` 或 `anonymous(anonymousId)` 的 TypeScript 聯合型別。安裝腳本生成器只能透過 `toInstallationUserReference()` 取得 `{ type: 'uid' | 'uuid', value }`，不得直接讀 Cookie 或把匿名 UUID 寫入 UID。

工作階段採伺服器端 opaque Token：Cookie 保存原文，PostgreSQL 只保存 SHA-256 摘要；登出採撤銷時間，已撤銷或過期 session 回落為匿名身份。

## 2026-08-25：Task #4 審計技能搜尋結論

`find-skills` 沒有找到適配 Node.js／Fastify／Drizzle 且達可信門檻的 audit logging／transactional outbox 技能。Spring Boot 候選雖有約 2.4K 安裝但技術棧錯誤；Sentry outbox 是 Django silo 內部技能；其他候選採用量過低。

依備援規則檢查 Agency Agents 的 Backend Architect Markdown 後，因其是廣泛 persona，並包含正規化、外鍵與全面安全預設，與本專案規則衝突，所以不安裝、不複製。Task #4 沿用已審查的 Supabase PostgreSQL 技能之交易、索引與查詢部分，並以任務規格及真實 PostgreSQL 測試補足 append-only 審計行為。

## 2026-08-25：技能搜尋次數上限

每個新任務由 Agent 按場景自主搜尋 1 或 2 輪，最多不超過 3 次。未找到適配且安全候選時立即停止，不重複更換近義詞消耗時間；改用框架官方文件、大廠公開實踐與成熟社區通用模式完成任務。

第一期的判斷標準是高效、完備地跑起功能閉環。技能是提升品質的工具，不是交付前置條件；不得為了形式安裝低可信或錯誤技術棧的內容。

## 2026-08-26：Task #8 分析口徑與技能搜尋收斂

套件分析期間固定用 `startedAt` 的閉區間，嚴格拒絕無時區 RFC 3339、非法日曆日期與反向時間範圍。作者、owner team 的 maintainer、global platform_admin 才能讀取；一般員工與匿名不能藉由前端隱藏規則取得報表。成功率必須分開 UID／UUID，並使用 Wilson 95% 信賴區間；活躍版本由成功與解除安裝事件折疊，待升級候選只保留版本較低且 OS／client runtime 相容的 UID。

遙測仍是 `best-effort`：平台時間是 `startedAt → endedAt`，員工時間是最近前序同安裝鍵下載到成功上報，且明示近似；缺少下載事件透過 `MISSING_DOWNLOAD_EVENTS` 交代。報表固定附「數據僅供參考」，不得宣稱為完整採用或精確人數。

Task #8 前兩次 registry 搜尋沒有輸出；Task 1 代理完成第三次 `DISABLE_TELEMETRY=1 npx -y skills find 'typescript service unit testing'` 並取得指定候選。Task 3 代理誤重複執行第四次，仍無輸出；此流程偏差已記錄，未安裝任何技能且 `skills-lock.json` 不變。`jeffallan/claude-skills@nestjs-expert` 約 4.8K 安裝但 NestJS 不適配 Fastify；`giuseppe-trisciuoglio/developer-kit@unit-test-service-layer` 約 2.4K 安裝，但未完成來源、stars、授權與目錄安全審查，拒絕採用；其餘 1～69 安裝或 C++／Go 候選也不適配。

## 2026-08-25：Outbox 與不可變 Audit 分離

`domain_events` 是發布器需要更新狀態與重試次數的 Outbox，不能套用 append-only trigger。不可抵賴操作記錄使用獨立 `audit_logs`；兩者在同一業務 transaction 寫入，但生命週期不同。

`audit_logs` 禁止 UPDATE／DELETE，PostgreSQL trigger 使用 SQLSTATE `55000` 拒絕。查詢只允許 `platform_admin`，採 `occurred_at + id` 游標而不是 offset。所有 actor／target 都是邏輯 ID，不引入外鍵。

reviewer 指派／撤銷已同交易寫入 Outbox 與 Audit。測試用 trigger 強制 Outbox 失敗後，業務指派與 Audit 均不存在，證明交易一致性。

## 2026-08-25：Task #3 技能搜尋一次即停止

Fastify／PostgreSQL catalog、search、cursor pagination 搜尋沒有合格候選；最高約 753 安裝且非官方，其他多低於 50。依搜尋上限立即停止，不安裝。Task #3 使用現有 PostgreSQL 技能、Fastify 5 現有模式、穩定排序游標與服務端可見性實踐直接交付。

## 2026-08-25：Task #3 目錄契約完成

套件使用穩定文字 `package_id`；版本直接保存同一邏輯 ID、作者、Client／OS 快照、發布者填寫的安裝／解除安裝命令與殘留副作用。沒有外鍵，套件、版本、Audit 與 Outbox 在應用交易內維持一致性。

列表與搜尋永遠只取 `published` 版本；匿名只看 public，登入身份可看 internal。`review_required` 只在詳情對作者或指定且非同團隊審核人可見，任何人都不能從下載 API 取得待審命令。第一期使用穩定排序的 offset cursor，後續資料量達到壓測門檻時再把查詢下推為資料庫 keyset cursor，不改 HTTP 欄位。

詳情資料固定提供用途／所有者、Client／OS、安裝與解除安裝命令、殘留說明、下載條件與採用摘要。`CatalogPageState<T>` 固定 Loading／Empty／Error／Partial／Success 五態，Task #9 只需映射，不重新定義語義。

## 2026-08-25：Task #5 腳本生成邊界

技能 registry 唯一一次搜尋沒有達 1K 安裝或官方來源的 Shell／PowerShell 候選；Agency Agents 只有寬泛 DevOps persona 且倉庫包含可執行腳本，因此不安裝、不複製、不執行。Task #5 直接採 Bash、PowerShell 與 OWASP 類型的最小權限、白名單遙測及不可變控制面慣例。

生成端只讀取已發佈 PackageVersion 保存的發布者命令。遙測 endpoint 由服務端注入，呼叫者只能選已聲明的 Linux／Windows、Client runtime 與 install／uninstall 動作。Linux 使用隔離子程序與父層 EXIT trap，Windows 使用 try/finally；遙測失敗落本機佇列且保留原始退出結果。

SHA-256 digest 用於傳輸完整性驗證，不宣稱公私鑰身分簽章。第二期若需要發布者不可抵賴，再加 KMS／Sigstore 簽章，不改動現有 digest 欄位。

## 2026-08-25：Taskmaster 與無人值守交付規則

每個任務開始先在專案根目錄執行 `task-master next` 與 `task-master show <id>`，確認依賴和驗收條件；熟悉 CLI 及專案 `.taskmaster/config.json` 後，才可真正執行 `list`、`set-status` 或其他更新。無人值守且沒有待確認的高風險決策時，依推薦方案自動推進；可用子代理處理互不依賴的工作以節省主會話。每個任務階段單獨提交。

## 2026-08-25：Task #6 發布治理與 Runner 邊界

治理模組是 lifecycle 的唯一寫入入口，採 expected-state／active-token CAS；作者與 owner team 成員迴避審核，工作台保存提交時 snapshot 與完整命令、殘留、digest、宣告矩陣及 Runner 證據。撤下後下載立即失效，按 UID 去重通知，匿名 UUID 不通知。首期 Runner 只支援 Linux Docker 與 Windows `powershell-wsl`；macOS 為 `not_supported`，原生 VM、外部通知 dispatcher 與進階安全加固留到第二期。

平台產生給終端使用者的三段式腳本，與 Agent 技能安裝政策分開：頭部 init 並取得 login UID／未識別 UUID；中部由 UI 保存發布者／維護者 install／uninstall 命令；尾部上報成功／失敗／原因且不覆寫原始退出碼。首期矩陣為 Linux／Windows × Codex／Claude Code，runtime 透過 adapter 擴展。

## 2026-08-25：Task #7 遙測事實與斷線補交

`installations` 是唯一不可變遙測事實表，直接保存 `package_id`、`version` 與 payload fingerprint 快照；legacy 數字版本 ID 只供追溯。新 migration、Drizzle schema 與查詢不得恢復外鍵或以內部 ID 作跨聚合關聯。

公開 `POST /api/telemetry/report` 不要求 session。白名單固定為十一欄；未知欄位只記名稱，不記值。first-write-wins 以 `idempotency_key` 唯一索引及 `ON CONFLICT DO NOTHING` 實作：相同 key／fingerprint 回 duplicate，不同 fingerprint 回 409，禁止 update 首筆事實。晚到事件以事件時間排序，不以到達順序推斷狀態。

冪等鍵必須在每次腳本真實執行時產生；同一 pending 行重試保持原 key。Linux／PowerShell 每次執行先依 FIFO 補交：2xx 移除、非重試型 4xx 進白名單 dead-letter，`408`／`425`／`429`、網路或 5xx 保留當前與後續行，並以單使用者鎖和同目錄臨時檔原子替換。遙測失敗不得改寫發布者命令退出碼；安裝或解除安裝成功但事件入隊時顯示資料同步中。

第一期不為每筆遙測再寫 Audit／Outbox，避免高頻事件三倍寫放大。若第二期需要串流消費，再新增 telemetry 專用 CDC／批次 Outbox；端點簽名、裝置證明、per-package token、進階限流與完整 anti-replay 同樣延後。

## 2026-08-25：Task #12 跨平台驗證結論

第一期遙測防繞過是 `best-effort`，不得在 UI、API 或文件宣稱不可偽造。Linux 的父層 EXIT trap、唯讀變數、隔離子程序與 PowerShell finally 只保證常見失敗路徑；同權限惡意命令防護、獨立 capture、隔離 VM、簽章與 attestation 留到第二期。

匿名 UUID 必須在目標使用者環境首次執行時生成並持久化：Linux／WSL 使用 `~/.agent-platform/uuid`，Windows 使用 `%APPDATA%\agent-platform\uuid`。不同作業系統使用者隔離；刪除後重新生成並視為新使用者。冪等 key 仍是每次腳本執行生成，不能與持久身份 UUID 混用。

`ValidationRunnerRegistry` 以 OS adapter 與 Client adapter 擴展。第一期預設只註冊 Linux／Windows 與 Codex／Claude Code；新 adapter 仍必須提供 install、telemetry、uninstall、cleanup 的完整證據，不能修改或降低共同協議。

## 2026-08-26：Task #9 前端選型與安裝腳本需求收斂

前端採 Vite 與 React，置於 `web/`，建置產物由 Fastify 靜態託管。取代 Task #9 任務詳情原本的 Next.js 建議：平台第一期僅供企業內部員工使用，即使允許居家訪問也不對外公開，SEO 需求為零，SSR 優勢歸零；同源託管可直接複用既有 opaque session 與 `HttpOnly` Cookie，不需要 CORS、`SameSite=None` 與本地 HTTPS。第二期若需 SSR，頁面元件為純 React，遷移主要影響路由層。

安裝目標收斂為三項作業系統：`linux/macos`、`windows`、`wsl`。Linux 與 macOS 的安裝命令多數可共用，合併為單一目標。Client 只記名稱不含版本號，版本相容性由發布者在使用說明中描述。第一期開放上述三系統與 Claude Code、Codex，其餘目標在介面顯示停用態並標註原因，保留擴充位置。

每份一鍵安裝腳本有獨立於技能版本的自身版本號，`v1` 起遞增，每次編輯儲存後自動遞增，並記錄變更描述、時間與遞增號。描述為選填，未填寫時顯示「無描述資訊」，不得顯示空白或自動佔位文字。檔名格式為 `install-{packageId}-{packageVersion}-{os}-{client}-{userRef}-v{scriptVersion}.{sh|ps1}`。刪除腳本採軟刪除，標記不可見但保留紀錄，版本紀錄仍可追溯。

發布者可為腳本宣告選項參數，含參數名、類型、說明與預設值，供員工在安裝時選擇安裝層級一類無法預先決定的項目。參數以 `ASP_OPT_` 前綴的環境變數原樣傳給中部命令，`--scope` 對應 `${ASP_OPT_SCOPE}`。平台只負責傳遞，不解析也不改寫參數值。員工所選選項隨遙測上報。

發布者必須填寫腳本使用說明，顯示於詳情頁並寫入腳本 `--help` 輸出。腳本內同時寫入技能版本與發布日期，於 `--help` 與安裝過程顯示。

詳情頁不得顯示中部安裝命令。中部是平台內部腳本片段，不是員工決策依據。此規則取代 PRD M3-8「下載頁展示安裝命令全文」的描述，該描述建立在已廢棄的 InstallPlan 原語模型上。員工需要的是功能描述、注意事項、使用說明與下載操作。

點讚、踩與評論屬第二期功能，PRD 第 40 行已列為 MVP 不做。第一期在資料庫設計時預留結構但不實作 API；詳情頁保留版面位置並標註「第二期功能，尚未實作」，計數顯示破折號而非 `0`，避免被誤讀為沒有人評價。

遙測欄位需從十一欄擴充加入 `script_version` 與 `options`。十一欄白名單原已提交隱私審核，擴充需重新確認；`options` 記錄員工選擇的安裝參數，屬行為資料，敏感度高於現有欄位。平台首頁底部提供隱私聲明入口，逐欄說明上報範圍與不收集項目，內容須與 `TELEMETRY_FIELDS` 保持一致。

介面禁止引入可信等級概念。歸檔線框的「公司推廣／精品／已驗證」在後端不存在，`PackageRecord` 無對應欄位。狀態一律使用 `VersionLifecycle` 真實值，安全性判斷使用 `hasResidualEffects`。

實作依據為 `docs/前端實作指導.md` 與 `docs/前端API契約.md`，線框存於 `design/wireframes/`。後端待補的 schema 調整彙整於 `docs/待決策與延後事項.md` 的 D-3。

## 2026-08-26：頁面實作前必須先出線框並經審核

實作任何前端頁面前，必須先產出該頁面的線框原型並保存到 `design/wireframes/`，交由使用者審核原型結構是否滿足需求，取得確認後才開始寫實作程式碼。未經審核不得直接進入頁面實作。

此約束適用於 Task #9 的所有頁面子任務，以及後續任何新增頁面或既有頁面的重大版面調整。純樣式微調、文案修正與不改變資訊架構的修改不受此限。

線框使用專案級 `prototype` 技能產出，picker 樣式依 `.agents/skills/prototype/PICKER.md` 逐字複製，不得套用專案 token。線框必須使用真實產品資料與真實後端欄位，不得使用 lorem ipsum，也不得虛構後端不存在的欄位。單次只探索一個頁面，避免多頁同時產出導致風格不一致。

線框同時保存為專案檔案與線上預覽：專案檔案是實作時的權威參考，不依賴網路；線上預覽供快速審閱。兩者內容必須一致。

審核通過後，將該頁面的結構決策寫入 `docs/前端實作指導.md`，並同步更新對應的 Task Master 子任務。線框只鎖定資訊架構、互動模型與 design token，不作為像素級規範；實作與線框衝突時，以 `docs/前端實作指導.md` 的文字規範為準。

此流程的目的是把版面與資訊架構的分歧在寫程式碼前解決。已發生的實例：詳情頁第一版線框誤將三段式腳本的中部命令攤開給員工看，在審核階段被發現並重做，若直接進入實作會造成整頁返工。

## 2026-08-26：Task #9 前端基礎設施與前兩頁實作結論

前端型別不 import 後端型別。後端 tsconfig 走 `NodeNext`、前端走 `bundler`，混用會產生解析衝突，因此 `web/src/api/types.ts` 與 `src/modules/*/types.ts` 平行維護，後端欄位變更時必須手動同步。

搜尋端點回傳的 `CatalogSummary` 不含 `adoption`，採用數據只在詳情端點提供。列表頁因此沒有安裝次數與成功率欄位，與線框不一致。若要補上須由後端讓搜尋回傳 adoption，不得由前端逐筆呼叫詳情造成 N+1。此事實在實作 9.2 前查 `catalog-service.ts` 才發現，先前依猜測寫的型別是錯的。

Fastify 靜態託管必須在所有 API 模組註冊之後掛載，否則 SPA fallback 會接管 API 路由。`setNotFoundHandler` 需排除 `/api/`、`/docs` 與 `/health`，否則 API 的 404 會回傳 HTML，前端 JSON 解析失敗導致錯誤訊息失真。

`@fastify/static` 需 10.1.3 以上。8.x 有四個 path traversal 與授權繞過漏洞，屬託管前端的核心依賴，不得沿用。

前端下載腳本走 `POST .../scripts` 生成後以 Blob 觸發，不是 GET 連結。後端會校驗目標是否在該版本聲明的支援清單內，不符回 409，因此前端須先依詳情資料過濾可選項，避免使用者選到必然失敗的組合。

`PackageDetailPage.tsx` 的 `OS_TARGETS` 是暫時對應表，收斂後的 `linux/macos` 與 `wsl` 都映射到後端目前接受的 `linux`。後端 `ScriptTargetOs` 補齊後需同步修正。

線框已規劃但後端尚未支撐的功能，實作時不得以假資料佔位：安裝選項參數、腳本自身版本與變更紀錄、腳本使用說明。寧可缺少，不得造成功能已存在的錯覺。使用者回饋區塊是例外，因為它是明確標註的第二期佔位。

本機預覽需 `npm run db:seed` 寫入示範資料；資料庫使用 tmpfs，容器重啟後需重跑。此腳本僅供本機預覽，不在測試或生產使用。

執行 `npm test` 前必須清除 `npm run db:seed` 寫入的示範資料，兩者共用同一個資料庫。示範資料留著時，`test/script-generator/script-generator-service.test.ts` 與 `test/governance/validation-runners.test.ts` 的 PowerShell 測試會出現 `Test timed out`。原因是這些測試實際啟動 pwsh，其在 WSL 冷啟動約 4.5 秒而預設逾時為 5 秒，資料變多使查詢變慢後越過逾時線。這是環境效能問題，斷言本身沒有失敗，不得因此修改測試或實作。遇到此類逾時先確認資料庫是否乾淨與 pwsh 啟動耗時。

## 2026-08-29：Task 13 上架 Matrix 完整實作

腳本命令的真實來源已從 package version 層級移到 target／revision 層級。`package_version_script_targets` 保存每個「系統 × Client」的目前指標與軟刪除狀態，`script_target_revisions` 以 append-only 快照保存命令、options、usage、殘留與複製來源。六個組合互不覆蓋，每個 target 首次完整儲存為 v1，其後單調遞增，revision 永不刪除。軟刪除只隱藏 current revision，重建時沿用同一 target id 並從 `max(script_version)+1` 續號。依第一期規則，兩張新表不建立任何外鍵，只用邏輯 ID 與唯一／複合索引。

送審閘門是本次的行為分界：矩陣改由 active target 的 current revision 精確導出，不再由 `supportedOs × clients` 做 Cartesian product 推測。缺少 active target、存在待填 target、只剩 legacy imported revision、命令或 usage 為空時，一律在寫入 validation、audit 與 outbox 之前以 `SCRIPT_TARGETS_INCOMPLETE` 擋下。validation run 另外保存 target snapshots 與 manifest digest，digest 取自排序後的 `(targetOs, clientRuntime, scriptVersion, contentDigest)`。

腳本生成器改為精確按 target 生成：`linux/macos` 與 `wsl` 走 Bash adapter，`windows` 走 PowerShell；選項以安全引號注入 `ASP_OPT_` 前綴環境變數，`--help` 在 UUID 與佇列初始化之前處理，因此不產生遙測。遙測新增 `installations.script_version integer` 與 `installations.options jsonb` 兩個可為空欄位；舊腳本缺省時映射為 null 以維持相容，`PrivacyPage` 同步標示這兩欄為新增欄位。

複製語意：複製後的目的 target 是獨立快照，帶 `copiedFrom` 來源標記；之後任何一次手動 PUT 都清除該標記，且不回寫來源。前端所有寫入只依伺服器成功回應更新畫面，不做樂觀假存。

驗收：354 項自動化測試、typecheck 與 production build 全數通過；22 項真實 API 端到端與 17 項瀏覽器驗收全數通過；migration 兩次執行冪等，`public` schema 外鍵數為 0。完整證據見 `docs/驗收記錄/Task-13-上架-Matrix-驗收.md`。

開發模式下 `/publish` 的 `GET /api/packages` 會出現一次 `net::ERR_ABORTED`。這是 React `StrictMode` 開發期刻意雙掛載，`usePageState` 的 cleanup 正確中止第一次請求所致，不是請求失敗；production build 單次載入失敗請求為 0，因此不改產品邏輯。

仍存在的邊界：舊 `package_versions` 單一命令欄位保留一個相容週期僅供讀取；migration 只回填語意明確的舊資料，含糊的多目標舊列需人工補齊；遙測擴充的對外書面隱私核准尚未取得，是正式上線前置條件。

## 2026-08-29：Task 11 體驗完善後端

Task 11 的四項功能中，三項可在第一期完整交付，一項按既有決策降級：升級差異、維護者支援入口與結構化反饋全做；推薦更新通知只做平台內通知，IM 與郵件的外部 dispatcher 依 Task #6 決策仍屬第二期。任務描述中的「一鍵升級腳本生成」不需要新端點，確認差異後沿用既有 `POST .../scripts` 生成目標版本腳本即可。

升級差異以 Task 13 的 target／revision 為權威來源精確計算，不從 `supportedOs × clients` 推測。比較範圍是雙方的 active target current revision：軟刪除的 target 與歷史 revision 都不參與，因為使用者升級後拿到的是目前指標，不是任何歷史快照。差異涵蓋腳本目標增減、安裝與解除安裝命令、使用說明、選項參數與殘留效應。

差異結果刻意不含命令全文，只回傳 `contentDigest`、`scriptVersion` 與變更旗標。這與「詳情頁不得顯示中部安裝命令」是同一條規則：中部是平台內部片段，不是員工決策依據；要看完整腳本仍須經安裝頁。此約束已由測試固定。

`requiresReapproval` 的語義是「使用者升級前需重新確認」，不是治理層的重新送審。命令、選項或殘留副作用一旦改變，使用者原本的安裝決策依據就不再成立。殘留副作用只在「本次新增」時列為理由；本來就有的不重複告警。

差異端點只比較呼叫者本來就看得到的版本，不可成為探測未發布內容的旁路。

支援入口與結構化反饋收在新的 `experience` 模組。支援入口採整組覆寫，送出的清單即為完整結果，未列出的既有渠道視為刪除；渠道類型限 `im_group`、`email`、`ticket_system`、`doc` 四種，避免自由文字讓使用者猜格式。讀取對所有能看到該套件的身分開放：員工遇到問題時需要能直接找到人，不應要求先登入才看得到求助管道。

反饋開放匿名 UUID 提交，因為安裝腳本的使用者不一定登入，要求登入會讓最需要協助的失敗案例回報不上來。但反饋明細含自由文字，只有維護者可讀，一般員工回 403、匿名回 401。統計固定回傳全部七個分類含計數 0：缺席的分類與「無人回報」是兩件事，隱藏會讓讀者誤判分佈；沒有樣本時平均滿意度為 `null` 而非 0。滿意度是自願填寫的自我聲明，與遙測同屬 best-effort。

反饋不寫 `audit_logs`。`audit_logs` 的語義是具名操作者的不可抵賴紀錄，而提交者可能是匿名 UUID；反饋本身即是明細。維護者變更處理狀態則有具名操作者，照常寫 audit。

新版本發布通知沿用既有 `user_notifications`，只擴充 `version_published` 型別，不新建通知表。收件人判定與撤下通知不同：撤下通知的是「同一版本」的安裝者，發布通知的是「同套件其他版本」的安裝者——本次發布的版本還沒有任何安裝紀錄，而已經裝到新版的人不需要被提醒升級。作者本人排除避免自己通知自己，匿名 UUID 沒有收件匣故不通知。通知與 audit、outbox 在同一交易寫入。

semantic version comparator 從 `analytics-service.ts` 移到 `shared/version/semantic-version.ts`。原因是 catalog 的差異計算需要它，而 analytics 已依賴 catalog 型別；catalog 反向 import analytics 的執行期函式會形成模組循環。catalog 原本只從其他模組 import 型別，唯一的執行期依賴是 shared，此次遷移維持該邊界。analytics 重新匯出 `compareSemanticVersions` 以維持既有匯入不變。

兩張新表 `package_support_channels` 與 `package_feedback` 依第一期規則不建任何外鍵，只用邏輯 ID 與唯一／複合索引。

驗收：380 項自動化測試、typecheck、production build 全數通過；migration 兩次執行冪等，`public` schema 外鍵數為 0。

前端（子任務 11.5）尚未實作。依 `AGENTS.md` 的前端頁面實作流程，升級差異檢視、支援入口展示、反饋表單與通知中心都必須先產出線框並經使用者審核才能進入實作；此閘門無法在無人值守模式下滿足。

## 2026-08-29：Task 11 前端與就地編譯產物污染

四個介面依使用者指示各出單一線框，不做多方向探索，風格沿用既有線框的 token 與 picker 慣例。線框經真實 Chrome 驗證後才進入實作。

升級差異頁不顯示任何命令全文。後端的 `VersionDiff` 本身不含命令，前端也不得改由其他端點補取；`unchanged` 的組合仍要顯示在清單中，否則使用者無法確認該組合確實沒變。`requiresReapproval` 為真時以核取方塊擋住下載入口，這是使用者層級的重新確認，不是治理層重新送審。

發布通知的 payload 補上 `installedVersion`。原因是差異比較需要來源與目標兩個版本，而通知原本只有新版本號；沒有這個欄位就只能猜使用者裝的是哪一版，猜錯比不提供入口更糟。同一人裝過多個舊版時取最高者。舊通知缺此欄位時只導向套件詳情。

詳情頁的「使用者回饋」佔位已改名為「點讚與評論」。原本的命名會與 Task 11 的結構化反饋混淆：前者是 P2-1 第二期功能，保留停用態與破折號計數；後者第一期已實作，是獨立區塊。兩者不共用版面。

支援入口採整組覆寫，介面必須明示移除的渠道會被刪除，因為後端不做增量合併。位址只有 `https?://` 與 email 做成連結，其餘原樣顯示，不猜測協定。

### 就地編譯產物讓測試數量虛高並造成偽逾時

`tsconfig.json` 原本沒有 `noEmit` 也沒有 `outDir`，因此任何一次裸 `tsc` 都會把 `.js` 就地輸出到 `src/`、`test/`、`web/src/` 旁邊。`npm run typecheck` 帶了 `--noEmit` 所以看不出問題，但直接執行 `tsc` 會留下 120 份殘留。

後果不只是檔案變髒：vitest 會把殘留的 `.test.js` 當成獨立測試檔收集，測試數量憑空翻倍（791 對比真實的 401），且同一個實際啟動 pwsh 的 PowerShell 測試被平行執行兩次而互相搶佔，穩定在 5 秒門檻逾時。

此前把該逾時歸因於「pwsh 冷啟動接近門檻加上示範資料拖慢查詢」並不正確。本次實測 pwsh 冷啟動為 0.48 秒，資料庫也是乾淨的，清除重複檔案後即穩定通過。真正原因是重複收集導致的平行搶佔。

已在 `tsconfig.json` 加上 `noEmit: true`，`tsconfig.build.json` 覆寫為 `false` 維持建置輸出到 `dist`；`.gitignore` 補上就地產物規則作為第二道防線。日後若再看到測試數量異常翻倍或 PowerShell 測試逾時，先查 `find src test web/src -name '*.js'` 是否有殘留。

另一個環境事實：本機 `/usr/bin/rg` 實際是 GNU grep 而非 ripgrep，不接受 `--type` 一類 ripgrep 參數。`rtk grep` 可正常使用。

### 驗收

401 項測試、41 個檔案全數通過；typecheck 與 production build 通過。真實 Chrome 對 production build 驗收技能池、套件詳情、通知中心、我的安裝、支援與反饋後台、升級差異六頁，皆無 console 錯誤、runtime 例外、失敗請求與整頁橫向溢位。

升級差異另以真實 API 驗證：命令變更、選項新增與殘留副作用引入三項 reapproval 理由皆正確導出，且回應與 DOM 皆不含命令全文。支援入口的整組覆寫、反饋提交、統計與狀態流轉亦以真實 API 驗證通過。

## 2026-08-30：Task 17 技能列表分類標籤資料化

五組標籤原本寫死在 `web/src/pages/catalog-taxonomy.ts`，只用於驗證版面。本次把來源、發布者、分類、分級四組資料化；熱度的下載數仍未埋點，屬 Task 18。

兩個前置決策經使用者確認：分級由審核人核定，發布者不得自評；category 收斂為八類列舉（前端、後端、資料、測試、部署運維、安全、產品設計、通用）。

### category 收斂採新增欄位而非改造舊欄位

舊 `packages.category` 是自由文字，實際資料同時存在 `backend` 與 `後端`、`DBA` 與 `部署`，且該值已被複製到 `publication_reviews.category` 與 `reviewer_assignments.category`。直接對舊欄位加 CHECK 需連帶改寫三張表，風險遠大於收益——`authorization-service.ts` 早已因為同一原因停用「按分類限縮審核範圍」。

因此新增受約束的 `category_code` 作為篩選與標籤的真實來源，舊 `category` 降級為 legacy 顯示標籤。migration 以正規化大小寫與空白後的比對表回填，無法歸類者留在預設 `general`，不猜測。實測既有資料全部正確歸類，無誤歸。

上架頁不再讓使用者填自由文字分類，`category` 一律由所選 `categoryCode` 的中文標籤導出。讓每個人自己填分類正是同義異名的來源。

### 分級的權責與端點邊界

分級屬於 package 而非 version：它描述技能在組織內的推廣地位，不隨每次發版重評。`CreatePackageInput` 與 `UpdatePackageInput` 都排除 grade，一律經 `PATCH /api/packages/:packageId/grade`，授權走 `canReview`（reviewer 或 platform_admin），與審核決議同一組人但不同端點。

不綁在審核決議上：改分級是發布後的常態操作，若只能在核准當下設定，之後想調整就得逼發布者重新送審一個無關的版本。已封存技能拒絕變更分級。核定記錄 `grade_decided_by_uid` 與 `grade_decided_at` 供審計追溯。

審核詳情頁的分級面板取技能當前值而非 `data.package`：後者是送審當下的快照，分級若在送審後被改過，拿快照當初始值會讓審核人一送出就改回舊值。

### 順帶整理

row→`PackageRecord` 的映射原本在 catalog、governance、analytics 三處各抄一份，新增欄位時只改到其中一兩處就會讓讀取端拿到缺欄位的快照。已抽成 `src/modules/catalog/package-row.ts`。前端 `PackageSummary`、`MaintainedPackage`、`PackageDetail` 三者重複的欄位清單抽成 `PackageRecordSummary`。

列表的「下載 / 安裝」欄改為只顯示下載並標「未埋點」：`PackageSummary` 依契約不含 adoption，安裝數只在詳情頁提供，列表不重複揭露。網址參數的列舉值逐一比對後才放行，無效值忽略而非讓後端回 400 把整頁變成錯誤狀態。

### 驗收

typecheck、production build 通過；627 項測試通過。3 項失敗為 PowerShell/process-runner 既有問題，已用 `git stash` 確認改動前同樣失敗。

### 一次診斷誤判與其擴散

驗證期間 API 回應缺少新加的欄位，我一度懷疑是程式缺陷並重建 `dist` 排查。實際原因是請求打到了一個更早啟動、尚未重載的 `tsx watch src/server.ts`。

會誤判是因為 `ss -lptn` 顯示該程序名為 `MainThread`，我據此判定「3000 埠被非本專案的服務佔用」，沒有進一步查 `/proc/<pid>/cmdline`——那裡明確顯示它就是本專案的 dev server。`MainThread` 只是執行緒名，不是程式身分。

這個錯誤結論擴散到了交付物：試用文檔要求改用 3100、本節原本也記為「環境事實」。而 `PORT=3100` 本身還是第二個錯——`vite.config.ts` 的代理目標硬編碼為 `127.0.0.1:3000`，改後端埠會讓前端找不到 API。

教訓：判斷程序歸屬要查 `/proc/<pid>/cmdline` 與 `cwd`，不以 `ps`／`ss` 的程序名欄位為準；埠與位址一律以 `.env` 與 `vite.config.ts` 為準，不靠推測。相關規約是 `rules/preferences/source-verification-min.md`——摘要不是事實，原始內容才是。

### 本機環境事實
