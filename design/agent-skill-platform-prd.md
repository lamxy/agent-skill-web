## 1. 目標與範圍

### 要解決的問題

技能從分享會、Wiki、群聊進入員工工作環境時，依賴、版本、環境問題導致安裝失敗，作者被迫反覆人工支援。平台提供統一的發現、下載、安裝、卸載與數據回流通路。

### MVP 交付目標

1. 員工能在平台瀏覽技能，下載一鍵安裝腳本，本機執行完成安裝
2. 安裝／卸載結果自動回流，作者能看見下載、安裝、卸載三段漏斗
3. 維護者能在頁面填寫安裝與卸載命令，經審核後發布
4. 管理員能審核發布、指定審核者、撤下有風險版本

### 範圍邊界

**MVP 做**：技能目錄與搜尋、腳本生成器、發布審核、遙測上報、作者分析頁、SSO 身份、管理員後台。

**MVP 不做**：點讚評論討論、精品池與自動晉升、強制安裝、Bundle 依賴解析、MCP 沙箱、IM Bot 與 IDE 原生頁面、Git PR 自動化管線（先手工上架）、多服務拆分。

### 技術選型基調

模組化單體，單一部署單元與單一關聯資料庫。模組間透過應用服務與領域事件通信，禁止跨模組直接改表。事件用同庫 Outbox，不引入外部消息中間件。

## 2. 核心機制

### 2.1 一鍵安裝腳本模型

平台不遠端操作員工機器，而是生成腳本供下載執行。**遙測錨點在腳本自身**，不依賴客戶端能力——[A0 查證](./a0-client-capability-matrix.md)證明五個主流客戶端（Claude Code、Codex、Gemini、Copilot、Cursor）均不提供週期性 Check-in，任何錨定在客戶端 hook 上的設計都不成立。

四段結構：

| 模組 | 內容 | 產出方 | 維護者可寫 |
|---|---|---|---|
| **頭部** | 初始化；取已登入 uid，未登入生成 UUID；記錄開始時間、腳本版本、PackageVersion、冪等鍵 | 平台生成 | 否 |
| **中間部** | 安裝命令；結構化錯誤輸出 | 維護者填寫 | 是 |
| **卸載部** | 卸載命令；殘留副作用聲明 | 維護者填寫 | 是 |
| **底部** | 匯總並上報成功／失敗／卸載 | 平台生成 | 否 |

**關鍵約束**：頭部與底部不對維護者開放，且中間部**不得覆寫、停用或繞過**兩者。這是遙測可信度的唯一保障，須在實施中重點驗證（見 §6.1）。

### 2.2 使用者標識

| 情境 | 標識 | 用途 |
|---|---|---|
| 已登入 | 平台 uid | 可歸屬到員工，納入待升級名單與通知範圍 |
| 未登入 | UUID | 本機持久化，同機重複安裝沿用同一值 |

UUID 不得由平台側推導或反查真實身份。已登入與 UUID 安裝在指標中分層展示，不合併為單一成功率。

### 2.3 遙測字段白名單

底部模組只允許上報以下字段。**此清單同時是隱私聲明範圍與審核判斷依據**：

| 字段 | 內容 |
|---|---|
| OS 系統類型 | `macos` / `linux` / `windows` / `wsl` |
| 使用者標識 | uid 或 UUID |
| 工具／技能標識 | Package ID 與 Version |
| 安裝狀態 | 成功 / 失敗 |
| 卸載狀態 | 已卸載 |
| 時間 | 各狀態發生時間 |

**明確不收集**：提示內容、業務代碼、憑證、完整環境變數、命令輸出全文、檔案路徑、機器名稱、IP、OS 細版本號。

新增字段須重新通過隱私審核。

### 2.4 發布審核標準

腳本模型下人工審核是主要安全防線。**兩項標準均通過才可 approve**：

**標準一：遙測合規**
- 中間部未收集白名單外資料
- 中間部未向平台以外位址外傳資料
- 中間部未嘗試覆寫、停用或繞過頭部與底部

**標準二：安裝正確且遙測可得**
- 在所聲明的每個系統上能正確完成安裝
- 平台確實收到預期遙測數據，字段與白名單一致
- 卸載命令可執行，`has_residual_effects` 聲明與實際相符

**執行方式**：管理員參考標準自行決策，不做自動化干預。MVP 不設審核時效要求。審核須在演示環境實測，不得僅憑閱讀命令文本完成。

### 2.5 Client 支援範圍模型

**Client 支援範圍是 Package 的一級屬性，隨適配工作演進**：

| `adaptation_source` | 定義 | 維護責任 |
|---|---|---|
| `official` | 上游作者提供的適配 | 上游作者 |
| `internal` | 公共架構或內部團隊實現 | 適配實現者（須具名）|
| `community` | 個人或社群實現 | 貢獻者，平台不承諾支援 |

某技能官方支援 Claude Code 與 Codex、未支援 Gemini，其範圍即為前兩者；公共架構實現 Gemini 適配並驗證後，範圍擴展至三者並標記 `internal`。

**公司 Client 優先級**（決定 Adapter 建設順序，不限制 Package 可宣告範圍）：

| 層級 | Client |
|---|---|
| P0 優先保證 | Claude Code、Codex |
| P1 涵蓋 | GitHub Copilot、Gemini |
| P2 保留擴展 | Cursor、Antigravity CLI、OpenCode、Pi 等 |

### 2.6 平台能力邊界（須如實對外聲明）

| 能力 | 平台能做 | 平台不能做 |
|---|---|---|
| 阻止新安裝 | 撤下下載入口，即時生效 | — |
| 停用已安裝 | 依上報記錄通知受影響 uid，提供一鍵卸載腳本 | **無遠端強制停用能力** |
| 清除殘留 | 展示殘留說明與手動清理步驟 | 代替使用者清理 |

不得以任何措辭暗示平台具備實際不存在的管控力。

## 3. 模組拆解（實施主體）

七個模組。標示 `[並行]` 者無前置依賴，可同時開工。

---

### M1. 身份與權限 `[並行]`

**職責**：SSO 登入、團隊／角色映射、審核權授予。

| # | 功能點 | 驗收 |
|---|---|---|
| M1-1 | SSO 登入與 session 管理 | 員工可登入，取得 uid 與所屬團隊 |
| M1-2 | 角色模型：員工／維護者／審核者／平台管理員 | 角色可疊加，權限按角色判定 |
| M1-3 | 平台管理員指定審核者 | 可按 Package 類型、分類或全域授權；指定與撤銷進審計 |
| M1-4 | 作者迴避規則 | **作者不得審核自己提交的版本**，系統層阻斷 |
| M1-5 | 未登入訪問策略 | 未登入可瀏覽與下載，安裝上報使用 UUID |

**對外接口**：`getCurrentUser()`、`hasRole(uid, role, scope)`、`canReview(uid, packageId)`

---

### M2. 技能目錄（Catalog） `[並行]`

**職責**：Package 與版本的元數據、搜尋、詳情展示。

| # | 功能點 | 驗收 |
|---|---|---|
| M2-1 | Package 註冊與元數據維護 | 支援 name、owner_team、category、visibility、source_uri、license |
| M2-2 | PackageVersion 管理 | 版本、變更說明、支援系統矩陣、Client 支援範圍 |
| M2-3 | 技能池列表與搜尋 | 支援關鍵字、分類、Client、系統篩選 |
| M2-4 | 詳情頁 | 按序展示：用途與所有者 → 支援 Client 與系統 → 安裝說明 → **殘留副作用聲明** → 下載入口 → 採用數據 |
| M2-5 | **待審核版本不可見** | `review_required` 狀態不出現在列表、搜尋與下載入口，僅作者與指定審核者可見 |
| M2-6 | 頁面狀態完整性 | 所有頁面定義 Loading／Empty／Error／Partial／Success |

**對外接口**：`GET /packages`、`GET /packages/{id}`、`GET /packages/{id}/versions`

---

### M3. 腳本生成器 ★核心

**職責**：維護者填寫入口、四段組合、簽名、下載分發。

| # | 功能點 | 驗收 |
|---|---|---|
| M3-1 | 頭部模組實現 | 取 uid；未登入生成並持久化 UUID；記錄開始時間、腳本版本、PackageVersion、冪等鍵 |
| M3-2 | 底部模組實現 | 匯總並上報；上報失敗寫入本機隊列，恢復後補交 |
| M3-3 | **防繞過機制** | 中間部無法覆寫、停用或跳過頭部與底部。**這是遙測可信度的基礎，見 §6.1** |
| M3-4 | 中間部填寫入口 | 維護者填寫安裝命令；須選擇適用系統（macos／linux／windows／wsl）|
| M3-5 | 卸載部填寫入口 | 填寫卸載命令；**須聲明 `has_residual_effects`**，為 true 時填寫殘留說明與手動清理步驟 |
| M3-6 | 四段組合與簽名 | 按目標系統組合，簽名後產生不可變腳本，記錄摘要 |
| M3-7 | 按系統分發 | 使用者只取得其系統對應的變體；**未聲明的系統不提供下載** |
| M3-8 | 執行前預覽 | 下載頁與腳本首部展示：安裝命令全文、影響資源、所需權限、**將上報的遙測字段** |
| M3-9 | 卸載前提示 | `has_residual_effects=true` 時，**執行卸載動作前**展示殘留說明並取得確認 |
| M3-10 | 模組化／SDK 形態 | 四段職責分離；不限定實現技術，但須滿足 §2.1 約束 |

**對外接口**：`POST /packages/{id}/versions/{v}/script`、`GET /packages/{id}/versions/{v}/script/download`

---

### M4. 發布審核（Governance）

**依賴**：M1（審核者角色）、M3（待審腳本）

| # | 功能點 | 驗收 |
|---|---|---|
| M4-1 | 版本生命週期狀態機 | `draft → validating → review_required → published → deprecated → delisted`；`emergency_disabled` 可覆蓋；`validation_failed → draft` |
| M4-2 | 提交審核 | 維護者提交後進入 `review_required`，此狀態不對員工展示 |
| M4-3 | 審核工作台 | 展示中間部與卸載部命令全文、支援系統、殘留聲明、遙測字段預覽 |
| M4-4 | **演示環境實測** | 提供乾淨環境供審核者執行待審腳本，驗證安裝成功、遙測如實上報、卸載可執行 |
| M4-5 | 審核決議 | `pending → approved｜rejected`；理由與操作者進審計；拒絕回 `draft` |
| M4-6 | 重新審核規則 | 作者修改後須重新審核，**不得沿用前次結果** |
| M4-7 | 撤下版本 | 撤下下載入口即時生效，記錄 reason_code、effective_at、操作者 |
| M4-8 | 通知受影響使用者 | 依上報記錄定位 uid，經公司通知渠道發出卸載或升級指引 |

**對外接口**：`POST /versions/{id}/submit-review`、`POST /reviews/{id}/approve`、`POST /reviews/{id}/reject`、`POST /versions/{id}/delist`

---

### M5. 遙測上報（Telemetry）

**依賴**：M3（腳本底部）

| # | 功能點 | 驗收 |
|---|---|---|
| M5-1 | 上報接收端點 | 接收 `ScriptDownloaded`、`InstallationSucceeded`、`InstallationFailed`、`PackageUninstalled` |
| M5-2 | 字段白名單校驗 | **服務端強制校驗**，白名單外字段直接丟棄並記錄異常 |
| M5-3 | 冪等去重 | 依冪等鍵去重，重試不產生重複記錄 |
| M5-4 | 斷線補交 | 接受本機隊列的延遲提交，按序處理 |
| M5-5 | 狀態明確性 | **安裝成功但上報失敗，不得表現為安裝失敗** |
| M5-6 | 結構化錯誤碼 | 失敗落入可操作分類，不含憑證、業務代碼、命令輸出全文 |
| M5-7 | 日誌脫敏 | 預設脫敏，禁止保存環境變數全集 |

**事件流**：
```text
瀏覽 → 下載 [ScriptDownloaded：興趣]
  → 執行 → 頭部取 uid/UUID
  → 中間部安裝
  → 底部上報 [InstallationSucceeded | InstallationFailed：採用]
  → （日後）卸載 [PackageUninstalled：流失]
```

### M6. 分析頁（Analytics）

**依賴**：M5（遙測數據）

| # | 功能點 | 驗收 |
|---|---|---|

## 4. 資料模型

### Package
`package_id`（穩定 ID，不隨名稱或倉庫變更）、`type`、`name`、`owner_team`、`source_uri`、`visibility`、`category`、`license`、`lifecycle`（`active` / `archived`）

### PackageVersion
`version`、`source_ref`、`release_notes`、`lifecycle`、`supported_os[]`、`script_digest`

**Client 支援範圍**（每筆）：
```yaml
clients:
  - name: claude-code
    version: ">=1.8"
    adaptation_source: official      # official | internal | community
    adaptation_maintainer: null      # internal/community 時必填
    adaptation_verified_at: null
```

**腳本內容**：
```yaml
script:
  install_command: <中間部，按系統分別填寫>
  uninstall_command: <卸載部，按系統分別填寫>
  has_residual_effects: bool         # 必填
  residual_description: string       # has_residual_effects=true 時必填
  manual_cleanup_steps: string       # 同上
```

### Installation
`installation_id`、`package_id`、`version`、`user_ref`（uid 或 UUID）、`user_ref_type`、`os_type`、`status`（`downloaded` / `succeeded` / `failed` / `uninstalled`）、`error_code`、各狀態時間戳、`idempotency_key`

### PublicationReview
`review_id`、`version_id`、`reviewer_uid`、`status`（`pending` / `approved` / `rejected`）、`reason`、`decided_at`

> 資料模型保留 `InstallationApproval` 與 `UserConsent` 的獨立位置（架構決策），MVP 不實現其執行路徑。同理保留 `approval_group`、`required_count` 供日後多人會簽。

## 5. 實施順序

### 批次一：可上架、可下載（最小閉環）

**並行開工**：M1 身份、M2 目錄、M7 審計

**接續**：M3 腳本生成器（核心，工作量最大）→ M4 發布審核

**批次一可用定義**：維護者能填寫命令並提交、審核者能審核並發布、員工能瀏覽並下載腳本、本機執行能完成安裝。

> 此時尚無數據回流，但**平台已具備完整交付價值**——這已經比 Wiki＋群聊好。

### 批次二：數據回流

M5 遙測上報 → M6 分析頁

**批次二可用定義**：三段漏斗可見、作者能看到失敗分布、員工能看到我的安裝。

### 批次三：體驗完善

- 升級流程與版本差異展示
- 維護者支援入口配置
- 結構化使用反饋（含「需要人工協助」標記）
- 推薦更新通知

### 依賴圖

```text
M1 身份 ─┐
M2 目錄 ─┼─→ M3 腳本生成器 ──→ M4 審核 ──→ 【批次一上線】
M7 審計 ─┘                                      │
                                    M5 遙測 ────┤
                                        │       │
                                    M6 分析 ────→ 【批次二上線】
                                                 │
                                            批次三體驗完善
```

## 6. 實施中的待解難題

這一節是實施階段真正需要攻克的技術問題，優先級高於任何流程性工作。

### 6.1 防繞過機制 ★最高優先

**問題**：中間部由維護者填寫，若能 `exit`、`unset`、覆寫函數或改寫上報位址，整個遙測模型即失效——M5、M6 全部建立在不可信數據上。

**須驗證**：
- 中間部提前結束時，底部能否仍然上報
- 中間部能否覆寫頭部定義的變數或函數
- 中間部能否改寫上報端點位址
- 中間部能否偽造成功狀態

**若無法從機制上保證**：須降級為「遙測為盡力而為，數據僅供參考」，並在分析頁如實標註——**不得讓使用者以為數據是完整的**。

### 6.2 跨系統腳本一致性

同一技能在 macOS／Linux／Windows／WSL 上的安裝命令差異大。需確定：
- 四段組合的模板機制如何處理系統差異
- Windows 用 PowerShell 還是要求 WSL
- WSL 視為獨立目標（已定），但與 Linux 的複用邊界在哪

### 6.3 UUID 持久化

- 存放位置（各系統的慣例路徑）
- 同機多使用者的處理
- 使用者清除後的重新生成規則（會影響去重）
- 保留期與隱私合規

### 6.4 上報失敗的使用者體驗

安裝成功但上報失敗時，使用者看到什麼？這決定了他會不會重跑腳本造成重複安裝。需定義本機隊列格式、重試策略與使用者可見狀態。

### 6.5 演示環境

M4-4 要求審核者在乾淨環境實測。需確定：容器還是虛擬機、如何覆蓋四個目標系統、環境重置成本、與 CI 的關係。

### 6.6 殘留副作用的判定

`has_residual_effects` 由維護者自行聲明。審核者如何驗證聲明屬實？完全依賴人工比對安裝前後差異是否可行，或需要工具輔助。

## 8. 風險

| 風險 | 影響 | 緩解 |
|---|---|---|
| **防繞過機制無法從機制保證** | 遙測不可信，M5／M6 價值歸零 | §6.1 列為最高優先；若失敗則降級為「盡力而為」並如實標註 |
| 維護者填寫的命令帶來供應鏈風險 | 終端安全 | **已顯式接受**。緩解：人工審核＋演示環境實測＋簽名＋全文預覽＋可即時撤下 |
| 人工審核成為交付瓶頸 | 多作者上架時延遲 | MVP 單作者不成問題；多作者前須解決 SLA、積壓可見性、輔助掃描 |
| 跨系統腳本維護成本 | 維護者負擔重 | 先只要求聲明實際支援的系統，不強求全覆蓋 |
| 卸載命令覆蓋不全 | 殘留污染使用者環境 | 強制聲明＋卸載前提示＋下載頁展示 |
| 遙測收集過度 | 員工不信任 | 白名單＋服務端強制校驗＋審核標準一 |
