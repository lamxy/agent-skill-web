SSO 登入與身份體系

Task 10.6 線框。說明企業 OAuth2 資訊如何落到平台資料庫、平台自身的使用者體系長什麼樣， 以及登入態在介面上如何呈現。標「待實作」者為取得 IdP 憑證後需要新寫的部分。

1

核心設計：企業 IdP 不進資料庫

平台只存「映射後的最小身份」

關鍵結論：企業的 OAuth2 資訊（endpoint、client id/secret、access token、refresh token） 一律不寫入資料庫。client 憑證由環境變數提供（第一期規則：秘密由環境變數提供）； access token 只在 callback 當下用一次，換到 uid／姓名／團隊後就丟棄。 資料庫只保留平台自己的身份記錄與自己簽發的 session。

企業 IdP 持有

  • 員工帳號與密碼
  • 組織架構、團隊歸屬
  • OAuth2 授權與 token 簽發
平台不儲存

環境變數持有

  • OIDC_AUTHORIZE_URL
  • OIDC_TOKEN_URL
  • OIDC_USERINFO_URL
  • OIDC_CLIENT_ID / SECRET
  • OIDC_REDIRECT_URI
待新增至 config.ts

平台資料庫持有

  • identities：uid、姓名、團隊
  • identity_sessions：自簽 session
  • role_assignments：平台角色
  • reviewer_assignments：審核範圍
四張表皆已存在

登入流程：企業帳號如何變成平台身份

兩個既有端點 /api/auth/login 與 /api/auth/callback 不變，只換 provider 實作

瀏覽器
點「使用公司帳號登入」
導向 GET /api/auth/login
平台 · beginLogin
組出 IdP 授權 URL
帶 client_id、redirect_uri、scope、state；state 綁 returnTo 防轉址竄改
企業 IdP
員工在公司頁面登入
平台看不到密碼
平台 · completeLogin
code 換 token 換 userinfo
回傳 ProviderIdentity：uid／displayName／teamIds。token 用完即棄
平台 · callback
upsert 身份 + 發 session
寫 identities，簽 asp_session HttpOnly Cookie

需要新寫的只有一個類別

OAuth2IdentityProvider implements IdentityProvider，兩個方法，落在 src/modules/identity/identity-provider.ts。介面早已定義，kind: 'oidc' 也已在型別中預留。

方法輸入輸出

已就緒、無需改動的部分

  • callback 路由的 upsert 與發 session 邏輯
  • session 以 SHA-256 摘要入庫，明文只在 Cookie
  • Cookie 為 HttpOnly，production 自動加 secure
  • 8 小時有效期、登出即撤銷
  • 非開發環境缺配置時 fail-closed 回 503
  • 正式/staging 環境禁用開發身份提供者
3

資料庫如何承接

四張表、零外鍵，跨表以業務 ID 關聯

資料表承接的內容關鍵欄位狀態
identities IdP 回傳身份的落地。provider_type 區分 development 與 oidc，同一份程式碼可切換來源。團隊以 jsonb 陣列冗餘保存，避免查詢時跨表。 uid (PK)、display_name、team_ids、provider_type、active 已存在
identity_sessions 平台自簽 session，與 IdP token 無關。存的是 token 的 SHA-256 摘要，資料庫外洩也無法反推 Cookie。 session_digest (PK)、uid、expires_at、revoked_at 已存在
role_assignments 平台角色，與 IdP 無關、由平台管理員授予。支援五種範圍，同一人可持多筆。 uid、role、scope_type、scope_value、active 已存在
reviewer_assignments 審核人的可審範圍（package_type × category），獨立於角色表，供審核工作台派單。 reviewer_uid、package_type、category、active 已存在
因此 10.6 不需要任何 migration。schema 在 Task 2 已按 OIDC 形狀設計完成， provider_type 的 CHECK 約束已含 'oidc'。取得憑證後只補程式碼與環境變數。
一個需要決策的點：IdP 的 uid 若與現有開發身份的 uid 撞號， upsert 會直接覆寫既有記錄連同其角色關聯。建議正式環境上線前確認 IdP uid 的命名空間， 或在 upsert 時加上 provider_type 一致性檢查。
4

使用者體系：三層

身份來自 IdP，角色來自平台，審核範圍再獨立一層

第一層 · 身份（誰）

由企業 IdP 決定，平台不可編輯。

uid
員工唯一識別
displayName
顯示姓名
teamIds
所屬團隊陣列

teamIds 同時是利益迴避的依據：審核人不得審自己團隊的套件。

第二層 · 角色（能做什麼）

平台管理員授予，可帶範圍。

employee 一般員工，瀏覽與安裝
maintainer 套件維護者，發版
reviewer 審核人，審上架申請
platform_admin 平台管理員，授權他人

第三層 · 審核範圍（管哪些）

reviewer 角色之上再切範圍。

packageType
skill / agent …
category
frontend / infra …

由「審核者管理」頁維護，已有線框與實作。

角色範圍（scope）的五種形態

global
全平台。scope_value 必須為空
team
限某團隊
package_type
限某套件類型
category / package
限某分類或單一套件

判定規則：global 範圍命中任何請求；其餘需 type 與 value 皆相符。 資料庫以 partial unique index 保證同一組合只有一筆 active。

5

第四種身份：匿名訪客

不是登入失敗，是一等公民

設計意圖

未登入者拿到一個 asp_anonymous UUID Cookie（一年有效）， 可瀏覽技能池、看詳情、被遙測記錄，但不能安裝、發布或審核。 登入後 session Cookie 優先，匿名 Cookie 保留但不再作為身份依據。

介面上不該把匿名狀態畫成「錯誤」或攔截牆。多數頁面應正常渲染， 只有需要身份的動作按鈕轉為「登入後可用」。

GET /api/auth/me 的兩種回應

{ kind: "anonymous",
  anonymousId: "8f3c-…" }
{ kind: "authenticated",
  uid: "e12345",
  displayName: "陳彥廷",
  teamIds: ["platform"],
  roles: [{ role, scopeType, scopeValue }] }

現況落差

取得憑證後的實際工作清單

前端目前完全沒有登入 UI。全專案搜尋確認：web/src 下沒有任何一處呼叫 /api/auth/me 或 /api/auth/login。後端身份體系完整，前端尚未接上。 這代表 10.6 的工作量比「等一組憑證」要大。
#工作項內容是否需憑證
1config.ts 加入 OIDC 配置五個環境變數與 zod 驗證；非開發環境缺配置即 fail-closed否
2OAuth2IdentityProviderbeginLogin 組授權 URL、completeLogin 走 code→token→userinfo；state 防護實作否／測試是
3userinfo 欄位映射IdP 回傳欄位名對應到 uid／displayName／teamIds，需對方提供欄位規格是
4provider 注入點createIdentityModule 依環境選 provider 的分支加入 oidc 分支否
5前端登入頁與身份選單本線框第 6 節；含匿名／已登入／不可用三態否
6前端角色導覽控制依 /api/auth/me 的 roles 決定導覽項與動作鍵可用性否
7首位 platform_admin 授予開發環境靠 dev-admin 自動授予；正式環境需要一條 bootstrap 路徑，否則無人能授權他人需決策
8整合測試登入／登出流程、角色映射；需 IdP 測試租戶或 mock server是
第 7 項是容易被漏掉的阻塞點。正式環境沒有 dev-admin， 而授予角色本身需要 platform_admin。上線前必須先決定首位管理員如何產生 （環境變數指定 uid、一次性 CLI，或 migration 種子資料）。
可以先做的：第 1、4、5、6 項不需要任何外部憑證，佔清單過半。 憑證到位後只剩第 2、3 項的實作細節與第 8 項驗證。
