## Paper Tigers

**P1｜「模組化單體會變成大泥球」**
聽起來是經典技術債風險，但 PRD 的防禦相當具體：模組禁止直接修改其他模組的表、跨模組走應用服務與領域事件、Outbox 保證一致性。而且 Pilot 1 只有一條端到端路徑，模組邊界被實際使用的次數很少——真正的邊界侵蝕發生在多條路徑競爭時，那是 Phase E／F 的問題。
*成為真 Tiger 的條件*：Pilot 2 加入 MCP 後，若出現任何「Governance 直接讀 Installer 表」的捷徑且未被 code review 攔下。

**P2｜「10–20 人樣本太小，證明不了什麼」**
PRD 已經正面處理：明確聲明只提供方向性信號、要求 50 次獨立嘗試才做推廣 Gate、要求 Wilson 95% CI、禁止單點估計宣稱達標。這個克制程度超過多數同類文檔。擔心它反而是誤讀了文檔。
*成為真 Tiger 的條件*：有人拿 Pilot 1 的 15/17 成功率去做公司級推廣決策——防線在「50 次」這個數字有沒有被守住，不在樣本量本身。

**P3｜「員工不會改用平台，會繼續問群聊」**
補充資訊已澄清：強制推廣由組織漸進推動，群聊與諮詢作者始終保留為可選路徑，不作硬性約束。平台的任務是可靠好用，不是贏得渠道競爭。這條在原 red-team 中被高估了。
*成為真 Tiger 的條件*：組織側推廣完全沒有啟動，平台純靠自願採用——此時它會重新變成真風險。

**P4｜「Manifest Schema 設計不夠通用，未來要破壞性變更」**
PRD 已有明確處理：版本化 Schema、新增字段向後相容、破壞性變更用新 `apiVersion` ＋ 自動遷移工具，且 Contract Test 覆蓋向後兼容與遷移。Pilot 1 只有一個 Package，遷移成本近乎為零。
*成為真 Tiger 的條件*：跳過 `apiVersion` 機制直接改 `v1alpha1` 的語義——這是流程問題不是設計問題。

## Elephants in the Room

> 這一節是本次 pre-mortem 最該被討論的部分。前面的 Tiger 都有 owner 和 deadline，Elephant 沒有——因為它們需要的是對話，不是任務。

### E1｜項目有一部分動力來自老闆指令，這會讓 Gate 難以守住

**沒被說出口的是**：當項目的存在理由部分來自上層意志時，「Gate 未通過所以延期」在組織裡的成本，比「帶著 TBD 開工」高得多。T1 描述了機制，但 Elephant 是**沒人願意當那個說「不能開工」的人**。

PRD 把 Gate 寫得很硬，但硬約束只有在有人願意執行時才是硬的。

*對話起點*：「如果 Phase A 結束時 Support Matrix 還有兩個 TBD，我們希望誰來做這個判斷？現在把名字定下來，比到時候臨場決定容易。」

### E2｜「平台可靠性」是可交付的，「作者中斷下降」不完全是

**沒被說出口的是**：M5（作者中斷 ≤1 次／日）掛在項目上，但它的達成有很大一部分不在項目控制範圍內——取決於中斷的真實構成（A1b 已處理）、取決於組織推廣節奏、取決於員工習慣遷移速度。

而 M5 恰恰是最容易被拿去向上匯報的那個數字，因為它最直觀。

風險是：項目把平台做得又好又可靠（真正的交付物），但 M5 沒達標，於是被判定為失敗。或者反過來——為了讓 M5 好看，把試點範圍縮到最配合的幾個人。

*對話起點*：「M5 我們有多少把握？如果平台各項技術指標都達標但 M5 只降到 2 次／日，這算成功還是失敗？現在講清楚比事後解釋容易。」

### E3｜Owner 同時是試點對象、數據記錄者和項目推動者

**沒被說出口的是**：Phase A 要求 Owner 記錄自己被打斷的次數和耗時，然後這個數字會成為證明項目價值的基線。Owner 同時是最希望項目成功的人。

這不是質疑誠信問題——是**觀察者效應**。知道自己在記錄中斷次數，本身就會改變處理中斷的方式（比如把兩次相關提問合併成一次記錄，或者把「順便問的」不算進去）。PRD 的 Metric Contract 已經定義了合併規則（同一使用者同一問題 30 分鐘內合併），這降低了隨意性，但沒有解決結構性問題。

*對話起點*：「基線數據由 Owner 自己記錄，我們接受這個限制嗎？還是找一個非項目成員做交叉記錄？後者成本不高——每天一次五分鐘的確認。」

### E4｜`superpowers` 是外部開源技能，但 Pilot 1 要為它建立內部發布管線

**沒被說出口的是**：整個發布管線（作者提交 Git PR → Manifest 驗證 → 安全掃描 → Adapter Dry Run → 審批 → 簽名快照 → Registry）假設的是**內部作者發布內部技能**。但 `superpowers` 是外部項目，公共架構是它的推廣者不是作者。

這意味著 Pilot 1 驗證的是「內部團隊代理發布外部技能」這條路徑，而 Expansion 階段的主要場景是「內部作者發布自己的技能」——兩者在 Manifest 維護責任、版本跟進節奏、上游變更響應上完全不同。上游發了新版本，誰負責更新 Manifest、誰負責重跑 Spike 驗證？PRD 沒有處理。

*對話起點*：「`superpowers` 上游發新版時，我們的更新流程是什麼？如果這個流程和內部作者發布不一樣，Pilot 1 驗證的管線對 Expansion 有多少參考價值？」

### E5｜這個項目在證明「公共架構團隊值得投資」，而不只是在解決安裝問題

**沒被說出口的是**：設計檔裡有一句話——「公共架構技術賦能工程師的本職是建設研發效能基礎設施，但安裝支援正在延誤平台工作」。這句話同時是問題陳述和**團隊價值論證**。

這解釋了為什麼 PRD 的可觀測性部分（Goal 3、C13、M8）寫得比嚴格必要的更重——它不只是產品功能，也是團隊向上證明工作成效的載體。這本身沒有問題，但它會產生一個具體風險：**當 Check-in 能力（Q0）不可得時，放棄 M8 的心理成本會遠高於它的技術成本**，可能導致為了保住採用分析而選擇一個技術上更差的 Client。

*對話起點*：「如果唯一支援 Check-in 的 Client 不是公司主流客戶端，我們會怎麼選？是為了採用數據遷就 Client，還是為了覆蓋率放棄採用數據？」

## 一句話結論

技術風險（T2、T3）都有明確的檢驗點和降級路徑，這份 PRD 在這方面已經寫得比多數同類文檔紮實。

**真正的失敗路徑是組織性的**：Gate 沒人敢守（E1／T1）、指標歸屬不清導致成功被判為失敗（E2）、以及為了保住向上匯報的數據而做出技術上次優的選擇（E5）。

這三條都不能靠補文檔解決，只能靠 Phase A 啟動前的一次對話解決。
