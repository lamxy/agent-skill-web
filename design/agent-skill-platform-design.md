## Executive Summary

建立一個供互聯網企業內部員工使用的 Agent 技能交付控制面。第一階段不以「技能社區」為核心，而是解決技能從分享會、Wiki 和即時通訊進入員工工作環境時的依賴、版本、權限和安裝失敗。

平台以 Git 和開放 Manifest 為技能內容的真實來源，使用模組化單體承載 Catalog、Installer、Governance、Feedback、Analytics 與 Audit。這使第一階段可以快速交付，同時為評論討論、精品池、公司級推廣、強制或推薦安裝、外部開源等後續能力保留清楚的擴展邊界。

第一個必須被證明的結果：

> 公共架構技術賦能工程師不再每天被安裝問題打斷 3–5 次，並且能回答「多少人安裝成功、失敗在哪裡、目前運行哪個版本」。

## Problem Statement

目前公共架構、產品、前端、後端和 DBA 團隊都會建立、推廣或分享 Agent 技能、工作流和 MCP 工具。例如：

- 公共架構推廣 `superpowers`、基於 Git 工作樹的開發流程、SDD、TDD 和動態任務調度技能。
- DBA 團隊推廣 MySQL MCP。
- 產品團隊分享 `pm-skill`。
- 後端團隊分享 `gsd-core` 工作流。
- 員工為縮短開源工作流的運行時間，自行建立輕量版本，並透過即時通訊在小範圍傳播。

現有分發方式通常是宣講、Wiki、安裝檔案和即時通訊。員工自行閱讀教程、處理依賴、調整環境並排查版本問題。技能作者因而反覆回答相同問題，甚至親自協助安裝。

問題不是缺少技能，而是缺少可靠交付：

1. 員工不知道技能是否可信、是否適用於自己的 Agent、操作系統和專案環境。
2. 安裝失敗無法被結構化診斷，解決方式依賴作者個人支援。
3. 技能作者無法看見安裝成功率、首次可運行時間、失敗原因和活躍版本。
4. 自定義技能散落於即時通訊和個人目錄，難以被搜尋、維護、升級或下架。
5. 公共架構無法證明一次推廣是否形成真實採用。
6. 後續的審批、公司級推廣、權限、憑證和外部開源缺少統一治理入口。

## Demand Evidence

已觀察到的真實行為：

- 幾乎大部分接受宣講的員工都會嘗試安裝相關技能。
- 員工陸續向作者詢問如何安裝和使用。
- 技能作者一天被打斷 3–5 次，每次支援從數分鐘到半小時。
- 最常見失敗包括依賴、環境和版本問題。
- 部分員工因開源工作流耗時而建立更簡單、快速的自定義技能，並在即時通訊中分享。
- 公共架構技術賦能工程師的本職是建設研發效能基礎設施，但安裝支援正在延誤平台工作。

目前尚未建立可靠基線：

- 每個技能的安裝人數未知。
- 從開始安裝到首次成功運行的時間未知。
- 求助率和作者總支援時間未知。
- 各版本的活躍分布未知。

因此，第一階段必須同時交付安裝能力和採用可觀測性。只做瀏覽頁面無法驗證價值。

## Status Quo

```text
作者／公共架構建立或選擇技能
        ↓
分享會介紹功能
        ↓
Wiki + 安裝檔案 + 即時通訊連結
        ↓
員工逐人閱讀、安裝、配置和調試
        ↓
依賴／環境／版本失敗
        ↓
在群聊中詢問作者
        ↓
作者重複解答或遠程協助
        ↓
無統一成功記錄、版本分布或反饋閉環
```

真正的現狀競爭者不是另一個技能商城，而是「Wiki＋Git＋群聊＋作者人工支援」。

## Target User & Narrowest Wedge

### 核心使用者

公共架構技術賦能團隊中，負責推廣 `superpowers` 等技能的工程師。

他的本職工作是建設研發效能賦能基礎設施，但每天被安裝問題打斷 3–5 次。他需要：

- 以可重複方式發布和升級技能。
- 在員工安裝前發現依賴、環境、版本和權限問題。
- 讓常見問題可以自動修復或產生可執行診斷。
- 看見誰成功安裝、失敗在哪裡、哪些版本仍在使用。
- 在必要時下架、禁用或回滾存在風險的版本。

### 次要使用者

- 安裝技能的產品、前端、後端、DBA 和公共架構員工。
- 上架自定義技能的內部作者。
- 負責審批、公司級推廣、安全和開源發布的管理員。

### 第一階段楔子

用一個統一入口完成：

```text
發現可信技能
  → 檢查環境與權限
  → 一鍵安裝
  → 驗證首次運行
  → 回報成功或結構化失敗
  → 安全升級、卸載或回滾
```

## Goals

### 第一階段

1. 建立可信、可搜尋的技能與工具包目錄。
2. 建立可容納 Skill、Plugin、MCP 和 Bundle 的統一元數據模型；Pilot 1 把 `superpowers` 作為 Plugin 交付。若 Technical Spike 證明其實際包裝不是 Plugin，必須先修正文檔和支持矩陣，不能在實現中靜默改型。
3. 支援版本化上架、驗證、發布、升級、棄用、下架和緊急禁用。
4. 提供安裝前環境、依賴、版本、權限和憑證需求預檢。
5. 提供一鍵安裝、升級、卸載、失敗診斷與回滾。
6. 收集最小必要的安裝和運行結果，建立採用基線。
7. 讓作者看到失敗原因和優先修復建議。
8. 為後續治理與社區能力預留穩定 Schema、Adapter 和 Event 擴展點，不實現其頁面與工作流。

### 長期

- 點讚、踩、評論、討論和使用反饋。
- 領域池、推廣池、精品池、通用標準池。
- 公司級推薦、默認安裝或受控強制推廣。
- 多環境、憑證、權限、審批與完整審計。
- 以公司開源品牌完成外部開源審核和發布。
- 自動部署工作流、團隊基線和策略即代碼。

## Non-Goals for Phase 1

- 不建立新的 Agent Skill、Plugin 或 MCP 打包標準。
- 不把技能二進制或源碼複製進平台數據庫。
- 不實現完整社交動態流、關注關係或聲望體系。
- 不根據點讚數自動提升技能等級。
- 不在缺少安全審批與回滾前強制安裝公司級技能。
- 不將公司憑證、Token 或密鑰寫入技能包。
- 不拆分為多個獨立微服務。
- 不承諾第一階段支援所有 Agent 客戶端和操作系統。

## Constraints

1. 企業內部網絡、SSO、源碼託管和憑證系統需要被復用。
2. 不同員工的操作系統、Shell、Agent 客戶端和版本可能不同。
3. MCP 可能執行高權限操作，不能與純 Markdown Skill 使用相同信任策略。
4. 員工自定義技能需要低門檻上架，但不能直接獲得公司級推廣資格。
5. 安裝遙測必須遵守公司隱私政策，預設不收集提示內容、業務代碼或憑證。
6. 第一階段需要快速證明價值，但不能產生阻礙後續治理的核心模型債務。

## Product Principles

1. **可信與相容優先於熱門。** 先告訴員工能否安全運行，再顯示評分。
2. **安裝是一筆可觀測交易。** 每次安裝都有預檢、執行、驗證和回滾結果。
3. **Git 是內容真實來源。** 平台索引、驗證和治理，不吞掉原有工程工作流。
4. **權限必須可解釋。** 員工在執行前看見技能需要的文件、命令、網絡和資料權限。
5. **憑證只被引用，不被打包。** Manifest 聲明需要的憑證類型，運行時向企業憑證系統取得。
6. **推廣不是下載排行榜。** 技能層級提升必須依賴質量門檻、風險審核和真實採用數據。
7. **模組邊界先於微服務。** 第一階段保持單體部署，透過接口、事件和資料所有權保留拆分能力。

## Premises

1. 第一階段服務的核心人物是公共架構技術賦能工程師。
2. 第一個核心結果是降低安裝求助和作者中斷。
3. Git 與開放 Manifest 保持內容真實來源。
4. 第一版必須同時包含預檢、安裝、診斷、版本追蹤和採用數據。
5. 憑證不進入技能包，敏感能力需要審批和審計。
6. 社區、精品池、公司推廣和外部開源不能阻塞第一個可用版本。
7. 第一階段必須預留後續擴展空間，但不提前支付分散式系統成本。

## Landscape Findings

- Open Agent Skills 已定義以 `SKILL.md` 為核心、可附加 scripts、references 和 assets 的技能格式。
- Backstage 驗證了「元數據跟隨 Git、平台負責索引與發現」的軟件目錄模式。
- GitHub Copilot Plugins 已把 Skills、Agents、Hooks、MCP 和 LSP 組合成版本化插件，並支援 Marketplace。
- GitHub Enterprise MCP 管理採用 Registry、Allowlist 和客戶端執行模式。

結論：

> 平台不應成為新的包格式或新的 Git 替代品。它應成為公司內部的信任、策略、安裝編排和採用可觀測控制面。

## Approaches Considered

### Approach A: GitOps 技能目錄

Git 倉庫保存 Manifest，CI 驗證後生成瀏覽頁面，CLI 負責安裝和回報結果。

- 優點：交付最快，平台運維最低。
- 缺點：評論、討論和複雜治理加入後需要引入服務端數據模型。
- Effort：人工 4–6 週；AI 輔助 5–8 天。
- Risk：低。

### Approach B: 模組化技能交付控制面

建立獨立的模組化單體，承載目錄、安裝、治理、反饋、分析和審計。內容仍由 Git 管理，平台透過適配器支援不同包類型與 Agent 客戶端。

- 優點：第一階段完成交付閉環，後續能力可沿既有邊界擴展。
- 缺點：需要後端、數據庫、SSO、遙測和安裝器的初期投入。
- Effort：先完成 Pilot 0 後按選定的客戶端、OS、SSO 和分發渠道重估。概念區間為人工 7–10 週、AI 輔助 2–3 週，但這不是交付承諾。
- Risk：中。

### Approach C: 完整事件驅動平台

從第一天拆分 Catalog、Artifact、Policy、Workflow、Installation、Community 和 Analytics 服務。

- 優點：多團隊獨立開發與複雜治理的長期上限最高。
- 缺點：在採用模式未知時提前承擔分散式一致性和運維成本。
- Effort：人工 14–20 週；AI 輔助 4–6 週。
- Risk：高。

## Recommended Approach

選擇 **Approach B：模組化技能交付控制面**。

### 系統形態

```text
┌───────────────────────────────────────────────┐
│ Web Portal │ CLI / Local Executor │ IDE Adapter│
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│              Modular Platform API             │
├──────────┬───────────┬──────────┬─────────────┤
│ Catalog  │ Installer │Governance│ Feedback    │
│ Versions │ Adapters  │ Policy   │ Discussion  │
├──────────┴───────────┼──────────┴─────────────┤
│ Analytics / Audit    │ Identity / Permissions │
└──────────────────────┬────────────────────────┘
                       │
┌──────────────────────▼────────────────────────┐
│ Git │ CI │ Agent Clients │ Secret Manager     │
└───────────────────────────────────────────────┘
```

第一階段採用單一部署單元和單一關聯數據庫。模組禁止直接修改其他模組的表，跨模組操作透過應用服務和領域事件完成。事件先使用同庫 Outbox，不引入外部消息中間件；只有在吞吐、隔離或團隊所有權證明需要時才拆分。

### 控制面與本機執行邊界

平台 API 是控制面，不直接操作員工電腦。CLI 內含 Local Executor，在員工設備上執行預檢、安裝、驗證、卸載和回滾：

```text
Portal 建立意圖
  → 使用者完成 UserConsent，必要時等待 InstallationApproval
  → API 簽發短期 Installation Token 與簽名 InstallPlan
  → CLI 拉取並驗證計畫
  → Local Executor 在本機執行
  → CLI 只回報脫敏後的步驟狀態和錯誤碼
  → API 聚合 Installation 終態
```

- 本機文件內容、完整環境變數、業務代碼和長期憑證不離開設備。
- Pilot 1 使用企業 SSO Device Flow，InstallPlan Token 綁定使用者、PackageVersion、有效期和冪等鍵，只允許低風險試點原語。OAuth Device Flow 不被當作設備身份。
- 需要設備級策略、特權操作或高風險 MCP 時，必須使用 MDM 簽發的設備身份／證明與安全密鑰存儲；否則平台不得宣稱設備級管控。
- 斷線時 CLI 將事件寫入本機加密隊列；恢復連線後按序提交。服務端根據步驟序號去重。
- 本機執行完成但服務端未確認時，Installation 顯示 `result_pending_sync`，不能被誤判為失敗並重複執行。
- Portal 可以生成安裝命令或深層連結，但不能繞過 CLI 的本機確認與策略檢查。

中斷恢復規則：

1. Local Executor 只從最後一個具有本機執行證據的完成步驟恢復，不依賴服務端猜測。
2. 恢復前重新驗證 Artifact Digest、InstallPlan Digest、當前 Policy、Revocation List、Token、UserConsent 和 InstallationApproval。
3. Token 過期但其他摘要未變時，控制面重新評估後簽發新 Token。
4. 計畫、權限、版本或作用範圍改變時，原 UserConsent 和 InstallationApproval 失效，建立新的確認／審批流程。
5. 已完成步驟若不是冪等或無可證明補償，不允許自動恢復；進入人工處理終態。

## Domain Model

### Package

代表平台中可發現和治理的邏輯項目。

| Field | Meaning |
|---|---|
| `package_id` | 全局穩定 ID，不隨名稱或倉庫變更 |
| `type` | `skill`、`plugin`、`mcp`、`bundle` |
| `name` | 顯示名稱 |
| `owner_team` | 負責維護與支援的團隊 |
| `source_uri` | Git 倉庫及路徑 |
| `visibility` | 個人、團隊、領域、公司、公開 |
| `category` | 通用、業務領域、前端、後端、DBA 等 |
| `license` | 內部專用或 SPDX 開源許可證 |
| `lifecycle` | Package 容器狀態：`active` 或 `archived` |
| `trust_tier` | 自定義、已驗證、領域、推廣、精品、通用標準 |

### PackageVersion

版本內容與發布狀態分離：

- `PackageVersionContent` 是不可變身份，由 Package ID、Version、Artifact Digest、Manifest Digest 和 Source Commit 唯一確定。
- `ReleaseStateEvent` 是追加式生命週期記錄。當前發布狀態由事件折疊得出，不修改版本內容或覆蓋歷史。

| Field | Meaning |
|---|---|
| `version` | SemVer 或來源格式的規範化版本 |
| `source_commit` | Git commit |
| `content_digest` | 安裝內容摘要 |
| `artifact_uri` | CI 發布的簽名不可變快照 |
| `manifest_schema_version` | 平台 Manifest 版本 |
| `compatibility` | OS、架構、Agent 客戶端及最低版本 |
| `dependencies` | 系統、Runtime、技能和 MCP 依賴 |
| `permissions` | 文件、命令、網絡、資料和憑證需求 |
| `install_plan` | 適配器可執行的聲明式步驟 |
| `validation_result` | 格式、安全、測試和策略結果 |
| `release_notes` | 變更與遷移說明 |
| `lifecycle` | `draft`、`validating`、`validation_failed`、`review_required`、`published`、`deprecated`、`delisted`、`emergency_disabled` |

### Installation

> ⚠️ **本節已過時** — 狀態機對應原語模型的執行流程。
> 現行方案見 PRD §4 Installation 資料模型。詳見文件頂部警示。

記錄某個使用者或受管設備上某版本的安裝狀態。

```text
requested
  → preflight_running
  → preflight_blocked ──→ cancelled
  → consent_required ──→ cancelled
  → approval_required
       ├→ approval_rejected
       ├→ approval_expired
       └→ approval_granted
  → installing
  → verifying
  → succeeded
  → failed
  → rolling_back
  → rolled_back
  → local_conflict
  → uninstalling
  → uninstalled
```

每次 Installation 保存：

- 目標客戶端與環境指紋的非敏感摘要。
- 預檢項目及結果。
- 經脫敏和分類的失敗碼。
- 開始、成功、失敗和回滾時間。
- 安裝器及 Manifest 版本。
- 是否需要人工協助。

不保存提示內容、業務源碼、密鑰或完整環境變數。

`result_pending_sync` 是客戶端同步視圖，不是可執行的服務端狀態；服務端仍停留在最後已確認狀態，直到收到帶序號和簽名的結果。

`local_conflict` 是 upgrade、uninstall 或 rollback 的可恢復結果，不是靜默成功或一般失敗。它保存受管資源、Baseline／Managed／Current 摘要、衝突類型和需要的使用者操作。解決後以新冪等鍵從衝突步驟恢復；未解決記錄不計入成功率，單獨進入人工介入指標。

### Policy

描述可發現、可安裝、需審批和推廣規則：

- 哪些信任層級可以在什麼環境運行。
- 哪些權限需要使用者、團隊主管、安全或 DBA 審批。
- 哪些 Package 或版本被允許、阻止或緊急禁用。
- 公司級推廣是推薦、默認安裝還是強制安裝。
- 強制推廣的延期窗口、例外和回滾規則。

### PublicationReview, InstallationApproval and UserConsent

三者不得共用一個 Approval 對象：

- `PublicationReview`：PackageVersion 上架與發布審核。
- `InstallationApproval`：特定使用者、環境和 PackageVersion 的特權安裝批准。
- `UserConsent`：員工對本次 InstallPlan 權限和影響的確認，不代表管理審批。

`PublicationReview` 與 `InstallationApproval` 使用：

```text
pending → approved | rejected | expired | cancelled
approved → revoked
```

- Policy 根據 Package 類型、權限、環境和信任層級解析審批角色，不把個人姓名寫死在 Package。
- Pilot 1 只支援單人審批；多方會簽與升級鏈延後，但資料模型保留 `approval_group` 和 `required_count`。
- 審批有有效期。PackageVersion、權限集合、目標環境或審批人角色發生變更時，舊審批失效。
- 同一冪等鍵只產生一個有效審批；拒絕、撤銷和過期都保留理由。
- Policy 評估輸入、規則版本、決策和責任人解析結果進入審計，保留期沿用公司安全審計政策；若公司尚無政策，生產前必須確定。
- `InstallationApproval=approved` 後，控制面重新評估 Policy，再簽發新的短期 Installation Token；舊 Token 不恢復。
- 拒絕、過期或撤銷將 Installation 轉入對應終態。撤銷發生於執行中時，Local Executor 在下一安全步驟停止並按 InstallPlan 補償。
- UserConsent 綁定 InstallPlan 摘要；計畫、權限或 PackageVersion 改變後必須重新確認。
- `InstallationApprovalRequested` 事件由公司通知渠道發送給解析出的審批角色；超時前提醒一次，Pilot 1 不自動升級到其他角色。

PublicationReview 的撤銷語義：

- 發布前撤銷：PackageVersion 回到 `review_required`。
- 發布後不能只撤銷歷史 Review 來改變運行狀態；管理員必須顯式執行 `delist` 或 `emergency_disabled`，生成獨立 ReleaseStateEvent 和審計記錄。

### Feedback

第一階段只保存結構化使用反饋和「需要人工協助」標記。模型預留：

- Vote：讚或踩。
- Review：帶版本和使用場景的評價。
- Discussion：主題式討論。
- Issue：安裝、運行、文檔或安全問題。
- PromotionEvidence：質量、採用和風險證據。

## Module Boundaries

### Catalog

- Package、PackageVersion、分類、所有權、可見性和搜尋。
- 從 Git 同步 Manifest。
- 不執行安裝，不決定審批。

### Installer

- 預檢、安裝計畫、執行、驗證、回滾和卸載。
- 按 Package 類型與 Agent 客戶端選擇適配器。
- 不持有長期憑證，只取得短期引用。

### Governance

- 上架審核、信任層級、推廣、棄用、下架和緊急禁用。
- Policy 評估和審批工作流。
- 不直接修改技能內容。

### Feedback

- 使用反饋、讚踩、評論和討論。
- 第一階段僅啟用結構化使用反饋。

### Analytics

- 聚合採用、成功率、首次運行時間、求助率和版本分布。
- 只接收定義過的事件，不讀取業務提示或代碼。

### Identity & Audit

- SSO 身份、團隊和角色映射。
- 記錄審批、策略、發布、安裝、推廣和管理員操作。

## Adapter Model

> ⚠️ **本節已過時** — preflight/plan/install 接口在腳本模型下不適用。
> 現行方案見 PRD §3 M3 腳本生成器。詳見文件頂部警示。

每個安裝適配器實現穩定接口：

```text
detect(context) -> CompatibilityResult
preflight(packageVersion, context) -> Check[]
plan(packageVersion, context) -> InstallPlan
install(plan) -> ExecutionResult
verify(packageVersion, context) -> VerificationResult
upgrade(from, to, context) -> ExecutionResult
uninstall(packageVersion, context) -> ExecutionResult
rollback(execution, context) -> ExecutionResult
```

第一階段只選擇公司最常用的 1–2 個 Agent 客戶端及主要操作系統。其他客戶端透過新適配器加入，不修改 Catalog 或 Governance。

### InstallPlan 限制

> ⚠️ **本節已過時** — 原語模型已被三段式腳本模型取代。
> 現行方案見 PRD §2.1 一鍵安裝腳本模型。詳見文件頂部警示。

InstallPlan 不是任意 Shell 腳本。每一步必須使用平台審核過的操作原語：

```text
download_verified_artifact
create_directory
write_managed_file
merge_structured_config
create_symlink
register_client_plugin
start_approved_service
verify_file_digest
verify_client_registration
```

- 每個原語有參數 Schema、允許路徑、超時、日誌脫敏和平台版本。
- 每個原語提供本地化的人類可讀預覽和機器可讀 `EffectSummary`，列出將建立、修改、刪除或啟動的資源；CLI 在 UserConsent 前展示，不把原語偽裝成 Shell 命令。
- 純 Skill 不允許執行腳本。
- Plugin 只能使用受支持客戶端的註冊原語。
- MCP 若需要進程或容器，只能使用已審核的啟動原語和固定入口；任意命令需更高信任層級、沙箱和顯式審批，Pilot 1 不支援。
- 每個步驟聲明 `reversible`、`compensation` 和 `side_effect_scope`。
- `reversible=false` 的步驟不得包含在 Pilot 1；後續高風險流程必須顯示不可逆影響並取得單獨確認。

### Managed Resource Ownership

> ⚠️ **本節已過時** — 依賴平台管控每一步副作用，腳本模型下不成立。
> 現行方案見 PRD §2.4 發布審核標準。詳見文件頂部警示。

Local Executor 為每個受管資源保存：

- PackageVersion、InstallPlan 和步驟 ID。
- 安裝前 Baseline Digest、安裝後 Managed Digest。
- 由平台擁有的文件、目錄、符號連結或結構化配置鍵。
- 結構化配置的字段級 Provenance，不把整個使用者文件視為平台所有。

升級、卸載和回滾規則：

1. 資源仍等於 Managed Digest 時，可以執行原定補償。
2. 使用者修改後，使用 Baseline、Managed 和 Current 做三方合併。
3. 無法安全合併時進入 `local_conflict`，展示差異並停止，不覆蓋或刪除。
4. 平台只刪除自己建立且未被修改的資源。
5. 使用者擁有的文件只移除平台管理的配置鍵；字段來源不明時保留文件並產生人工清理指引。

### Dependencies and Bundles

- PackageVersion 依賴使用穩定 Package ID 和 SemVer 範圍。
- 發布時解析完整傳遞依賴，拒絕循環依賴和無解約束。
- 解析結果生成不可變 Lockfile，記錄每個成員版本與摘要。
- 安裝嚴格使用 Lockfile，不在員工設備上重新選版本。
- 同一 Package 的兩個不相容版本需求產生 `DEPENDENCY_VERSION_CONFLICT`，不自行選擇較新版本。
- Bundle 是一組 PackageVersion Lockfile。Pilot 1 只支援 Catalog 發現，不支援 Bundle 安裝。
- 後續 Bundle 安裝預設原子化；若成員包含不可逆外部副作用，必須明確標記為非原子並逐步審批。

## Lifecycle and Promotion

### Package 生命週期

```text
active → archived
archived → active
```

Package 只代表穩定身份與版本容器。只要仍有需要保留的版本、安裝或審計記錄，就不做物理刪除。

### PackageVersion 發布生命週期

```text
draft → validating → review_required → published
published → deprecated → delisted
published | deprecated | delisted → emergency_disabled

validation_failed → draft
```

下架不等於刪除：

- 新使用者不能安裝。
- 既有使用者收到替代或卸載指引。
- 審計與歷史安裝記錄保留。
- 緊急禁用可阻止後續啟動，但必須有明確權限和審計。

合法轉換由 Governance 模組集中定義。`deprecated` 仍允許既有使用者運行和受控安裝；`delisted` 不允許新安裝；`emergency_disabled` 覆蓋其他版本狀態並阻止策略範圍內的新啟動。

### Installation 生命週期

Installation 狀態機只描述一次目標設備上的交付交易，不承載 Package 發布狀態。PackageVersion 狀態變更可以觸發通知、卸載或禁用策略，但不能直接篡改歷史 Installation 終態。

### 信任金字塔

```text
個人／自定義
  → 團隊或領域已驗證
  → 公司推廣
  → 精品
  → 通用標準
  → 內部標準或外部開源
```

每次提升與下降都產生 `TierChanged` 事件，保存操作者、理由、證據和生效範圍。第一階段只實現「自定義、已驗證、公司推廣」三層，其他層保留枚舉和策略擴展點，不啟用流程。

## Installation Safety

1. 下載後驗證內容摘要，發布版本不可原地覆蓋。
2. 顯示權限差異，升級新增權限時重新取得同意或審批。
3. 安裝到暫存位置，驗證成功後原子切換。
4. 保留上一個可用版本和回滾資料。文件和結構化配置使用補償動作；依賴安裝、憑證授權或外部系統副作用必須被標記為不可自動回滾。
5. MCP 及可執行腳本按風險等級執行靜態掃描、依賴檢查和沙箱策略。
6. 安裝器只使用短期憑證，日誌執行脫敏。
7. Registry 或 Policy 不可用時，受管高風險工具採失敗關閉；已安裝的低風險純文本 Skill 可按本地快取策略繼續運行。
8. 緊急禁用必須能按版本和範圍生效，並提供受控回滾。

### Emergency Revocation

> ⚠️ **本節已過時** — A0 證明五個客戶端均無 Check-in 與遠端停用能力。
> 現行方案見 PRD §2.6 平台能力邊界。詳見文件頂部警示。

- 在線受管 CLI 使用推送或每 5 分鐘拉取簽名 Revocation List，成功後保存帶到期時間的本機快取。
- 高風險 MCP 的禁用快取最大 TTL 為 30 分鐘；快取過期且控制面不可達時失敗關閉。
- 低風險純文本 Skill 可在離線狀態繼續運行最多 24 小時；超時後提示重新連線，不自動刪除本機內容。
- Revocation List 包含 PackageVersion 摘要、作用範圍、理由碼、生效時間和最低 CLI 版本。
- 低於最低安全版本的 CLI 不允許啟動受管高風險 Package。
- 客戶端套用禁用後回傳簽名回執；控制面顯示已確認、待確認和離線設備。
- 策略恢復不會自動重啟被禁用的 Package，必須由使用者或管理員重新啟用。

Revocation 記錄使用以下匹配字段：

```text
package_id, version_range, content_digest,
organization_id, team_ids[], user_ids[], device_ids[],
environment, client_name, effective_at, expires_at,
action, reason_code, minimum_cli_version, priority
```

- 更具體的 Scope 優先於較廣 Scope；同等具體度時，更高 `priority` 優先；仍衝突時採更嚴格 Action。
- Pilot 1 只使用 organization、PackageVersion 和 Client Scope；Team、User、Device Scope 在具有可信身份來源後啟用。
- Action 由適配器實現：`block_launch`、`disable_registration`、`terminate_managed_process`、`quarantine_files`。
- 純文本 Skill 通常只能阻止受管客戶端再次載入；平台不宣稱能終止已在模型上下文中的內容。
- Plugin 必須由客戶端提供可驗證的停用接口，否則只能在下一次客戶端啟動時禁用。
- 長期運行 MCP 只有在平台管理的 Process Supervisor 下才能承諾 `terminate_managed_process`；非受管進程標記為 `manual_containment_required` 並通知管理員。
- 每個 Action 回傳 `applied`、`unsupported` 或 `manual_required` 回執。
- Pilot 1 的「在線」只指最近 5 分鐘內提交過簽名 Check-in 的 Installation，不宣稱具有設備身份。Device Scope 和「受管設備」措辭只在 MDM 證明啟用後使用。

### Technical Spike Gate

> ⚠️ **本節已過時** — Gate 機制已隨定位變更取消。
> 現行方案見 PRD §6 實施中的待解難題。詳見文件頂部警示。

Pilot 1 開發前，必須針對真實 `superpowers` Plugin、選定 Client 和 OS 完成：

1. 將現有人工安裝轉換成只包含批准原語的 InstallPlan。
2. 從 Git commit 產生簽名不可變 Artifact，並以摘要安裝。
3. 在乾淨環境完成安裝、驗證、升級、卸載和回滾。
4. 在每個步驟注入斷線、權限不足、磁盤不足、內容被使用者修改和進程中止故障。
5. 證明 Managed Resource Ownership 和三方合併不覆蓋使用者修改。
6. 列出所有不可聲明化或不可逆步驟。
7. 證明選定 Client 的 Plugin 停用方式、Check-in 傳輸機制和禁用生效時點。
8. 在最近 Check-in 的試點安裝上量測 Revocation 傳播、接收、套用和回執延遲。

Exit Gate：所有 Pilot 1 步驟可逆且能由批准原語表示，Support Matrix 不含 `TBD`，而且禁用行為與 Check-in SLO 有實測證據。否則縮小自動化範圍、降低禁用承諾或停止 Pilot，不能用任意 Shell 腳本繞過。

### Pilot 1 Minimum Path and Launch Blockers

最低可發布路徑：

```text
SSO 使用者
 → Web 查看已發布 superpowers Plugin
 → CLI 預檢與 UserConsent
 → 取得簽名 Artifact 和 InstallPlan
 → 本機安裝、驗證、回報
 → 作者查看成功與失敗
```

硬阻塞：

- 沒有簽名 Artifact Registry：不得發布可安裝版本。
- 沒有可靠 CLI 分發與自更新：不得宣稱緊急禁用 SLO。
- 沒有 SSO：只能做隔離技術演示，不進入員工試點。
- 沒有設備身份：只允許使用者綁定的低風險 Plugin 操作，不允許設備級或高風險策略。
- 沒有結構化預檢和回滾：不得開放自助安裝。
- 沒有隱私批准的事件 Schema：只保留本機診斷，不上報採用分析。
- 沒有 Git/CI 自動同步：可以由管理員手工導入單一簽名版本，但不得擴展多作者上架。

### Pilot 1：閉環安裝

先以 10–20 名來自後端、前端、產品和 DBA 的員工做可用性與錯誤分類試點，使用平台安裝同一版本：

- 觀察使用者，不做引導式演示。
- 記錄預檢命中率和自動修復率。
- 每個失敗必須落入可操作錯誤分類。
- 與 Pilot 0 基線比較作者支援成本。

10–20 人只能產生方向性信號，不能證明跨公司普遍效果。若進入公司級推廣決策，至少累積 50 次獨立安裝嘗試，並報告成功率的 Wilson 95% 信賴區間；不以單一點估計宣稱達標。

### Pilot 2：第二種 Package 類型

加入 MySQL MCP，驗證：

- 權限聲明。
- 憑證引用。
- DBA 審批。
- 高風險工具的允許清單和審計。

Pilot 2 只接受 DBA 預批准的單一 MySQL MCP、固定版本、固定啟動方式、只讀資料庫角色和最小權限模板。不在此里程碑承諾通用 MCP 腳本掃描或跨 OS 沙箱。

### Expansion

在兩種類型和兩個團隊完成閉環後，再引入 `pm-skill`、`gsd-core` 和員工自定義技能上架。

## Success Criteria

> ⚠️ **本節已過時** — 目標值改為上線後依真實數據設定。
> 現行方案見 PRD 附錄 A。詳見文件頂部警示。

Pilot 1 在兩週內提供方向性信號；累積至少 50 次獨立安裝嘗試後再做推廣 Gate。目標：

1. 從安裝意圖到本機驗證的成功率至少 90%，同時單獨報告通過預檢後的執行成功率。
2. 首次可運行時間中位數低於 5 分鐘。
3. 需要作者人工協助的安裝比例低於 10%。
4. 試點作者被安裝問題打斷從每日 3–5 次降到每日不超過 1 次。
5. 100% 安裝結果具有成功、失敗或回滾終態。
6. 100% 失敗具有結構化錯誤碼，且不包含憑證、提示或業務代碼。
7. 發布後可以看見活躍版本分布和待升級使用者。
8. 最近 5 分鐘內有簽名 Check-in 的 Pilot Installation，在 10 分鐘內完成緊急禁用確認；無近期 Check-in 的安裝不進入此 SLO 分母，按離線風險窗口單獨報告。回滾演練在 10 分鐘內完成只適用於全部步驟可逆且在線的 InstallPlan。

如果無法先取得可靠基線，成功標準 3 和 4 改為相對改善至少 70%，但必須在試點前固定計算方式。

### Metric Contract

> ⚠️ **本節已過時** — 指標定義已隨腳本模型重寫。
> 現行方案見 PRD §2.3 遙測字段白名單、§3 M6 分析頁。詳見文件頂部警示。

Pilot 0 結束前凍結以下定義：

| Metric | Definition |
|---|---|
| 獨立安裝嘗試 | 同一使用者、設備、PackageVersion 在 24 小時內以第一個冪等鍵計一次 |
| 意圖到驗證成功率 | `succeeded` 的獨立安裝嘗試 ÷ 所有建立安裝意圖的獨立嘗試；預檢阻塞、執行失敗和超時都在分母，使用者取消與策略拒絕分層展示 |
| 合格預檢後執行成功率 | `succeeded` ÷ 進入 `installing` 的獨立嘗試，用於區分預檢問題與執行器問題，不作唯一推廣 Gate |
| 首次可運行時間 | 從 CLI 接受簽名 InstallPlan 到本機 `verify` 成功；等待人工審批時間單獨報告 |
| 需要人工協助 | 使用者提交「需要協助」、作者建立關聯支援記錄，或試點觀察員記錄人工介入，任一即為 true |
| 活躍安裝 | 最近 30 天由受支持 Adapter 回報一次可驗證 Usage Ping 的成功 Installation；Revocation Check 只證明設備在線，不證明使用 |
| 待升級使用者 | 活躍安裝版本低於當前推薦版本，且相容性和 Policy 允許升級 |
| 作者中斷 | Owner 記錄的一次非計劃同步支援接觸；同一使用者同一問題 30 分鐘內合併 |

- 成功率同時報告分子、分母和 Wilson 95% 信賴區間。
- 缺少終態超過 24 小時的記錄列為 `unknown`，單獨展示且不得排除於報告。
- 指標只使用 Package ID、Version、錯誤碼、時間、Client、OS 大版本和匿名設備 ID；不收集提示、代碼、完整命令或憑證。
- 「真實採用」在 Pilot 1 只定義為成功安裝加一次本機驗證；七日活躍與業務任務完成屬於後續指標。

每個 Adapter 必須聲明它是否能產生 Usage Ping、事件來源和最小頻率。Pilot 1 Plugin Adapter 是硬合同：客戶端運行期間至少每 5 分鐘產生簽名 Check-in，Plugin 載入時產生去重 Usage Ping。若選定客戶端無法提供這兩項，Pilot 1 不得宣稱活躍版本分布、待升級名單或 10 分鐘禁用 SLO，相關成功標準必須在啟動前移除或降級。

## Open-Source Export

後續外部開源不直接公開內部 Package：

1. 建立公開分支或導出倉庫。
2. 移除公司域名、內部路徑、憑證引用和專用策略。

## Security and Privacy

- SSO 與 RBAC 控制發布、審批、推廣、下架和緊急禁用。
- PackageVersion 內容摘要不可變；高信任版本要求簽名。
- 不執行未驗證來源提供的任意安裝腳本。
- MCP 依照工具級權限與資料敏感度分類。
- 憑證由企業 Secret Manager 或短期 Token 服務提供。
- 日誌預設脫敏，禁止保存環境變數全集。
- 使用者可查看安裝器將執行的操作原語、參數摘要、資源影響和權限；Pilot 1 不展示或接受任意 Shell 命令。
- 管理員操作、策略變更和審批全部進入不可抵賴審計。
- 遙測只收集平台定義事件；任何新增字段需經隱私審核。
- 外部開源導出必須通過 Secrets 與 License Gate。

## Failure and Edge Cases

- Git 倉庫不可用：Catalog 顯示最後同步狀態，不允許發布未知內容。
- Registry 不可用：已快取低風險技能可按策略運行，高風險 MCP 不允許新啟動。
- 安裝中斷：重試使用冪等鍵，狀態恢復到最後可證明步驟。
- 升級失敗：原子切換前不破壞舊版本；切換後失敗立即回滾。
- 作者刪除或轉移倉庫：Package 保持穩定 ID，進入來源異常狀態。
- 版本被重打 Tag：內容摘要不一致時拒絕同步。
- 使用者有本機自定義：安裝前展示差異，預設不覆蓋。
- 技能新增權限：升級前重新確認或審批。
- 技能下架但仍在使用：保留審計，通知替代版本並按風險決定禁用。
- 同名 Package：以穩定 ID、來源和所有者區分，顯示名稱不作唯一鍵。
- 長名稱、零搜尋結果、部分分析數據和遙測延遲：UI 提供明確狀態。
- 本機完成但回報斷線：保留加密結果隊列，服務端顯示 `result_pending_sync`，不重複執行。
- 審批人在等待期間失去角色：重新解析責任人，原審批不再有效。
- 禁用清單過期：高風險 MCP 失敗關閉，低風險 Skill 按 24 小時離線窗口處理。
- 安裝包含不可逆外部副作用：Pilot 1 拒絕；後續只能在顯式審批、確認和補償手冊存在時執行。

5. Secret Manager 或短期憑證服務。
6. 是否已有 Backstage 或其他內部開發者門戶。
7. 允許收集的安裝遙測字段。
8. 公共架構、安全、DBA、法務和開源辦公室的審批責任。

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| 先建商城、後補安裝 | 平台有瀏覽量但不降低支援成本 | Pilot Gate 必須以安裝和作者中斷為成功標準 |
| 支援過多客戶端 | 適配器矩陣拖慢交付 | 第一階段只選 1–2 個客戶端 |
| 執行任意腳本 | 供應鏈與終端安全風險 | 聲明式計畫、掃描、簽名、沙箱與權限差異 |
| 遙測收集過度 | 員工不信任或觸犯政策 | 最小事件 Schema、脫敏、隱私審核 |
| 提前微服務化 | 延遲 MVP 並增加故障面 | 模組化單體＋Outbox，按證據拆分 |
| 作者維護責任不清 | 技能過期和無人支援 | 強制 Owner、支援渠道和棄用策略 |
| 強制推廣無回滾 | 大範圍破壞開發環境 | 分批推廣、延期窗口、例外和回滾演練 |
| 自定義技能泛濫 | 搜尋噪音與重複技能 | 可見性分層、重複檢測、領域審核 |

## The Assignment

在寫平台代碼前，選擇 `superpowers` 做一次兩週基線試點：

1. 指定一名公共架構技術賦能工程師為 Owner。
2. 招募 10–20 名真實員工。
3. 記錄每人的操作系統、Agent 客戶端、開始時間、成功時間、失敗類型和是否求助。
4. 記錄 Owner 每天被打斷次數和支援耗時。
5. 收集現有 Wiki、安裝檔案和最常見的 10 個問題。
6. 用這些結果固定第一個客戶端、第一個操作系統、預檢規則和 Pilot 1 成功基線。

這個試點不是演示。讓員工自行使用現有材料，不在旁邊指導；觀察他們真正卡住的位置。

## What I Noticed About How You Think

- 你最初描述的是完整金字塔：「個性化技能池 → 領域技能 → 推廣技能 → 精品 → 通用標準 → 內部／開源」，但接受先用可靠交付取得第一批真實採用。
- 你補充「第一階段為後續擴展預留下可擴展的空間」，這直接排除了純頁面式 MVP，也避免為了遠期願景提前拆微服務。
- 當被要求提供需求證據時，你沒有停在「大家都需要」，而是補充了分享會、Wiki、自行安裝、即時通訊傳播和作者反覆支援的完整現狀。
- 你把技術賦能工程師每天被打斷 3–5 次與平台開發延期連起來，這讓項目有了可衡量的內部投資回報。

## Reviewer Concerns

三輪對抗式審閱後仍有兩項不能靠文檔推理消除的外部證據缺口：

1. Pilot 1 的 Client、Client Version、OS、OS Version、Package Version、Adapter 和 Artifact Digest 尚未由 Pilot 0 實測確定。Support Matrix 存在任何 `TBD` 時，不得開始估算或實現。
2. 10 分鐘緊急禁用 SLO 取決於選定 Client 是否支援 5 分鐘簽名 Check-in 和可驗證 Plugin 停用。Technical Spike 未證明前，這只是候選目標，不是交付承諾。
